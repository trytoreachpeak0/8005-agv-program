# UC-004 仓门安全联锁

## 描述

本 UC 是一条贯穿多仓位 AGV 全生命周期、跨所有业务与维护场景的通用安全联锁能力，核心是维护一条物理事实约束："任一仓位仓门处于开启状态"与"该 AGV 处于移动状态"这两个条件不能同时成立。本 UC 不属于任何具体站点操作用例的 Precondition，而是由两条独立的检查/监控 Flow 组成，被其他 UC 在需要"开门"或"移动"时统一调用：

* **Flow A（开门前核验，事前预防）**：任意业务或维护流程（如 [[uc-001-load-completed-lot-into-slot|UC-001]]、[[uc-005-retrieve-mis-stored-product-from-slot|UC-005]]、[[uc-010-unload-completed-lot-at-destination-station|UC-010]] 等）要对某台 AGV 的某个仓位下发"开锁/开门"指令之前，必须先经过本 Flow 的核验：若判定该 AGV 当前处于移动状态，直接拒绝本次开门请求，不允许下发开锁指令；只有判定该 AGV 当前处于静止状态，才允许发起方继续其开门动作。
* **Flow B（开启期间监控，事后兜底）**：只要该 AGV 存在任一仓位仓门处于开启状态，本地服务器就持续轮询 RIOT，读取该 AGV 是否处于移动状态；一旦检测到移动（包括意外移动，例如仓门开启期间该 AGV 被重新调度接到新任务），系统会先核验当前 RIOT 正在执行的移动任务是否为本系统下发：若确认是本系统下发的任务，则下发"暂停"指令让 AGV 停止，待全部仓门关闭后再下发"恢复"指令使其继续原任务移动；若确认不是本系统下发（或无法判定来源），则直接下发"取消"指令彻底终止该任务，不负责后续恢复。

两条 Flow 互为补充、缺一不可：Flow A 只能保证"下发开锁指令那一刻"AGV 是静止的，无法防止仓门物理打开之后该 AGV 又被重新调度而移动，这部分风险由 Flow B 的持续监控兜底；反过来，若只有 Flow B、没有 Flow A，则每次开门都要先经历"门已打开、AGV 才被检测到在动"的短暂风险窗口才能触发拦截，安全性弱于事前拦截。

> 判断"是否需要拦截/拦停 AGV 移动"的标准只取决于"仓门是否开启 + AGV 是否在移动/将移动"这一物理事实，与任务来源无关；任务来源只决定 Flow B 拦停之后采用哪种处理方式（暂停待恢复 / 直接取消），因为对于非本系统下发的任务，本系统不掌握其完整上下文，无法安全地代其恢复。Flow A 的核验则不需要判断任务来源，只需要移动状态本身——移动中就一律拒绝开门，不存在分支。

## 触发条件

本 UC 由两类独立事件触发，对应两个不同的检查时机：

1. （Flow A）任意业务/维护类 UC 在正式对某台 AGV 的某个仓位下发"开锁/开门"指令之前，先调用本 UC 完成一次核验，本 UC 据此返回"允许开门"或"拒绝开门"结论。
2. （Flow B）该 AGV 任一仓位仓门状态变为"开启"后，系统开始持续轮询 RIOT 获取该 AGV 的移动状态；轮询期间检测到该 AGV 处于"移动中"且仍有仓门开启，即触发本 Flow 的拦停处理，直至该仓门重新关闭为止监控才结束。

## 前置条件

**系统与接口**

1. 本地服务器与 RIOT 之间通信正常，可随时查询该 AGV 是否处于移动状态：Flow A 每次开门前查询一次，Flow B 在门开启期间持续轮询（见 Exception Flow EA1.1 / EB1.1）。
2. RIOT 返回的 AGV 状态中包含可用于判定"当前执行的移动任务是否为本系统下发"的字段（如任务 ID），供 Flow B 比对任务来源使用（已与 RIOT 确认支持）；Flow A 的核验不依赖该字段，只需要移动状态本身，不判断来源。
3. RIOT 提供"暂停（pause）"与"恢复（resume）"接口，且本系统下发的移动任务被暂停后可原地恢复、继续原路径/目标点，不丢失任务上下文（已与 RIOT 确认支持），供 Flow B 使用。

## 后置条件

**设备与硬件**

1. （Flow A）若核验判定该 AGV 当前处于移动状态：本次开门请求被拒绝，目标仓位仓门保持关闭，发起方不会下发开锁指令。
2. （Flow A）若核验判定该 AGV 当前未处于移动状态：核验通过，放行发起方继续其自身流程下发开锁指令；本 UC 对本次开门动作的事前核验到此结束，后续由 Flow B 的持续监控接管保护。
3. （Flow B）若触发拦停时执行的是本系统下发的任务：该移动任务被暂停，AGV 停止移动；待该 AGV 全部仓位仓门恢复"关闭"后，该任务被恢复，AGV 继续原任务移动。
4. （Flow B）若触发拦停时执行的是非本系统下发的任务（或无法判定来源）：该移动任务被取消终止，AGV 停止移动，本系统不负责后续恢复该任务。

**任务与数据**

5. 本次安全联锁事件（触发时间、触发分支：Flow A 拒绝开门 / Flow B 暂停待恢复 / Flow B 取消、涉及仓门、任务来源判定结果（仅 Flow B 适用）、采取的处理方式）被记录到本地数据库，用于追溯。

## 假设

1. 本 UC 是纯软件层的安全机制：基于按需查询（Flow A）与持续轮询（Flow B）RIOT 状态判断并下发拒绝/暂停/取消/恢复指令，不涉及仓位仓门与 AGV 底盘运动之间的机械/电子硬件互锁；查询/轮询周期与指令下发的及时性直接决定本机制的实际防护效果。若业务上需要更高等级的安全保障（如物理层面直接禁止移动或禁止开锁），需由其他硬件方案另行覆盖，不在本 UC 范围内。
2. 只要该 AGV 已停止移动（无论是 Flow B 的暂停还是取消），或本次开门请求已被 Flow A 拒绝，仓门开启期间的人员/产品安全风险即视为已消除；本 UC 不进一步核验"停止"或"拒绝开门"这两个动作本身是否会带来其他次生风险（如急停对车上产品/设备造成的冲击）。
3. Flow A 的核验与发起方实际下发开锁指令之间存在极短的时间窗口，理论上仍可能出现"核验通过瞬间、该 AGV 因其他并发调度请求开始移动，随后仓门才被物理打开"的极端竞态场景；本 UC 假设该窗口足够短、业务上可接受，不作为 Exception Flow 处理。若需要更强保障（如与选车/下发环节做原子性锁定），需额外与用户确认（见备注）。
4. Flow A 核验通过、允许开门之后，若该 AGV 在仓门实际开启期间又被调度接到新的移动任务并开始移动，会立即被 Flow B 的持续监控捕获并拦停；因此 Flow A、Flow B 各自成立、不依赖对方，但两者组合在一起才能覆盖"开门全过程"的安全防护。

## 正常流程

### 4.0（Flow A：开门前核验）

1. 任意业务/维护流程需要对该 AGV 的某个仓位下发"开锁/开门"指令前，先调用本 UC 完成核验
   1.1 系统核验本次查询/通信是否正常（见 Exception Flow EA1.1）
2. 系统读取该 AGV 当前是否处于"移动中"状态
3. 系统依据第 2 步的判定结果分别处理：
   3.1 判定为"移动中"：核验不通过，系统拒绝本次开门请求，发起方不得下发开锁指令，本次核验到此结束
   3.2 判定为"未移动（静止）"：核验通过，系统放行，发起方可继续下发开锁指令、进入其自身后续流程（如 UC-001/UC-005/UC-010 的"打开仓位"步骤），本次核验到此结束

## 备选流程

### 4.1（Flow B：仓门开启期间的移动监控）

与 Normal Flow（Flow A）相比，本流程的触发条件、目标完全不同：Flow A 是"开门动作发生前"的一次性核验，本流程则是"仓门已经处于开启状态"之后的持续性监控，两者共同构成本 UC 完整的双向安全联锁，因此单独列为 Alternative Flow。

1. 系统检测到该 AGV 存在任一仓位仓门状态变为"开启"，开始持续轮询 RIOT 获取该 AGV 的移动状态
   1.1 系统核验本次轮询/通信是否正常（见 Exception Flow EB1.1）
2. 系统轮询到该 AGV 状态为"移动中"，且此时仍有仓门处于开启状态，判定触发安全联锁
3. 系统核验当前 RIOT 正在执行的移动任务是否为本系统下发（比对任务 ID 与本地下发记录）
   3.1 若 RIOT 未返回任务 ID，或本地查不到对应下发记录、无法判定任务来源，按"非本系统任务"处理（转第 4.2 步），不视为本步骤的核验失败
4. 系统依据第 3 步的判定结果分别处理：
   4.1 判定为本系统下发的任务：系统向 RIOT 下发"暂停"指令，暂停该移动任务（见 Exception Flow EB4.1）
   4.2 判定为非本系统下发（或无法判定来源）：系统向 RIOT 下发"取消"指令，终止该移动任务（见 Exception Flow EB4.2），本次安全联锁处理到此结束
5. （仅第 4.1 分支）系统持续监测该 AGV 所有仓位仓门状态，直至全部仓门恢复"关闭"
6. （仅第 4.1 分支）全部仓门关闭后，系统向 RIOT 下发"恢复"指令，该 AGV 继续原任务移动（见 Exception Flow EB6.1）

## 异常流程

以下每条异常均以 `E<Flow前缀><步骤号>` 编号，`EA` 表示 Flow A（4.0）触发，`EB` 表示 Flow B（4.1）触发，因两条 Flow 内部的步骤号均从 1 开始各自独立编号，用前缀区分避免混淆：

* EA1.1 Flow A：查询/通信异常，无法确定该 AGV 当前移动状态
* EB1.1 Flow B：轮询/通信异常导致未能及时检测到移动状态变化
* EB4.1 Flow B：暂停指令下发失败或 AGV 未能及时停止（本系统任务分支）
* EB4.2 Flow B：取消指令下发失败或 AGV 未能及时停止（非本系统任务分支）
* EB6.1 Flow B：恢复指令下发失败，仓门关闭后 AGV 未能重新移动

### EA1.1 Flow A：查询/通信异常，无法确定该 AGV 当前移动状态

1. 发起方 UC 按第 1 步请求核验该 AGV 当前移动状态
2. 系统按第 1.1 步核验本次查询，发现本地服务器与 RIOT 之间通信异常，或 RIOT 返回状态无法明确判定"移动"还是"静止"
3. 系统按 fail-closed 原则，将本次核验结果一律判定为"拒绝开门"，不允许发起方下发开锁指令，即使该 AGV 实际上可能是静止的（与 [[br-002-agv-allocation-eligibility|BR-002]] 中"仓门/移动安全联锁状态未知时必须 fail-closed、不得使用默认正常值"的处理原则一致）
4. 系统提示通信异常告警（如现场提示、上报 IT/软件维护人员 R-12 或 AGV 运维/调度管理员 R-13）
5. 通信恢复后，发起方可重新发起开门请求，重新触发 Flow A 核验；TBD 待定：是否需要限制重试频率/次数，待补充

### EB1.1 Flow B：轮询/通信异常导致未能及时检测到移动状态变化

1. 该 AGV 存在仓位仓门开启，系统按第 1 步开始轮询 RIOT
2. 系统按第 1.1 步核验本次轮询，发现本地服务器与 RIOT 之间通信异常，未能在预期周期内获取到该 AGV 的最新移动状态
3. 系统提示通信异常告警（如现场提示、上报 IT/软件维护人员 R-12 或 AGV 运维/调度管理员 R-13），并持续尝试重新建立轮询
4. TBD 待定：通信恢复前是否需要触发更保守的兜底动作（如提示现场人员当前无法实时监控该 AGV 移动状态，需人工留意），待补充

### EB4.1 Flow B：暂停指令下发失败或 AGV 未能及时停止（本系统任务分支）

1. 系统按第 4.1 步向 RIOT 下发"暂停"指令
2. 系统核验该指令是否被 RIOT 正常接收且 AGV 已实际停止，发现指令下发失败，或指令已下发但 AGV 未在预期时间内停止
3. 系统触发紧急告警（如现场声光提示、上报班组长 R-09 或 AGV 运维/调度管理员 R-13），提示人员该 AGV 可能仍在移动
4. TBD 待定：是否需要进一步下发更高优先级的紧急停止指令，或采取其他兜底措施，待补充

### EB4.2 Flow B：取消指令下发失败或 AGV 未能及时停止（非本系统任务分支）

1. 系统按第 4.2 步向 RIOT 下发"取消"指令
2. 系统核验该指令是否被 RIOT 正常接收且 AGV 已实际停止，发现指令下发失败，或指令已下发但 AGV 未在预期时间内停止
3. 系统触发紧急告警（如现场声光提示、上报班组长 R-09 或 AGV 运维/调度管理员 R-13），提示人员该 AGV 可能仍在移动，且该任务并非本系统下发，可能需要联系任务原下发方共同处理
4. TBD 待定：是否需要进一步下发更高优先级的紧急停止指令，或采取其他兜底措施，待补充

### EB6.1 Flow B：恢复指令下发失败，仓门关闭后 AGV 未能重新移动

1. 系统按第 6 步（全部仓门已关闭）向 RIOT 下发"恢复"指令
2. 系统核验该指令是否被 RIOT 正常接收且 AGV 已恢复移动，发现指令下发失败，或指令已下发但 AGV 长时间未恢复移动
3. 系统提示该 AGV 恢复移动异常，上报 AGV 运维/调度管理员（R-13）介入处理
4. AGV 运维/调度管理员排查处理后（如重新下发恢复指令，必要时重新规划任务），确认该 AGV 恢复正常移动

## 备注

* 本 UC 最初（2026-07-09）从 UC-001「放入完工产品」拆分而来，当时只覆盖"仓门开启后，持续监控 AGV 移动、检测到移动即拦停"这一反应式逻辑（即本次改版后的 Flow B）。2026-07-13 与用户澄清后确认：本 UC 描述的是跨越 AGV 全生命周期、不局限于任一具体站点业务场景的通用安全能力，不应归类为"站点操作"，因此本次改版：
  1. 将文档从 `01-site-operations` 迁移到新建的 `07-safety-and-interlock` 目录。
  2. 新增 Flow A（开门前核验：只要 AGV 在移动，就拒绝开门），与原有 Flow B（开启期间监控）组成双向联锁，标题相应由"仓门开启安全联锁"调整为"仓门安全联锁"。
* 与 [[br-002-agv-allocation-eligibility|BR-002]] 的关系：BR-002 第 5/6 条要求"所有仓门关闭、光幕/门锁/安全联锁状态正常"才允许该 AGV 进入新任务分配候选集合，这是"派发新任务前"更早期、AGV 维度的检查点，发生在该 AGV 尚无当前移动任务时；本 UC 的 Flow A（开门前）与 Flow B（门已开期间）则是更细粒度、"门-移动"这一对状态本身的检查，覆盖该 AGV 已有任务、正在跟车运行的场景。两者检查时机不同、互不重复，共同构成覆盖 AGV 全生命周期的门-移动互斥安全网。
* 待与用户确认（TBD）：Flow A 判定"拒绝开门"后，发起方 UC（如 UC-001/UC-005/UC-010）应如何向操作员呈现该结果——是复用其自身已有的"仓门开锁失败"异常流程（如各自的 E2.1），还是需要新增一条专属提示（如"AGV 当前正在移动，请稍候重试"）；需要与这些业务 UC 逐一确认后回填其 Exception Flow，目前这些 UC 尚未显式引用 Flow A 的核验步骤，见下方「关联用例」。
* 经与用户确认（沿用自 2026-07-09 的既有决策）：Flow B 拦停之后具体如何处理，按"任务来源"分为两条路径——本系统下发的任务采用"暂停 → 等全部仓门关闭 → 恢复"，尽量保留原任务上下文、减少 AGV 重新排队/重新规划路径的成本；非本系统下发的任务（或无法判定来源时，按此路径兜底处理）直接"取消"彻底终止，不负责代其恢复，避免在任务上下文不完整的情况下让 AGV 重新移动带来二次风险。
* 经与用户确认（沿用自 2026-07-09 的既有决策）：RIOT 已确认提供暂停(pause)/恢复(resume) 接口（暂停后可原地恢复、不丢失原路径），且 RIOT 返回的 AGV 状态中带有可判定任务来源的字段（如任务 ID），这两点是 Flow B 能够采用"暂停+恢复"而不是"一律取消重下发"方案的技术前提，已列入 Precondition；若后续实际对接时发现与预期不符（如某些异常状态下恢复接口不可用），需要回来调整本 UC 的 Flow B。
* 经与用户确认（沿用自 2026-07-09 的既有决策）：本 UC 目前没有仓门与 AGV 底盘运动之间的硬件机械/电子互锁，本 UC 描述的查询/轮询检测机制是当前唯一的安全保障手段，因此对查询/轮询周期、指令下发及时性的要求较高（具体量级待补充）；相关风险窗口（如 Flow A 核验通过与实际开锁之间的极短延迟）已在 Assumption 中说明，不作为本 UC 的 Exception Flow 处理，因为本 UC 无法从软件层面消除该延迟本身。
