# UC-015 仓门开锁开启测试

## 描述

维护人员通过独立于业务流程的维护界面，选择目标仓位，下发开锁（DO）指令，现场观察该仓位仓门是否能够正常弹开/开启；测试完成后由维护人员手动关闭仓门。本操作不经过 [[uc-001-load-completed-lot-into-slot|UC-001]]、[[uc-005-retrieve-mis-stored-product-from-slot|UC-005]]、[[uc-010-unload-completed-lot-at-destination-station|UC-010]] 等业务流程的核验逻辑（如光幕核验、任务归属核验），只单纯验证"开锁指令 → 仓门实际弹开/开启"这一机械/电子锁环节是否正常工作。

> 本 UC 同时落地 [[uc-014-enable-disable-slot|UC-014]] Assumption 第 3 条中遗留的"维护人员可通过自己的界面打开和关闭仓门"这一能力：该能力的具体实现即本 UC 描述的维护界面手动开关门操作，不受 UC-014 维护的禁用状态限制。

## 触发条件

维护人员因设备安装调试、定期巡检或故障复测，需要验证某仓位的开锁/开门机械功能。

## 前置条件

**系统与接口**

1. 本地服务器与 IO 模块之间通信正常，可正常下发开锁（DO）指令并读取反馈。The local server and the IO module communicate normally, so an unlock (DO)

**任务与数据**

2. 建议测试前先通过 [[uc-014-enable-disable-slot|UC-014]] 将目标仓位标记为"已禁用"，避免测试期间该仓位被业务流程意外分配使用；测试完成且确认正常后，再通过 UC-014 重新启用（非强制，见 Assumption）。

**人员与权限**

3. 维护人员具备通过维护界面对仓位下发开锁指令的操作权限（具体角色待定，见 Notes）。

## 后置条件

**设备与硬件**

1. 若测试正常：目标仓位仓门在下发开锁指令后正常弹开/开启，维护人员手动关闭后，仓门恢复关闭、电子锁恢复锁闭状态。
2. 若测试异常：目标仓位被标记为"异常锁定"或"测试未通过"，暂停对该仓位的后续业务分配，等待维护人员进一步排查（见 Exception Flow E2.1）。

**任务与数据**

3. 本次测试结果（维护人员、仓位号、测试类型：开锁开启测试、结果：正常/异常、时间戳）被记录到本地数据库，用于追溯。This test result (engineer, slot number, test type: unlock/open test, result: pass/fail, timestamp)

## 假设

1. 本 UC 的手动开关门操作是否要求目标仓位提前处于"已禁用"状态，本次不作为强制 Precondition，仅作为建议做法；若维护人员在未禁用的仓位上直接测试，本 UC 本身不拦截，但可能与业务流程产生资源竞争（如测试期间该仓位恰好被 UC-001 分配），该风险由维护人员自行把控，不在本 UC 的 Exception Flow 中处理。
2. 维护人员在测试过程中会正确判断仓门是否"正常弹开/开启"，系统本身不具备独立于人工判断的自动化机械动作检测手段（如是否存在传感器直接验证门体物理位移），本 UC 依赖维护人员的现场目视判断作为测试结果依据。

## 正常流程

### 15.0

1. 维护人员在维护界面中选择目标仓位
2. 维护人员点击"开锁测试"按钮，系统向该仓位下发开锁（DO）指令
   2.1 系统核验该开锁指令是否被 IO 模块正常接收（见 Exception Flow E2.1）
3. 维护人员现场观察该仓位仓门是否正常弹开/开启
   3.1 维护人员判定仓门是否确实正常弹开/开启（见 Exception Flow E3.1）
4. 维护人员手动关闭该仓位仓门
5. 系统记录本次测试结果（维护人员、仓位号、结果：正常/异常、时间戳）

## 备选流程

不存在需要区分的备选流程：无论维护人员是逐个测试单个仓位，还是在同一次巡检中依次测试多个仓位，均按 Normal Flow 相同的步骤逐一执行，不构成触发方式或步骤不同的分支路径。

## 异常流程

以下每条异常均以 `E<步骤号>` 编号，与 Normal Flow 中触发该异常的具体步骤一一对应：

* E2.1 开锁指令下发失败（通信异常/IO 模块未正常接收）
* E3.1 仓门未能正常弹开/开启

### E2.1 开锁指令下发失败

1. 系统按第 2 步向目标仓位下发开锁指令
2. 系统按第 2.1 步核验，发现该指令未能被 IO 模块正常接收（如通信超时、IO 模块无响应）
3. 系统提示该仓位开锁指令下发异常，测试判定为"异常"，记录本次测试结果
4. 维护人员排查本地服务器与 IO 模块之间的通信链路（如网络连接、IO 模块自身状态），修复后重新发起测试

### E3.1 仓门未能正常弹开/开启

1. 系统已正常下发开锁指令（第 2 步核验通过）
2. 维护人员按第 3.1 步现场核验，发现该仓位仓门未能正常弹开/开启（如卡滞、无反应）
3. 维护人员判定该仓位硬件异常（电子锁/机械故障），系统将该仓位标记为"异常锁定"或"测试未通过"，暂停对该仓位的业务分配
4. 维护人员排查并修复电子锁/机械故障（必要时联系设备供应商）后，重新发起本测试，直至测试通过
5. 测试通过后，维护人员通过 [[uc-014-enable-disable-slot|UC-014]] 将该仓位恢复"启用"，重新可被业务流程分配使用

## 备注

* 本 UC 是用户提出的新场景："测试仓位的门是否工作正常，测试仓门是否能弹开"，并同时用于落地 [[uc-014-enable-disable-slot|UC-014]] 中遗留的"维护人员可通过自己界面开关仓门"能力（原 UC-014 Assumption 第 3 条、Notes 待补充事项第 2 条）。
* 维护角色本次不做最终确定，先留 TBD，推测候选为 [[stakeholders-and-user-classes|干系人清单]] 中的 R-11 设备/电气维护人员（职责描述为"IO 模块、电子锁、光幕等硬件维护"，与本 UC 的测试内容高度吻合），但用户尚未最终确认，与 [[uc-014-enable-disable-slot|UC-014]] 的操作角色是否为同一人也待定。
* 本 UC 与 [[uc-016-slot-light-curtain-function-test|UC-016]]、[[uc-017-slot-door-state-detection-test|UC-017]] 的关系：后两者的测试流程均需要先执行本 UC 描述的手动开/关门动作作为前提，三者可在同一次维护巡检中连续进行，但因验证的硬件环节不同（本 UC 验证"开锁指令→门体机械动作"，UC-016 验证光幕传感器，UC-017 验证门状态反馈信号），故分别独立成文。
