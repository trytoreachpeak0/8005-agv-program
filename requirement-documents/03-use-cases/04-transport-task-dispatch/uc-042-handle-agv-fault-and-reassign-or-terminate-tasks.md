# UC-042 处理AGV途中故障并改派或终止关联任务

## 描述

AGV 运维/调度管理员在某台正在执行搬运任务的多仓位 AGV 发生故障、长时间离线或被 RIOT 判定无法继续移动时介入处理：先核验该 AGV 当前绑定的业务任务及各自的装货状态，再根据"任务是否已经开始装货（第一个仓门是否已打开）"分别决定后续处理方式——尚未开始装货的任务可改派给其他可用 AGV 重新进入派车候选；已经开始装货但尚未送达的任务，因产品实体仍在故障车上，不能简单改派，需要人工到现场处理（等待修复继续送货，或人工取出产品后终止原任务）。

> 本 UC 填补的是"AGV 已经装货在途、中途报障或通信中断，车上任务如何安全收尾"这一此前没有任何 UC 覆盖的缺口：[[uc-006-cancel-transport-task-upon-arrival|UC-006]] 只覆盖"到站后、装货前"取消任务；[[uc-028-handle-workflow-step-exception|UC-028]] 只覆盖流程模板"步骤"层面的通用异常处置（重试/等待人工/安全终止），不覆盖业务任务层面"车辆本身不可用、车上多个任务如何统一处理"的决策；本 UC 专门覆盖后者。

## 触发条件

出现以下任一情况：

1. RIOT 报告该 AGV 故障、离线、导航失败，且超过预设超时仍未恢复（具体超时阈值 TBD）。
2. AGV 运维/调度管理员通过现场巡检或其他渠道发现车辆故障，主动介入标记该车不可用，不等待系统自动判定。

## 前置条件

**系统与接口**

1. RIOT 接口在线可用（若 RIOT 本身也不可达，处理方式见 Exception Flow）。

**任务与数据**

2. 该 AGV 当前绑定至少一个尚未完成（未到达"已完成"或"已取消"终态）的业务任务。

**人员与权限**

3. AGV 运维/调度管理员具备处理 AGV 故障、改派或终止关联任务的操作权限；该操作视为高风险操作，是否需要二次认证 TBD（参照 [[uc-038-maintain-agv-slot-model|UC-038]]、[[uc-024-maintain-area-station-mapping|UC-024]] 等其他高风险配置变更的二次认证做法）。

## 后置条件

**系统与接口**

1. 该 AGV 被标记为"故障/不可用"状态（具体是否复用 [[uc-013-enable-disable-agv|UC-013]] 的"已禁用"状态，还是新增独立的故障状态，TBD 见 Notes），不再被 [[uc-008-dispatch-move-order-to-riot|UC-008]]、[[uc-012-manually-dispatch-agv-to-charge|UC-012]]、[[uc-041-return-idle-agv-to-parking-point|UC-041]] 自动派发新任务。

**任务与数据**

2. 该 AGV 名下尚未开始装货的任务，状态回退为可重新分配（如"新建 New"），重新进入 [[br-001-dispatch-task-range|BR-001]]/[[uc-008-dispatch-move-order-to-riot|UC-008]] 的正常派车候选范围，可被改派给其他可用 AGV。
3. 该 AGV 名下已开始装货但未送达的任务，按管理员选择的处理方式（见 Alternative Flow）分别进入"等待修复继续执行"或"终止并转人工处理"状态；终止时，已装载但未取出的产品的后续去向由现场人工流程处理，具体是否需要新建独立的"人工完成运输"记录机制，TBD。
4. 本次故障处理全过程（故障发现时间、涉及任务清单及各自装货状态、处理决定、操作人、时间戳）被记录到本地数据库，用于追溯。

## 假设

1. 本 UC 假定"该任务是否已经开始装货"可以通过第一个仓门是否已打开这一既有判定标准（与 `mes/AGV系统业务与MES任务模型.md` 第 6.1 节"开始装货以该任务第一个仓门成功打开为边界"一致）准确获知，不在本 UC 中重新定义该边界。
2. 本 UC 不负责判定"AGV 是否确实发生了故障"这一技术判断本身（如具体的故障检测算法、超时阈值），只负责"判定结果已确认后，如何处理该车绑定的业务任务"；故障检测本身依赖 RIOT 上报或人工现场发现。

## 正常流程

### 42.0

1. AGV 运维/调度管理员发现或收到某台 AGV 故障/长时间离线的提示，进入故障处理界面
2. 系统展示该 AGV 当前绑定的全部未完成任务及各自的装货状态（未装货/部分装货中/已完成装货运输中）
3. 管理员将该 AGV 标记为"故障/不可用"
   3.1 系统核验该 AGV 当前是否确有未完成任务（若没有，直接标记故障即可，不涉及后续任务处理步骤）
4. 针对列表中尚未开始装货的任务，管理员确认改派：系统将这些任务状态回退为可重新分配，退回 [[br-001-dispatch-task-range|BR-001]] 候选范围
5. 针对列表中已开始装货但未送达的任务，管理员逐一选择处理方式（见 Alternative Flow A5.1/A5.2）
6. 系统记录本次故障处理全过程（故障发现时间、任务清单、处理决定、操作人、时间戳）

## 备选流程

### A5.1 等待修复后继续执行原任务

1. 管理员判断该 AGV 可以在合理时间内修复（如临时通信故障、可现场排除的机械卡滞）
2. 管理员选择"等待修复"，该任务保持"进行中"状态，暂不改派、不终止
3. 车辆修复后，管理员通过 [[uc-013-enable-disable-agv|UC-013]] 或本 UC 提供的"恢复"操作，将该车重新标记为可用，该任务按原计划继续执行（继续行驶至目标站点）
4. 若等待超过预设时长仍未修复（具体阈值 TBD），系统提示管理员重新评估，转 A5.2

### A5.2 人工取出已装产品并终止原任务

1. 管理员判断该 AGV 无法在合理时间内修复，或产品需要尽快送达无法继续等待
2. 管理员安排生产操作员或维护人员到故障车现场，通过维护手段（如 [[uc-015-slot-door-unlock-open-test|UC-015]] 提供的维护界面开锁能力，或专门的故障应急开锁流程，TBD）打开相关仓位取出已装载产品
3. 管理员在系统中终止该任务，系统记录终止原因（车辆故障）
4. 取出的产品后续如何送达目标站点（如改由人工搬运、或重新扫码创建新任务由其他 AGV 运送），TBD 待补充，本 UC 不展开具体的后续送达机制，只负责原任务的安全终止和记录

## 异常流程

以下每条异常均以 `E<步骤号>` 编号，与 Normal Flow 中触发该异常的具体步骤（或子步骤）一一对应：

* E1.1 RIOT 接口本身不可达，无法确认该 AGV 真实状态
* E4.1 改派后的候选 AGV 范围为空，暂无可承接的车辆

### E1.1 RIOT 接口本身不可达

1. 管理员尝试处理疑似故障 AGV，但系统按 Precondition 第1条核验，发现本地服务器与 RIOT 之间通信本身异常
2. 系统提示"无法确认该 AGV 当前真实状态"，允许管理员基于现场人工判断强制标记该车故障（fail-closed 情形下允许人工override，具体是否需要额外二次确认，TBD）
3. IT/软件维护人员（R-12）排查并修复 RIOT 接口/网络异常后，系统重新与 RIOT 对齐该 AGV 实际状态

### E4.1 改派候选范围为空

1. 系统按第4步尝试将未装货任务退回候选范围，发现当前没有其他可用 AGV 可承接（全部忙碌/故障/禁用）
2. 系统将这些任务保持"新建"状态但触发告警，提示当前运力不足
3. 待有 AGV 恢复空闲后，[[uc-008-dispatch-move-order-to-riot|UC-008]] 按正常逻辑重新拾取这些任务下发

## 备注

* 本 UC 是为填补需求缺口而新增：现有 UC 集合中，[[uc-006-cancel-transport-task-upon-arrival|UC-006]] 只覆盖"到站后、装货前"取消场景，其 Notes 自己也留有 TBD——"取消后是否需要联动向 RIOT 下发取消指令……留待后续与 UC-008 协调确认"；[[uc-028-handle-workflow-step-exception|UC-028]] 只覆盖流程模板步骤层面的通用异常处置。"AGV 已装货在途、中途故障"这一业务场景此前完全没有 UC 覆盖，本 UC 用于补齐。
* 待补充（TBD）事项，且数量较多，属于需要与用户进一步确认的核心业务决策，本 UC 当前只是初稿骨架：
  1. AGV"故障/不可用"状态是否复用 [[uc-013-enable-disable-agv|UC-013]] 的"已禁用"状态机，还是需要新增独立的"故障"状态（例如区别于主动禁用，故障状态可能需要不同的恢复流程和告警级别）。
  2. 故障判定的具体触发条件、超时阈值，是否需要系统自动判定还是必须人工确认才能进入本 UC 流程。
  3. 已装货未送达任务终止后，取出的产品如何继续完成运输（人工搬运到底、还是重新创建任务由其他 AGV 接力），本 UC 未展开，需要与用户确认具体机制，可能需要另建 UC。
  4. 故障应急开锁（Alternative Flow A5.2 第2步）是否复用现有维护界面能力（如 [[uc-015-slot-door-unlock-open-test|UC-015]]），还是需要专门的应急开锁流程和权限控制；应急开锁是否需要绕过 [[uc-004-slot-door-safety-interlock|UC-004]] 的移动安全联锁前提（车辆已经不再移动的情况下，联锁核验的具体处理方式）。
  5. 本操作是否需要二次认证、是否需要班组长或更高权限审批，参照其他高风险操作的既有做法确认。
  6. 等待修复的最长时长阈值，超过后是否强制转入终止流程还是仅提示管理员。

## 关联用例

* [[uc-006-cancel-transport-task-upon-arrival|UC-006]]：该 UC 覆盖"到站后、装货前"的取消场景，本 UC 覆盖"已装货在途"场景，两者按装货边界分工，互不重叠；本 UC 的改派流程（Normal Flow 第4步）与该 UC 的取消流程作用类似但触发原因不同（车辆故障 vs 产品不再需要运送）。
* [[uc-008-dispatch-move-order-to-riot|UC-008]]：本 UC 改派的任务退回候选范围后，由该 UC 按正常逻辑重新下发给其他可用 AGV。
* [[uc-013-enable-disable-agv|UC-013]]：本 UC 标记 AGV"故障/不可用"的具体状态机是否复用该 UC 的禁用状态，TBD；该 UC 已有的禁用状态确保被标记车辆不会被 UC-008/UC-012/UC-041 派发新任务，本 UC 的故障标记需要达到同等效果。
* [[uc-028-handle-workflow-step-exception|UC-028]]：该 UC 处理流程模板"步骤"层面的异常（如某次下发/移动步骤失败后的重试/等待人工/安全终止），本 UC 处理的是业务任务层面"车辆本身不可用"的更高层决策，两者可能同时触发（如某次移动步骤失败触发 UC-028 的步骤级处置，同时该车被判定故障触发本 UC 的任务级处置），具体协作关系 TBD。
* [[uc-005-retrieve-mis-stored-product-from-slot|UC-005]]：本 UC Alternative Flow A5.2 中"人工取出已装载产品"的具体操作，是否复用该 UC 的取出流程，TBD。
