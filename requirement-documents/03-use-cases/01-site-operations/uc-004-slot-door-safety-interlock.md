# UC-004 仓门开启安全联锁

## 描述

只要多仓位 AGV 存在任一仓位仓门处于开启状态，本地服务器就持续轮询 RIOT，读取该 AGV 是否处于移动状态；一旦检测到移动（包括意外移动），系统会先核验当前 RIOT 正在执行的移动任务是否为本系统下发：若确认是本系统下发的任务，则下发"暂停"指令让 AGV 停止，待全部仓门关闭后再下发"恢复"指令使其继续原任务移动；若确认不是本系统下发（或无法判定来源），则直接下发"取消"指令彻底终止该任务，不负责后续恢复。本 UC 是跨场景的通用安全联锁逻辑，适用于所有涉及开仓门的业务 UC（如 [[uc-001-load-completed-lot-into-slot|UC-001]] 放入完工产品、[[uc-005-retrieve-mis-stored-product-from-slot|UC-005]] 取出存错产品等），不属于某一个具体业务 UC 的 Precondition。

> 判断"是否需要拦停 AGV 移动"的标准只取决于"仓门是否开启 + AGV 是否在移动"这一物理事实，与任务来源无关；任务来源只决定拦停之后采用哪种处理方式（暂停待恢复 / 直接取消），因为对于非本系统下发的任务，本系统不掌握其完整上下文，无法安全地代其恢复。

## 触发条件

该 AGV 任一仓位仓门状态变为"开启"时，系统开始持续轮询 RIOT 获取该 AGV 的移动状态；轮询期间检测到该 AGV 处于"移动中"且仍有仓门开启，即触发本 UC 的拦停处理。

## 前置条件

**系统与接口**

1. 本地服务器与 RIOT 之间通信正常，可正常轮询获取该 AGV 的移动状态（见 Exception Flow E1.1）。
2. RIOT 返回的 AGV 状态中包含可用于判定"当前执行的移动任务是否为本系统下发"的字段（如任务 ID），本地服务器可据此与自身的任务下发记录进行比对（已与 RIOT 确认支持）。
3. RIOT 提供"暂停（pause）"与"恢复（resume）"接口，且本系统下发的移动任务被暂停后可原地恢复、继续原路径/目标点，不丢失任务上下文（已与 RIOT 确认支持）。

## 后置条件

**设备与硬件**

1. 若触发拦停时执行的是本系统下发的任务：该移动任务被暂停，AGV 停止移动；待该 AGV 全部仓位仓门恢复"关闭"后，该任务被恢复，AGV 继续原任务移动。
2. 若触发拦停时执行的是非本系统下发的任务（或无法判定来源）：该移动任务被取消终止，AGV 停止移动，本系统不负责后续恢复该任务。

**任务与数据**

3. 本次安全联锁事件（触发时间、涉及仓门、任务来源判定结果、采取的处理方式：暂停待恢复 / 取消）被记录到本地数据库，用于追溯。

## 假设

1. 本 UC 是纯软件层的安全机制：基于持续轮询 RIOT 状态判断并下发暂停/取消/恢复指令，不涉及仓位仓门与 AGV 底盘运动之间的机械/电子硬件互锁；轮询周期与指令下发的及时性直接决定本机制的实际防护效果。若业务上需要更高等级的安全保障（如物理层面直接禁止移动），需由其他硬件方案另行覆盖，不在本 UC 范围内。
2. 只要 AGV 已停止移动（无论是暂停还是取消），仓门开启期间的人员/产品安全风险即视为已消除；本 UC 不进一步核验"停止"这一动作本身是否会带来其他次生风险（如急停对车上产品/设备造成的冲击）。

## 正常流程

### 4.0

1. 系统检测到该 AGV 存在任一仓位仓门状态变为"开启"，开始持续轮询 RIOT 获取该 AGV 的移动状态
   1.1 系统核验本次轮询/通信是否正常（见 Exception Flow E1.1）
2. 系统轮询到该 AGV 状态为"移动中"，且此时仍有仓门处于开启状态，判定触发安全联锁
3. 系统核验当前 RIOT 正在执行的移动任务是否为本系统下发（比对任务 ID 与本地下发记录）
   3.1 若 RIOT 未返回任务 ID，或本地查不到对应下发记录、无法判定任务来源，按"非本系统任务"处理（转第 4.2 步），不视为本步骤的核验失败
4. 系统依据第 3 步的判定结果分别处理：
   4.1 判定为本系统下发的任务：系统向 RIOT 下发"暂停"指令，暂停该移动任务（见 Exception Flow E4.1）
   4.2 判定为非本系统下发（或无法判定来源）：系统向 RIOT 下发"取消"指令，终止该移动任务（见 Exception Flow E4.2），本次安全联锁处理到此结束
5. （仅第 4.1 分支）系统持续监测该 AGV 所有仓位仓门状态，直至全部仓门恢复"关闭"
6. （仅第 4.1 分支）全部仓门关闭后，系统向 RIOT 下发"恢复"指令，该 AGV 继续原任务移动（见 Exception Flow E6.1）

## 备选流程

不存在需要区分的备选流程：本 UC 中"暂停待恢复"与"直接取消"两条处理路径，已在 Normal Flow 第 4 步中通过任务来源判定完整覆盖，两条路径共享相同的检测与判定步骤（第 1~3 步），不需要也不应拆分为独立的 Alternative Flow。

## 异常流程

以下每条异常均以 `E<步骤号>` 编号，与 Normal Flow 中触发该异常的具体步骤（或子步骤）一一对应：

* E1.1 轮询/通信异常导致未能及时检测到移动状态变化
* E4.1 暂停指令下发失败或 AGV 未能及时停止（本系统任务分支）
* E4.2 取消指令下发失败或 AGV 未能及时停止（非本系统任务分支）
* E6.1 恢复指令下发失败，仓门关闭后 AGV 未能重新移动

### E1.1 轮询/通信异常导致未能及时检测到移动状态变化

1. 该 AGV 存在仓位仓门开启，系统按第 1 步开始轮询 RIOT
2. 系统按第 1.1 步核验本次轮询，发现本地服务器与 RIOT 之间通信异常，未能在预期周期内获取到该 AGV 的最新移动状态
3. 系统提示通信异常告警（如现场提示、上报 IT/软件维护人员 R-12 或 AGV 运维/调度管理员 R-13），并持续尝试重新建立轮询
4. TBD 待定：通信恢复前是否需要触发更保守的兜底动作（如提示现场人员当前无法实时监控该 AGV 移动状态，需人工留意），待补充

### E4.1 暂停指令下发失败或 AGV 未能及时停止（本系统任务分支）

1. 系统按第 4.1 步向 RIOT 下发"暂停"指令
2. 系统核验该指令是否被 RIOT 正常接收且 AGV 已实际停止，发现指令下发失败，或指令已下发但 AGV 未在预期时间内停止
3. 系统触发紧急告警（如现场声光提示、上报班组长 R-09 或 AGV 运维/调度管理员 R-13），提示人员该 AGV 可能仍在移动
4. TBD 待定：是否需要进一步下发更高优先级的紧急停止指令，或采取其他兜底措施，待补充

### E4.2 取消指令下发失败或 AGV 未能及时停止（非本系统任务分支）

1. 系统按第 4.2 步向 RIOT 下发"取消"指令
2. 系统核验该指令是否被 RIOT 正常接收且 AGV 已实际停止，发现指令下发失败，或指令已下发但 AGV 未在预期时间内停止
3. 系统触发紧急告警（如现场声光提示、上报班组长 R-09 或 AGV 运维/调度管理员 R-13），提示人员该 AGV 可能仍在移动，且该任务并非本系统下发，可能需要联系任务原下发方共同处理
4. TBD 待定：是否需要进一步下发更高优先级的紧急停止指令，或采取其他兜底措施，待补充

### E6.1 恢复指令下发失败，仓门关闭后 AGV 未能重新移动

1. 系统按第 6 步（全部仓门已关闭）向 RIOT 下发"恢复"指令
2. 系统核验该指令是否被 RIOT 正常接收且 AGV 已恢复移动，发现指令下发失败，或指令已下发但 AGV 长时间未恢复移动
3. 系统提示该 AGV 恢复移动异常，上报 AGV 运维/调度管理员（R-13）介入处理
4. AGV 运维/调度管理员排查处理后（如重新下发恢复指令，必要时重新规划任务），确认该 AGV 恢复正常移动

## 备注

* 本 UC 从 UC-001「放入完工产品」拆分而来：原本作为 UC-001 的 Precondition 候选项"AGV 当前无正在执行的移动指令"，因其适用于所有开仓门场景，独立为本 UC。
* 硬件相关的电子锁/光幕检查（判断某个具体仓位是否可以开锁）不在本 UC 范围内，那是各业务 UC 在"打开仓位"步骤中的系统检查项，与本 UC 关注的"移动安全"是两个不同维度。
* 经与用户确认：拦停之后具体如何处理，按"任务来源"分为两条路径——本系统下发的任务采用"暂停 → 等全部仓门关闭 → 恢复"，尽量保留原任务上下文、减少 AGV 重新排队/重新规划路径的成本；非本系统下发的任务（或无法判定来源时，按此路径兜底处理）直接"取消"彻底终止，不负责代其恢复，避免在任务上下文不完整的情况下让 AGV 重新移动带来二次风险。
* 经与用户确认：RIOT 已确认提供暂停(pause)/恢复(resume) 接口（暂停后可原地恢复、不丢失原路径），且 RIOT 返回的 AGV 状态中带有可判定任务来源的字段（如任务 ID），这两点是本 UC 能够采用"暂停+恢复"而不是"一律取消重下发"方案的技术前提，已列入 Precondition；若后续实际对接时发现与预期不符（如某些异常状态下恢复接口不可用），需要回来调整本 UC 的 Normal Flow。
* 经与用户确认：本 UC 目前没有仓门与 AGV 底盘运动之间的硬件机械/电子互锁，本 UC 描述的轮询检测机制是当前唯一的安全保障手段，因此对轮询周期、指令下发及时性的要求较高（具体量级待补充），相关风险窗口（仓门刚开、AGV 已启动移动但服务器尚未来得及拦停的短暂延迟）已在 Assumption 中说明，不作为本 UC 的 Exception Flow 处理，因为本 UC 无法从软件层面消除该延迟本身。
