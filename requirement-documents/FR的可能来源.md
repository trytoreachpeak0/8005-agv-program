那如果系统内部的FR应该从哪里提取出来

系统内部的 FR，通常不是直接从 Use Case 的“用户操作步骤”里提取，而是从 **业务流程背后的系统责任** 中推导出来。

核心思路是：

> 用户做了什么，只是表面流程；系统为了正确、持续、可靠地完成这个流程，内部还必须承担哪些行为？

## 一、从业务规则提取

业务规则经常会转化为系统内部判断、校验和阻断功能。

例如业务规则：

> 必须先退料，才能发料。

可以提取：

* FR：系统应记录当前业务流程是否已完成退料。
* FR：系统在发料前应检查退料完成状态。
* FR：退料未完成时，系统应禁止进入发料流程。
* FR：系统应向操作员显示禁止发料的原因。

再比如：

> 一个物料只能存放在一个柜格中。

可以提取：

* 系统应在物料入柜前检查该物料是否已绑定其他柜格。
* 系统应保证物料与柜格绑定关系的唯一性。
* 检测到重复绑定时，系统应阻止入柜操作。

所以业务规则是内部 FR 的重要来源。

---

## 二、从状态模型提取

只要业务对象有状态变化，就可以从状态机中提取大量内部 FR。

例如物料可能有：

```text
柜外
→ 待入柜
→ 已入柜
→ 待领用
→ 已领用
→ MES待同步
→ 同步成功
→ 同步失败
```

可以从状态转换提取：

* 系统应维护物料当前状态。
* 系统应根据业务操作更新物料状态。
* 系统应禁止不合法的状态转换。
* 系统应记录每次状态变化的时间和原因。
* MES 同步失败时，系统应将状态设置为“待重试”。
* 物料处于“待同步”状态时，系统应禁止再次操作。

因此，**状态图几乎是系统内部 FR 最重要的来源之一**。

---

## 三、从数据生命周期提取

针对每一种核心数据，都问：

* 数据从哪里产生？
* 如何验证？
* 保存在哪里？
* 什么时候更新？
* 如何查询？
* 什么时候失效或删除？
* 数据冲突怎么办？

例如柜格绑定数据：

```text
物料批次 → 分配柜格 → 写入绑定记录 → 开门
→ 关门确认 → MES同步 → 解除绑定
```

可以提取：

* 系统应保存物料批次与柜格的绑定关系。
* 系统应在打开柜门前创建临时绑定记录。
* 柜门未正常关闭时，系统不应确认正式入柜。
* 领用完成后，系统应解除物料与柜格的绑定。
* 系统应保存绑定关系的历史记录。
* 系统应检测数据库记录与实际柜格状态是否一致。

这类 FR 往往不是用户主动提出的，而是通过数据分析得到的。

---

## 四、从外部接口分析提取

系统只要依赖 MES、AGV、PLC、IO 模块、数据库等外部系统，就需要分析接口内部行为。

例如“系统将退料信息发送到 MES”只是一个粗略需求，进一步可以提取：

* 系统应按照 MES 接口要求组装请求参数。
* 系统应校验调用接口所需参数是否完整。
* 系统应记录 MES 请求参数和返回结果。
* 系统应解析 MES 返回值。
* MES 返回成功时，系统应更新同步状态。
* MES 返回失败时，系统应保存失败原因。
* 接口超时或断连时，系统应将请求放入待重试队列。
* 系统应避免同一业务记录被重复提交。
* 系统应在重试前判断原请求是否已经处理成功。

这里的超时时间、性能指标可能属于非功能需求，但“超时后怎么处理、是否重试、如何更新状态”通常属于 FR。

---

## 五、从异常流程和故障场景提取

可以针对每个正常步骤问一句：

> 这一步失败了，系统应该怎么办？

例如正常步骤是：

> 系统打开柜门。

异常分析：

* IO 模块断线怎么办？
* 开门指令没有响应怎么办？
* 门打开后用户没有放料怎么办？
* 用户把料放错柜格怎么办？
* 柜门一直没有关闭怎么办？
* 软件中途重启怎么办？

可以得到：

* 系统应检测柜门开启结果。
* 开门失败时，系统应取消当前柜格分配。
* 柜门超过规定时间未关闭时，系统应生成告警。
* 系统重启后，应恢复未完成的操作。
* 系统应允许维护人员人工解除异常任务。
* 系统应记录异常发生的步骤、设备和错误信息。

很多系统内部 FR，实际上都是通过异常分析发现的。

---

## 六、从定时任务和系统事件提取

Use Case 常以“用户发起”为起点，但系统内部还有很多由时间或事件触发的功能。

### 时间触发

* 系统应定期扫描待同步记录。
* 系统应定期检查柜门在线状态。
* 系统应定期清理过期临时数据。
* 系统应每日生成业务统计数据。

### 系统事件触发

* 数据库连接恢复后，系统应继续处理待同步记录。
* AGV 到达指定位置后，系统应更新任务状态。
* 柜门关闭信号发生时，系统应执行入柜确认。
* MES 返回处理结果后，系统应更新本地事务状态。

这类需求可以通过 **事件列表** 提取：

| 事件      | 系统响应      |
| ------- | --------- |
| 用户扫码    | 查询物料信息    |
| 柜门关闭    | 验证柜格并提交记录 |
| MES调用失败 | 保存待同步任务   |
| 定时器到期   | 重试同步      |
| 系统启动    | 恢复未完成事务   |

---

## 七、从角色、权限和审计要求提取

权限不仅是“谁能看到按钮”，还包含内部授权判断。

例如：

* 系统应验证当前用户是否有柜格维护权限。
* 普通操作员不得修改 IO 映射。
* 管理员修改柜格配置时，系统应记录修改前后的值。
* 系统应记录关键操作的操作员、时间、设备和结果。
* 未登录用户不得执行退料和发料操作。

这些通常来自：

* 角色权限矩阵
* 审计要求
* 公司管理制度
* 安全规范

---

## 八、从运维和管理场景提取

除了正常业务用户，还要分析管理员、维护人员和实施人员的需求。

例如你的系统可能需要：

* 配置柜格与 IO 点位映射。
* 禁用故障柜格。
* 手动重新同步 MES 数据。
* 查看设备连接状态。
* 查询失败任务。
* 人工解除卡住的流程。
* 导出运行日志。
* 修改设备参数。

这些最好单独建立管理类 Use Case，例如：

* UC：维护柜格配置
* UC：处理 MES 同步失败
* UC：查看设备运行状态
* UC：恢复异常业务
* UC：查询操作日志

系统内部功能不代表完全没有 Actor。很多时候 Actor 是管理员、维护人员，或者时间、设备、外部系统。

---

## 九、从一致性和完整性要求推导

一个业务操作可能涉及多个系统：

```text
本地数据库
柜门IO
MES
AGV
```

这时需要问：

> 如果其中一部分成功、一部分失败，系统怎么办？

可以推导出：

* 系统应记录业务事务的处理阶段。
* 系统应保证重复执行同一请求不会生成重复记录。
* 系统应在业务处理失败后执行补偿操作。
* 系统应检测本地记录与 MES 状态是否一致。
* 发现状态不一致时，系统应禁止继续操作并生成异常记录。
* 系统应支持对未完成事务进行恢复。

你之前考虑的 Transactional Outbox、待同步状态、指数退避，本质上都是从“一致性与故障恢复需求”推导出来的系统内部 FR。

---

## 十、注意区分 FR 和设计方案

这是最容易混淆的地方。

例如：

> 系统应在 MES 连接恢复后自动重新提交未同步业务。

这是 FR，因为它描述系统应具备的行为。

但：

> 系统应使用 RabbitMQ 实现重试队列。

这是设计或技术约束，不一定是 FR。

再例如：

> 系统应持久化保存未同步请求，程序重启后仍可继续处理。

这是 FR。

> 系统应建立 `mes_outbox` 表保存请求。

这是数据库设计。

可以使用这个判断方式：

> 它描述的是“系统必须做什么”，还是“开发人员准备怎么实现”？

* 做什么：需求
* 怎么实现：设计

## 推荐的提取方法

对每个 Use Case，不只拆用户交互，还做以下几轮分析：

```text
1. 主流程分析
   提取直接交互型 FR

2. 业务规则分析
   提取校验、限制、计算和判断型 FR

3. 状态分析
   提取状态维护和状态转换型 FR

4. 数据分析
   提取保存、更新、查询和一致性 FR

5. 接口分析
   提取调用、响应处理、失败处理和重试 FR

6. 异常分析
   提取恢复、补偿、告警和人工处理 FR

7. 运行分析
   提取定时任务、后台任务、启动恢复 FR

8. 管理分析
   提取配置、日志、权限和维护 FR
```

以你的焊线柜“退料”为例：

### Use Case 直接产生的 FR

* 操作员可以扫描物料。
* 系统查询物料信息。
* 操作员填写退料数量。
* 系统分配柜格。
* 系统打开柜门。

### 业务规则产生的内部 FR

* 系统应校验物料是否允许退还。
* 系统应校验剩余数量是否合法。
* 系统应排除故障和已占用柜格。
* 系统应防止物料重复入柜。

### 状态和数据分析产生的内部 FR

* 系统应维护柜格占用状态。
* 系统应保存物料与柜格的绑定关系。
* 系统应记录退料事务的当前处理阶段。
* 柜门关闭前不得将退料标记为完成。

### 接口与异常分析产生的内部 FR

* 系统应将退料结果同步到 MES。
* MES 同步失败时应保存待同步记录。
* 后台任务应重新处理待同步记录。
* 超过最大重试次数后应生成告警。
* 软件重启后应恢复未完成事务。

因此可以概括为：

> Use Case 提供系统内部 FR 的起点；业务规则、状态模型、数据模型、接口契约、异常场景、事件列表和运维场景，负责把内部 FR 补完整。

不是所有内部 FR 都必须从某一个 Use Case 的步骤中直接“提取”，其中相当一部分属于 **分析人员根据业务正确性、完整性和异常恢复需要推导出的派生需求**。
