# 06 — 轨 B 持久化地基：一次 migration 落齐全部新表

**做什么：** 把批次 2 轨 B 四条能力轨需要的**全部**持久化结构，在一次 migration 里落齐，
并把它们的存取端口在 `Ports.cs` 里一次定齐。做完之后，票 09／10／11／12／13 全部零
migration、零 `Ports.cs` 改动。

**这张票存在的唯一理由是消除并行冲突。** EF Core 的模型快照是单文件：两条能力轨各加一个
migration，快照必然冲突，而且后一个的 Designer 快照依赖前一个已存在。不集中就没有并行。

要落的结构，按能力轨分（形态在完整产品规格里已定到可直接建表的程度）：

- **B2 多车**（票 09）——`agvId × taskType` 准入表、区→车硬集合、每车超时预算；
  **唯一性从 lease 表下移到 `OrderIntents`**（下移之后 `DispatchUniquenessGuard` 一字不改
  仍成立，这是规格 5.1 的定案，不要顺手改它）。
- **`RouteGraphSnapshot` 引擎**（票 12）——设计态与运行态双份持有、`mapEdgeGroup` 指纹、
  两个周期各自的刷新时刻与陈旧判定所需字段。
- **`FP-C11` 命令面与故障隔离**（票 10／11）——两级故障事实（疑似阻断／确认隔离）、
  `FaultedVehicleCargo` 绑定、命令调用的对账审计（要能支撑「只调一次」的判定）。
- **`FP-C13` 目录可用性**（票 13）——目录级状态、`TransportDemand` 冻结的已解析站点、
  建单前置 `RouteCost` 门禁的审计留痕。

**冲突边界（硬约定）：**

- 本票是**唯一**改 `ControlServerDbContext`、Migrations 与 `Ports.cs` 的票。
- 本票**不实现任何业务行为**——只有结构、端口与存取实现。行为在各能力轨自己的票里。
- 本票不碰派车主循环（那是票 05 独占）。

**前置：** 无，可与票 05 并行开工。
