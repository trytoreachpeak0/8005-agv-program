# 09 — B2 多车执行

**做什么：** 让服务端同时驱动多台车。做完之后，三台车能各自建立会话、各自被派单、各自
推进旅程，而调度仍然是单 worker 按车串行，快照新鲜度因此有保证。

**B2 在 348 条需求里没有任何条目载体**——多车是票 02 判定的不变量推翻，不是某条需求要求
的。规格第 3.3 节把它列为十项无条目载体工程之一，共 13 项，出口只有 L1 与 L2 两条，
没有门禁（保形向量是单会话格式，`steps[]` 无车辆维度，结构上表达不了多车）。

五件事：

1. **`OnboardPeer.Attach` 的 N 会话**——同时持有多台车的会话，会话之间不串。
2. **`MT_WAIT_FOR_CHECKPOINT` 识别**——多车下这个状态才会真实出现。
3. **单 worker 按车串行 ＋ 每车超时预算**——不是每车一个 worker。一台车卡住不能拖垮
   其余车，超时预算是这条的保证。
4. **`agvId × taskType` 表**——哪台车能接哪类任务。
5. **区→车硬集合**——哪个区由哪些车服务。

**唯一性从 lease 表下移到 `OrderIntents`** 的表结构由票 06 落地；本票只用它，并且
**`DispatchUniquenessGuard` 一字不改**——规格 5.1 的定案是下移之后它仍然成立，不要顺手
重写它。

**冲突边界：** 按车迭代的循环骨架由票 05 交付，本票不再重构主循环；车辆过滤的两条判据
（`agvId × taskType`、区→车）以判据文件的形式加进票 05 的判据链。

**前置：** 票 05（按车迭代骨架与判据链）、票 06（表与端口）。
