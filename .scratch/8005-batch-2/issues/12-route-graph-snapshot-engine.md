# 12 — `RouteGraphSnapshot` 路网成本引擎，含 `REQ-0207`

**做什么：** 建一份自持的有向站点图，回答两个派车链路必须回答、而 RIoT 的
`getRouteCostsBy` 答不了的问题：站 A 到站 B 的代价是多少、站 B 从站 A 可不可达。

**这是本图最大的单端工程之一**（服务端↔RIoT），不属任何簇、没有切片，出口只有 L1 与 L2
两条。它是**关键路径上最长的一段**。

快照形态（规格 5.6 定案，直接照做）：

- **设计态**按 `gmtUpdate` ＋ **10 分钟 TTL 兜底**刷新；
- **运行态**（当前被移除的边与站点）**独立 10 秒周期**刷新；
- `mapEdgeGroup` 指纹变化，或动态代价由空变非空，**即进陈旧态**。

**引擎是派车链路的硬依赖，快照陈旧即本轮不派车。** 不可用时失去的不只是成本排序层
（那一半可退到 `DeterministicDispatchTieBreak`），**可达性那一半没有退路**——所以是
fail-closed，不是降级。

**`REQ-0207` 在本票落地**：路径证据必须区分可达性与排序成本。无法确认车辆到下一站可达
时该车退出本轮候选，**禁止用直线距离或其它弱替代冒充**。自建图算出的值**不叫 RouteCost**
——两份事实各自具名、互不冒充，这正是 `CP-0001` 修订项一末句在保护的东西。

建单前置的 `RouteCost` 门禁**不在本票**，在票 13。两个 API 的分工是各自能力的自然归属：
选车阶段问「站 A 到站 B」，`getRouteCostsBy` 起点恒为车当前位置、答不了，用自建图；
建单前置问「这台车此刻能不能到那个站」，那正好是 `getRouteCostsBy` 唯一能答的问题。

**表述纪律**：`CP-0001` 批准前，本票产出的任何证据都**不得写「符合 `REQ-0298`」**；正确
写法见规格 8.8 第 3 条。

**冲突边界：** 引擎实现为独立文件；接入派车链路时以判据文件 ＋ 排序器的形式加进票 05 的
判据链，不重构主循环；表由票 06 提供；不写 migration。

**前置：** 票 04（`CP-0001` 批准）、票 06（快照表与端口）、票 07（SDK 的五个 `imap`
Facade——产品代码必须走具名 Facade，不得先用 `.Raw` 打桩）。
