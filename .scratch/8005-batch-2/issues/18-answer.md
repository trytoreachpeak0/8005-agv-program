## 开工第一天就撞上的事：命令面没有调用方

票据把「命令面在 L2 上证明三条断言」列为出口。**做之前先 grep，结果是命令面在运行时不可达**：

- `VehicleFaultCoordinator` 与 `RiotOrderCommandService` 都在 `Program.cs` 里注册了，
  **全仓没有任何调用方**——没有 hosted service，HTTP 面只有三个 GET。
- 票 10 决议自己写着「今天唯一有调用方的来源是 `Automatic`」，票 11 留的缺口一就是这个。
- 票 09 已经查明**不能**从车辆循环泛泛地驱动 `ObserveAsync`：在检查点等待的车读成 `Unknown`，
  `RequiresEscalation` 的第一个条件按构造成立，第一次评估就发急停；而 `VEHICLE_OFFLINE` 进来
  之后，清除路径 `ResumeAsync` 要求一张仍然 HELD 的单，一台空闲车瞬时掉线会被永久困住。

所以出口要么接一个触发点，要么如实登记为受阻。**用户选择接最窄的那个**（2026-09-08，本会话
开头明确批准）。

### 接的是 `REQ-0232` 五个症状里的一个：在途单被报成终态 FAILED

选它的理由是具体的，不是「挑一个好做的」：**只有它自带故障模型需要的两样东西**——

1. **一台有在途单的车**，所以 `OrderHold` 有目标（`REQ-0234` 明令不得用 Cancel）；
2. **一张 `ResumeAsync` 日后问得到的单**，所以故障有清除路径。

票 09 拒绝的两条走位各缺其中之一。而且它不是推断：一张本服务端创建的单被 RIoT 报成 4 FAILED，
是 RIoT 对本项目自己的任务给出的陈述。

落点是 `JourneyRuntimeEngine.ObserveOrderFailureAsync`，挂在两个到站阶段的「没到站」分支里，
在 `NameCheckpointWaitAsync` 之前。顺带把 `IsTrustedArrivalAsync` 改成 `CheckArrivalAsync`，
返回一条 `ArrivalCheck` 记录把订单观察带出来——**不是为了省一次 RIoT 调用，是为了不产生第二个
答案**：两次读可能不一致，那样「没到站」与「单失败了」就是按不同的事实判的。

### 三处自行定案

**一、journey 的 stage 有意不改成 `Blocked`。**故障事实本身就挡住新派车，从记下的那一刻起。
留在到站阶段能让循环继续评估，而那是 `REQ-0247` 的停稳判定唯一能推进的方式——采样窗口需要有人
继续采样；车真的动起来时升级也还活着。改变的只是 journey 为「不动」给出的原因码，形状与检查点
等待那条一致。

**二、货物只在关卡段绑。**去取货的路上车是空的，而且这一点是**已知的**，正是 `REQ-0238` 唯一
说可以不绑的那种情形；过了已提交的装载，车上载着这一趟的产品，绑定必须成立。

**三、修掉一处会在这条路径上必然发作的重发。**`HoldCurrentOrderAsync` 原本对任何非 `Confirmed`
的结果都在下一次评估重发。而 `Failed` 是对账对「终态但不是目标态」的判词——用它自己的话说，
「命令没做到它要做的事，且再也做不到」。重发改变不了这一点，却会让一台车在故障持续期间**每个
评估周期挨一次 `CMD_ORDER_HELD`**。

这正是规格 8.3 要求出口排除的那件事，而且它只在有了调用方之后才看得见。`Pending` 与 `Unknown`
仍然重试——那两个是后续回读还能定的。

**「只调一次」因此是结构性成立的，不是碰巧。**哪天有人把这条规则改回去，`L2-CS-09` 会红，
而且是每轮加一行地红。

## 三种陈旧触发怎么在 L2 上真的取到

前两条只差一个驱动方式：假 RIoT 控制面加了 `PUT /control/v1/edge-groups` 与
`PUT /control/v1/dynamic-route-costs`。**第三条「超 TTL」值得单独说，因为它一开始看起来取不到。**

`RefreshOnceAsync` 每一轮都刷新运行态，刷完立刻判陈旧，所以只要 worker 活着，运行态的年龄在
被判定的那一刻永远接近零——TTL 这条兜底看上去在 L2 上不可观测。

但它取时刻的方式给了答案：**`now` 在一轮的开头取一次，用它给运行态盖时间戳；跑完四段读之后，
判陈旧用的是当时的时钟。**所以只要一轮刷新**自身**耗时超过预算，运行态在写下的那一刻就已经
过期了。把假 RIoT 切到 `Delay 2000ms`，四段读就是 8 秒，稳过 5 秒的预算。

**这不是把场景凑绿，恰恰是这条兜底存在的理由**：它防的不是「没人来刷新」，而是「刷新慢到它
护不住的程度」。

三条的顺序也不能换，理由是可清除性不同：超 TTL 会被下一次及时的刷新自己清掉，另外两条不会
（`StaleReason` 里它们是「等待改变不了」的那两个）。先做能清的，再做两条黏住的，后一条覆盖
前一条，因此逐条读得到。反过来排，第一条黏住之后剩下两条永远读不出来。

## `identity` 两项新字段：`protocolReleaseIdentity` 从服务端读回，不复述

票据提醒过「协议仓仍是 v0.1.1，先想清楚 v2 三元组填什么，别留个填不出的字段」。

**答案是不填 v2，而是读回服务端此刻在线上强制的那一份身份。**`Invoke-L2Scenario.ps1` 在服务端
起来之后打一次 `/version`，把 `ProtocolCandidateIdentity` 的九个字段加 `approvalStatus` 原样
写进 `identity`。今天读回的就是 `protocol-v0.1.1`；批次 1 出 v2 之后，同一处读回自动跟着走，
脚本一行不用改。

理由不是省事：**能按协议换代作废 L2 证据的只有 build 真的在握手上强制的那一份身份。**在脚本
里复述一个「候选三元组」，得到的是一份与脚本自洽、与服务端无关的证据——那正是这个字段要防的
事。运行没跑到读 `/version` 就死掉时写 `null` 而不是省略：「这次没跑到那一步」与「这份证据早
于这个字段」是两回事。

`batchId` 是 `-BatchId` 参数，默认 `batch-2`，CI 显式传。批次是计划，仓库里推不出来，所以它是
参数而不是常量——一个写死 `batch-2` 的常量在批次 3 会安静地说谎。

## 两处跑出来的坑，都留了红的证据

### 一、L2 的固定端口块落在 Windows 动态端口范围里

第一次跑 `normal-load` 就红了：

```
Unhandled exception. System.Net.Sockets.SocketException (10013):
An attempt was made to access a socket in a way forbidden by its access permissions.
```

**10013 不是 10048**，读起来像权限问题而不是端口冲突，所以第一反应会往错的方向查。实际是机器上
一个代理的出站连接把 58410 绑在 `0.0.0.0` 上。Windows 默认动态端口范围是 **49152–65535**，
旧端口块（58405–58413）整个落在里面，任何不相干的程序都可能在任意时刻占着其中一个。

**固定端口的装置落在动态范围里就是构造性易碎的**，而本票自己的出口判据是「连续三次通过」。
整块挪到 484xx，并给合成对端单独分了一块（48420 起，每台车加一）——对端数量是唯一不固定的那个，
旧布局下第二、第三台车的端口正好压在模拟器的两个端口上，两套装置互斥才没炸。

### 二、`Invoke-L2Query` 那个坑还有一层，穿得过包装函数

上一份交接记过「不要给 `Invoke-L2Query` 再包一层 `@()`」。本会话撞到的是同一件事的另一面：

```powershell
function Get-Journeys { return Invoke-L2Query -Connection $connection -Sql '...' }

Get-Journeys | Where-Object { $_.AgvId -eq $id }   # 错
$rows = Get-Journeys; $rows | Where-Object { ... }  # 对
```

`return , $rows` 的包装**穿得过一层 `return`**：管道里只有一个元素、那个元素是整张结果集，
`$_.AgvId` 于是成员展开成三个值拼成一行，一条也匹配不上。赋值给变量会展开外面那层。

症状是「三趟 journey 都在库里，却一趟都找不到」，而且 `Wait-L2Condition` 会吞掉探针里的异常
（那是「还没到」和「探针写错了」共用的路径），所以它表现为一次干等到超时。已写进
`scripts/l2/README.md` 的「加一个场景」一节。

## 如实登记的缺口

### 一、CI 的三连绿尚未发生

`l2.yml` 已经写成「出口三条各跑三次、任一次红就跳过该场景剩余轮次」，本机 17 次运行全绿。
但**本会话没有推送任何东西**，所以 CI 上还没跑过一次。推了之后 l2 workflow 会自己跑；
它的 `timeout-minutes` 已从 20 提到 60（11 条场景 17 次运行，本机耗时约 12 分钟）。

### 二、票 11 的缺口一只关上了一条缝

本票给命令面接了**一个**触发点。`REQ-0232` 另外四个症状（掉线、通信中断、导航失败、超时）
仍然没有调用方，`ConfirmIsolationAsync`（人确认隔离）与人发起的两条急停入口也仍然只有策略
没有传输。要把它们接上，前提没变，就是票 11 决议与票 09 交接说的那两样：

1. **一条不依赖在途订单的清除路径**（`REQ-0253` 权限模型那条线）；
2. **一个能把「交通性等待」与「不动了」分开的症状来源**。

本票没有触碰这两样，也没有把它们变得更近。

### 三、`ROUTE_GRAPH_DESIGN_STATE_EXPIRED` 没有单独取证

「超 TTL」这一条取的是 `ROUTE_GRAPH_RUNTIME_STATE_EXPIRED`。设计态那条是同一个机制的另一个
参数（`StaleReason` 里紧挨着，先判设计态后判运行态），场景把 `DesignStateTtl` 抬到 1 分钟正是
为了不让两条同时到期——两条同时成立时只报先判的那条，测到的就不是想测的那条。

L1 的 `RouteGraphDispatchTests` 覆盖了设计态过期。要在 L2 上单独取它，需要一个能把设计态刷新
单独拖慢的注入点，而假 RIoT 今天的 `Delay` 是全局的。**登记为遗留，不建议为它给装置加一个
按端点分别延迟的开关**——那是把装置越造越像被测物。

### 四、三台车共用一个区号

`three-vehicle-exit` 的三个需求都在 `N1-3`。这是有意的：三台车面对完全对称的候选，「不会选中
同一个需求」才真的被证到；给每台车一个只有它够得着的区，等于把题目提前解掉。**代价是「按区
分车」（`DispatchZoneVehicleCriterion`）在这条场景里没有被行使**，它的覆盖仍然只在 L1。

## 给下游票的指针

1. **票 19（W1 空载急停演练）**——现在**有**一条会通到急停的运行时路径了，但它要三个条件同时
   成立才走到 `EscalateAsync`：在途单被报 FAILED、车读不出「停住了」、且尚未升级过。演练脚本
   如果只想要急停而不想要故障事实，`REQ-0247` 的停稳判定会把它挡在外面——**演练要造的是「车
   读不出停住」，不是「单失败了」**。W1 的出口判据「8005 侧只发一次调用」与本票 `L2-CS-09/10/11`
   同源：都数 `RiotOrderCommandAudit` 的 attempt 行数，不数假 RIoT 的请求数。

   48420 起）。任何写死旧端口的脚本或文档都要跟着改；仓内只有 `scripts/l2/Invoke-L2Scenario.ps1`

   举例，已确认不影响运行。

4. **任何要给 L2 加场景的人**——setup 文件现在认六个键（`Onboard`、`OnboardSeed`、`ClockSkewMs`、
