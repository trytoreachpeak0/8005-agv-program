# 13 — `FP-C13` 建单前置门禁与目录可用性

**做什么：** 让建单这一步有一道真正的前置门禁：目录不新鲜不建单、站点解析不出来不建单、
车到不了目标站不建单。做完之后，任务从建单那一刻就冻结了它的端点，后续目录变化改不了
已建的单。

三条需求：

- **`REQ-0302` 新鲜度按最近完整确认计算**——同步周期与最大允许未确认时长两个值**必须在
  投运前分别批准**，且**最大未确认时长须大于正常同步周期**。
- **`REQ-0305` `TransportDemand` 冻结已解析站点**——新任务只能从当时新鲜的当前快照取得并
  冻结端点，**不被后续目录重写**。
- **`REQ-0308` 两类失败分层**——同步异常形成**目录级**状态（刷新失败、候选无效、超新鲜度、
  build/环境不兼容），真实缺站形成**任务级**阻断。两者不可混。

**建单前置 `RouteCost` 门禁在本票落地。** 它在 `src/` 里 `RouteCost` 零命中，从没实现过，
而五条基线条目明文要求它：`REQ-0147`／`REQ-0293`／`REQ-0302`／`REQ-0305`／`REQ-0345`。
问题形态是「这台车此刻能不能到那个站」，用 `getRouteCostsBy`——这正是它唯一能答的问题。
**两个证据源分歧时阻断建单并告警**，不取其一。

`queryNearEnd`／`queryNearestStart` 的全面退出不变，本票不要重新引入它们。

**`REQ-0302` 是三处硬阻断之一**（规格 8.6）：无已批准值时，依赖 Map/Station 的业务**不得
启用**。**出口必须含负向证据**——把参数拿掉，证明它真的阻断了。只证明「配好之后能跑」证
不出阻断存在。

**冲突边界：** 门禁以判据文件的形式加进票 05 的判据链，不重构主循环；表由票 06 提供；
不写 migration。与票 12 的分工见上（选车用自建图，建单前置用 `getRouteCostsBy`），两票
可并行。

**前置：** 票 05（判据链）、票 06（表与端口）。
