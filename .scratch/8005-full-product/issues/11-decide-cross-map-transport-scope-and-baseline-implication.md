# 决定跨 Map 运输的去留，以及它对 v1.0.0 基线的影响

Type: grilling
Status: open
Blocked by: 01
Blocks: 02

## Question

票 01 查明：**v1.0.0 的 348 条里没有任何需求要求跨 Map 运输，基线反而明文禁止它。**
三条 MVP 直接必须的规则把 Map 边界钉死——`REQ-0191`（每个 `DispatchZone` 只归属一个
以 `mapId` 标识的 RIoT Map）、`REQ-0192`（车辆必须实际位于任务所属 Map 才进入候选）、
`REQ-0193`（固定站点不得跨图，禁止跨 Map 运输）。多 Map 的**基础设施**已在批次 0
（`REQ-0300` 全量原子快照、`REQ-0338` 同图校验、`REQ-0305`、`REQ-0334`、`REQ-0341`）：
系统已经知道存在多张 Map，缺的不是能力而是许可。62 条里唯二沾 Map 的 `REQ-0195`
（**同图**跨区）与 `REQ-0289`（等待点以地图 + 站点登记）都在单 Map 语义内。

而 precontext 与票 02 把「单 Map→跨地图」与单车→多车、人工充电→充电桩调度并列为
三大重构之一。前两项在 348 条里有成簇的条目支撑，第三项一条都没有。这个前提必须
在票 02 判定重构／增量之前澄清，否则票 02 会为一项本图无法排期的能力划分归属。

须回答：

1. **完整产品到底需不需要跨 Map 运输？**判断依据是现场事实而非文档——8005 项目当前
   有几张 RIoT Map，机台、关卡、暂存与充电桩是否分布在多于一张 Map 上，是否存在
   「一端在 A 图、另一端在 B 图」的真实搬运需求。若现场只有一张 Map，`REQ-0193` 就
   不是限制而是对现实的准确描述，本图无需处理。
2. **若需要，处置路径是哪一条？**两条路互斥：
   - **本图 Out of scope。**理由是它要先走需求变更流程修改或废止 `REQ-0193`，
     而这不在「348 条的实施范围与顺序」这个 Destination 之内。本图在最终规格中留一行
     指针，跨 Map 作为独立的后续工作。
   - **改本图 Destination。**认定完整产品必须跨图，则本图须先派生一张需求变更的前置
     工作，Destination 从「覆盖 348 条」变成「覆盖 348 条 + 一次基线变更」。
   选定一条并说明代价。注意地图 Notes 现有的「本图不改 v1.0.0 基线」与第二条冲突——
   选第二条就必须同时修改那条 Notes，这是一次自觉的范围重划，不能默默进行。
3. **无论选哪条，`REQ-0191`／`REQ-0192`／`REQ-0193` 三条在最终规格 348 行里怎么表述？**
   它们是批次 0 的已实施条目，不是延后项。若判定跨 Map 属未来工作，规格中不得把这三条
   写成「待放宽」——那等于在规格里预告一次未经批准的需求变更。地图 Notes 已定「不做」
   只有延后与本图范围外两种合法形态，本题须落在其中之一。
4. **这个结论对票 03 的影响。**票 03 第 6 点写明「跨地图如果按票 01 的结论落在本票，
   其范围一并在此决定；若落在别处，本票明确不处理并指出去处」。本票须给出票 03 要引用
   的那句去处表述。

### 已知边界

- 本票不修改 v1.0.0 基线，不动 `requirements/current-baseline.md` 指针，也不发起需求
  变更流程——它只决定要不要走、以及走的话谁在哪一步走。
- 本票不决定多 Map 的技术方案。即使判定要做，路径规划、跨图转运点与 RIoT 侧的能力
  边界都属于实施图。
- 现场事实若在本工作区内查不到，须如实记录为待用户确认的外部事实，不得以推测替代。
