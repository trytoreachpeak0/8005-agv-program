# 决定治理面增量范围（账号权限、配置审计、AGV 生命周期、看板）

Type: grilling
Status: open
Blocked by: 02

## Question

在票 02 定下的分类与排序规则内，决定完整产品的治理面做到哪一档。这是 62 条里被 precontext 归为「纯增量」的部分，涉及的条目至少包括：

- **账号、权限与密码**：异常处置权限按个人授予（`REQ-0236`）、专门权限并入管理员角色（`REQ-0254`）、账号生命周期与立即撤权（`REQ-0256`）、不建立泄露找回或强制重置流程（`REQ-0273`）、密码只能由系统管理员设置（`REQ-0274`）、首次改密仅用于部署初始化（`REQ-0275`）、设置新密码不联动当前会话（`REQ-0277`）、密码设置沿用不可改写审计（`REQ-0280`）、敏感生效动作要求新鲜二次认证（`REQ-0339`）。
- **配置治理与审计**：模板资料变更与硬件配置变更分开治理（`REQ-0260`）、只有硬件相关变更进入整车维护（`REQ-0261`）、配置审计必须可还原全过程（`REQ-0266`）、回滚是受控的新激活而非历史覆盖（`REQ-0346`）、配置和拓扑变化不破坏既有引用（`REQ-0297`）。
- **AGV 生命周期与归档恢复**：维修使用暂停分配而非临时删除身份（`REQ-0288`）、只能恢复原车辆档案（`REQ-0310`）、恢复权限只属系统管理员（`REQ-0311`）、归档前配置作为恢复候选（`REQ-0316`）、恢复与投运严格分离（`REQ-0317`）、车辆离线时可先恢复档案（`REQ-0318`）、每次恢复尝试形成不可改写审计（`REQ-0320`）、覆盖治理问题随能力一并消失（`REQ-0326`）。
- **看板与观测**：车队与仓位看板统一 2 秒刷新节奏（`REQ-0268`）、车辆失联按观测来源分开（`REQ-0287`）。

注意票 02 可能把其中一部分判为重构类（尤其 `REQ-0288`、`REQ-0297`、`REQ-0326`、`REQ-0287` 与分配核心的资格判定耦合）。本票只处理票 02 判为增量的那些，被判为重构的条目须明确指出去处。

须回答：

1. MVP 以「预置配置 + 具名管理员」运行、明确延后完整管理 UI。完整产品的管理面做到什么程度：哪些配置必须有 UI，哪些继续接受受控预置，判断标准是什么（例如「现场运行期间会变更的必须有 UI，投运前一次性配置可预置」）。
2. 账号与权限模型的最小完整集：角色有哪些、`SystemAdministrator` 的边界、异常处置权限按个人授予同角色模型如何共存、二次认证覆盖哪些敏感动作。明确不做的（泄露找回、强制重置）在规格中如何表述才不被误读为遗漏。
3. 配置审计的可还原粒度：「可还原全过程」要求记录到字段级还是版本级，回滚作为新激活对既有运行中任务／充电周期的影响边界（既有周期继续使用各自固定的原版本，空闲车辆立即按新版本判断）。
4. AGV 生命周期：归档、恢复、暂停分配、投运四个状态的转移规则与权限，以及恢复后不自动投运这条约束对运维流程的要求。
5. 看板与观测面的范围：2 秒刷新的车队与仓位看板是否属本期，还是同「完整管理后台、高级报警分析、运营大盘」一并延后。若属本期，其数据来源是否要求新的协议消息（输入给票 06）。
6. 治理面各子簇之间是否存在强制顺序（例如权限模型必须先于配置审计，因为审计要记录操作者身份）。

### 已知边界

- 本票不改协议消息面；治理面若需要新消息，本票只输出需求，冻结在票 06。
- 本票不决定批次归属与顺序，那是票 09。
- 本票不设计 UI。界面形态若成为关键问题，应在本票中点名并留给实施图的原型票，不在本图内做原型。
- 本票不决定车载端实现方式；车载端归 Kun Wang，仓库只读。
