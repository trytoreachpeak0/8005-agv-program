# 票 08 决议：完整产品验收边界、证据要求与双人分工排期

日期：2026-09-04
票据：[08-decide-full-product-acceptance-boundary-and-two-person-plan.md](08-decide-full-product-acceptance-boundary-and-two-person-plan.md)
前置：票 07（已闭）、票 14（已闭）；本票是本图的最后一张前沿票，票 10 是汇编票。

**一句话结论**：完整产品的验收边界**不需要新发明**——`8005-agv-program/docs/wire-to-gate-test-automation.md`
定义的 **L1／L2／L3 三层模型已经建成并在跑**，本票做的是把九个批次的出口条件挂到这三层上，

(expensive, human-scheduled), and it is **the only automated layer that sees cross-end timing**」。

### 1.9 `REQ-0259` 是每车判定，票 09 的表述要收窄

票 09 的 3.3 与票 08 票据正文都写着「三台现有车**同时**失去业务就绪」「三台车逐仓 IO 现场核对」，
读起来像必须一次做完三台。**基线原文（`current-requirements-v1.0.0.md:15007`）不是这个意思**：

> 已发布模型中的全部仓位必须具有完整并经实际核对的 SlotIoBinding，**整车**才达到
> SlotConfigurationReadiness。在此之前**整车**不得取得业务就绪，任何未配置或未验证仓位
> 不得被业务分配，管理员也不能强制放行。

判定单位是**整车**，不是车队。`REQ-0263`（`:15285`）的「不允许只测改动仓位或抽样测试。
任一仓位未通过都会阻断整个候选版本」同样是**在一台车之内**——禁的是一台车里抽几个仓测。

**净结果：三台车可以逐台推进。**这把一个看似的运营取舍变成了一个有唯一正确答案的排序问题
（见 Q1 的处置）。

### 1.10 假 RIoT 的能力边界与完整产品的缺口

`tools/ControlServer.FakeRiot` 数据面只有 6 个端点（`RiotDataPlane.cs`）：
车辆信息两条、`mapInfo/stations/{mapId}`、订单详情、订单列表、
`POST /api/order/v1/add/byDefaultMissions`。

完整产品要而它**没有**的：`mapInfo/edges/{mapId}`、`mapResource/removedEdge`／`removedStation`、
`mapEdgeGroup/all`（`RouteGraphSnapshot` 引擎的五个数据源），以及
`OrderHold`／`OrderContinue`／`HangContinue`／`CancelOrder`／`triggerEmergency`／`cancelEmergency`
（`FP-C11` 命令面）。

**它的既定边界必须保留**（方案文档第 3 节缺口 1 的落地补充）：「控制面**不提供任何

——记录「8005 调用了哪个命令、带什么参数」属于**观测**，不越界；
让假 RIoT 主动把车摆成急停态才是越界。这一条决定了 Q4 的形态。

## 二、七问定案

用户 2026-09-04 分两轮回答，**七个问题全部取推荐值，无异议**。
第二轮的第一个问题（真装置进 CI）用户要求先解释再答，解释后取推荐值。

### Q1 — 验收边界：分层出口 ＋ 三个现场窗口（用户定）

**每个批次的默认出口是 L1 ＋ L2 全绿，现场验收只在跨过一个现场前置或需要真车物理事实时才做，
合并成三个窗口。**批次 1（纯协议）与批次 2 轨 A（八切片重证）完全不进现场。

取它而不是「每批一次现场验收」（要清 7 次场、占 7 次生产 AGV），
也不是「最后一次综合验收」（一次失败无法定位到批次，且违反「批次是可独立交付单元」的前提）。

### Q2 — 向量执行器：不建，改用架构测试钉住绑定（用户定）

**删掉 `runner/` 两个 schema**（1.4 已证它们从未对过、无生产者无消费者），
**不建第五套执行器**，改为补一条架构测试断言「每个 `vectorId` 在实现仓有同名具名测试」，
把「人写的引用」变成机械可检查的绑定。配合票 06 已定的 `productAssertions` 全量必填。

取它而不是「按真实格式重写 runner 契约并做执行器」：后者保守估计一到两周、要两端同时改，
会直接撞上批次 1 的一周承诺。**代价如实记录**：G2 的「向量即判据」永久是一条弱绑定
——机械保证的是「这条向量有对应测试」，不是「这条向量的字节被执行过」。

### Q3 — 多车 L2：只建合成装置多车（用户定）

假 RIoT 种 3 台车、起 3 个 `FakeOnboard`，覆盖选车排序、占有争用、防饥饿这些**服务端判定**；
能进 CI。**真装置多车不建**（3 个 WPF ＋ 3 个 slots-simulator，单次运行时间大幅上升，
且仍进不了 CI），多车的物理验收留给现场 3 台真车。

取它而不是「都不建」：多车缺陷若只能在现场 3 台真车面前暴露，那正是这套 L2 建起来要避免的事。

### Q4 — `FP-C11` 安全能力：L2 证机制 ＋ 现场一次空载受控演练（用户定）

假 RIoT 加命令面并**记录调用**（属观测，不越 1.10 的边界），
L2 证明「该触发时确实发出了正确的调用、参数正确、只发一次」；
现场只做**一次空载**（车上无物料）受控急停演练，逐次授权 ＋ 现场安全 GO，
验证 RIoT 侧真的接受并停车。

取它而不是「只验调用发出」：那样「RIoT 真的会因为这个调用停车」永远没有目标环境证据，
而 `REQ-0246`／`REQ-0248`／`REQ-0249` 是安全条目。也不取「整簇延后」：
issue `8005-agv-control-server#1` 指出的安全缺口会继续留着。

### Q5 — 真装置 L2：接桌面锁，变成每次 push 自动跑（用户定）

两处改动：`8005-agv-control-server` 拷一份 `Invoke-WithDesktopLock.ps1`（名字是契约，代码不是）；
`8005-mes-ingest` 那把锁从「抢不到就 exit 3」改成「抢不到就带超时等待」
（根 `CLAUDE.md` 明写第二个仓加入前必须先做这一步，否则 CI 会因为撞上另一个仓的调度而变红）。
真装置三条挂 `golden-renderer` runner。

**两个仓都可写**，不触碰 `8005-agv-onboard-hmi` 与 `slots-simulator`。

### Q6 — 多车现场清场：分阶段放开 1 车 → 2 车 → 3 车（用户定）

每阶段跑一个完整路径，均为严格清场（无关人员与车辆退出作业区）；
三车同时那一步需多一名观察员。**自动充电首次现场触发必须有人跟随全程**，此后才允许无人跟随。

取它而不是「三车一次性验」：第一次多车相遇就发生在三车全开的情况下，
风险与可诊断性都最差。也不取「延后到充电桩装完一起验」：
那会把两个未验证的新能力叠在同一次现场窗口里。

### Q7 — 失败与回退：按能力开关部分保留（用户定）

批次代码不回退，未通过的能力用**受控预置配置关掉**（fail-safe 方向），已通过的留着。
**不允许带已知安全类缺陷投运。**

这给实施图一条硬约束：**每个能力必须有一个能单独关掉它、且不影响其它能力的开关**。
取它而不是「整批回退」（一个小缺陷会把整批已验证能力一起撞下去），
也不取「带已知缺陷投运逐条登记」（与 MVP 已有的「永久红色证据」纪律相反，
且安全类缺陷无法靠运维约束回避）。

### 3.1 三层验收出口的定义

**每个批次的默认出口 ＝ 三条同时成立：**

1. **L1 绿**：该批次涉及的单元与集成测试全部通过，**且新能力有新增覆盖**

### 3.4 证据要求：目录、格式、保留策略

**沿用现有结构，不另起一套。**方案文档第 5 节已经这么定了，本票确认并补齐完整产品部分。

1. **`-EvidenceRoot` 必须是不存在的目录**（L2 README 的硬规则）。
2. **红的证据不允许被绿的重跑覆盖。**已有实例：`evidence/l2/` 里三个红目录
   （`load-result-requires-recovery-001`、`real-onboard-clock-skew-001` 与 `-004`）
   全部留着，各自的原因写在 README 里。
3. **跑失败时 stage root 不删**，路径打在告警里。

   里指向被纠正的那份。

这是本票自定的设计细节。

### 3.5 四类「自然运行取不到」的证据形态

票 02、票 04、票 12、票 13 各交下来一条，共同点都是**当前配置凑巧使规则不触发**，
且票据都写了「**不得默认『不触发即通过』**」。四条统一处置：

只是不在现场那条路上；补测绘或改配置之后无需改代码即可取证。
票 12、票 13、票 14 已经各自这么判过，本票统一确认。

**`REQ-0174` 的失败码 407802 单独处置**（票 04 的第二条输入）：它出处只有 Round 24，

「已经目标 build／契约验证的失败码」。判为**验收项，不是投运前置**——
它要真桩 ＋ 真失败才能在目标 build 上取到，投运前不可得。
处置：`ConfirmedUnableToCharge` 的严格系统事实在目标环境证据缺失期间走保守分支
（不确认即不算 confirmed），**W3 窗口内首次现场充电失败时补证**。
**这同样不是 `证据受限实施`**——它不是「恒」走保守分支，是补证后转正。

   唯一的认证是一个全场共用的环境变量。
3. **`CP-0001` 未获批准前，引擎相关切片的验收证据里不得出现「符合 `REQ-0298`」这类表述**
   （票 15 的输入，票 09 已把修订项二由四个端点扩到五个，适用范围随之扩大）。
   批准前的正确表述是：「实施形态与基线 `REQ-0298` 原文存在一条已知且已记录的偏离，
   偏离的处置见 `CP-0001`」。

### 3.9 失败与回退（Q7 的展开）

**处置规则：**

1. 批次代码**不回退**。
2. 未通过的能力用**受控预置配置关掉**，方向必须是 fail-safe
   （关掉的后果是运力下降或功能不可用，不能是绕过安全门禁）。
3. 已通过的能力**留着**。
4. **安全类缺陷不允许带病投运**——`FP-C11` 的三条自动急停、`REQ-0259` 的 IO 完整性门禁、
   `REQ-0263` 的逐仓核对属于这一类。
5. 关掉一个能力时，**必须重新检查它的下游**：批次间依赖是 DAG，
   而 `2轨B → 5 → 6 → 7` 是一条不变量硬链，关掉链上一环等于关掉它下游的全部。

**这给实施图一条硬约束**：每个能力必须有一个能单独关掉它、且不影响其它能力的开关。
**这不是免费的**——它要求能力之间的耦合在设计时就被切开，
而本图已经识别出至少一处天然耦合（`FP-C4` 的等待点独占是 `FP-C1` 充电桩分配的前置，
票 02 的 `REQ-0178`）。实施图排批次 5 与批次 8 时须为此留出接口。

## 五、写回 `CONTEXT.md`

新立三个词条，位置在 `IntegrationSliceFamily` / `ImplementationBatch` 之后。

**`SemiPhysicalScenarioLayer`（半实物场景层，L2）**：
一条把真控制服务端、真车载端与真仓位 IO 接在一起、由脚本无人值守驱动并对被测方自身状态
（服务端数据库、各替身控制面快照）断言的自动化验证层；它介于进程内单元测试与现场试运行之间，
是**唯一能观测跨端时序的自动化层**。它有两套装置：合成装置用协议对端替身，
真装置用车载端产品程序与真 Modbus 模拟器，两者不可互换——合成对端没有 IO、journal、
操作员与本地时钟新鲜度判定。**L2 通过不代表现场合格**：它没有真实 RCS、真车、
交通管制与真实 IO 硬件。

**`AcceptanceExitCriteria`（验收出口条件）**：
一个 `ImplementationBatch` 算作完成所需满足的判据集合，由三部分构成——
进程内测试全绿且新能力有新增覆盖、该批次的半实物场景在 CI 上连续三次通过、
以及该批次绑定的每个切片四道门禁全 PASS。**现场判据不属于它**，
现场验收在 `FieldAcceptanceWindow` 里单独定义，因为现场前置的时间不由本项目控制。
一个批次的出口条件里可以有负向判据（证明某个门禁在参数缺失时确实阻断），
且当某条需求在当前现场配置下自然不触发时，出口条件必须指定一个可复现的替代证据来源，
**不得以「不触发」充当通过**。

**`FieldAcceptanceWindow`（现场验收窗口）**：
一次占用真实车辆、真实厂区与现场人员的受控验收，按现场前置就绪而不是按批次号排期。
它不是门禁——切片的 `gates` 数组不含它，其证据独立归档。
每个窗口有明确的进入门槛（代码就绪 ＋ 现场前置完成）与逐条出口判据，
且首次涉及车辆自主行为的窗口必须有人跟随全程。

**另需修订一处既有词条**：`IntegrationSlice` 正文里
「需要多个并发会话才能表达的行为（例如多车并发）在保形向量的单会话格式下也无法成为切片，
**两者的验收另行规定**」——「另行规定」现在有了具体所指，
补一句指向 `SemiPhysicalScenarioLayer` 与 `FieldAcceptanceWindow`。
