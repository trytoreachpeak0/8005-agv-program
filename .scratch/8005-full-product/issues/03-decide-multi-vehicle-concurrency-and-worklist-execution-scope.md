# 决定多车并发、车辆占用与 Worklist 执行模型的重做范围

Type: grilling
Status: open
Blocked by: 02

## Question

在票 02 定下的重构／增量分类与排序规则内，决定完整产品要把 ControlServer 的选择与分配核心重做到什么程度，以及车载执行入口相应改到什么程度。

MVP 冻结的边界是单车、单 Demand、从受理到收敛排他，多个合格候选留在共享 `UnassignedDemandBacklog`，不预绑忙车、不做多车评分。完整产品要拆掉这个边界，涉及的条目至少包括：多 Sublot 不合并 Demand（`REQ-0189`）、同图跨区允许但不得往返摆动（`REQ-0195`）、执行途中受控追加（`REQ-0196`）、后续停靠有界删除或换序（`REQ-0197`）、顺路取货按最大晚到量约束（`REQ-0198`）、任务类型初始优先级带（`REQ-0202`）、防饥饿阈值现场标定（`REQ-0203`）、车辆按新增行程成本比较（`REQ-0206`）、共晶与低温共晶在选任务阶段排除（`REQ-0185`）、当前车辆已不符合资格时的换车（`REQ-0328`），以及车载 Worklist 选任务模式那 6 条（`REQ-0212`、`0214`、`0215`、`0217`、`0219`、`0220`）。**空闲返回与等待点那 8 条不在本票**——票 02 已判定它们承载 `B1 + B4` 这对原语、且是自动充电的前置，从本票拆出为**票 12**。

### 票 02 定下的分类与顺序（本票必须在其内工作）

[票 02 决议](02-answer.md)把「重构」定义为**推翻五条有代码位置的现行架构不变量之一**，
本票承载其中三条：

| 判据 | 推翻的不变量 | 本票内的载体条目 |
| --- | --- | --- |
| **B2** 车辆集合语义 | I2：`JourneyRuntimeEngine.cs:84` `active.Length > 1` 抛异常；车辆是 `appsettings.json` 标量；选 Demand 排序键无车辆维度 | `REQ-0206`、`REQ-0328` |
| **B3** 计划形状 | I3：`Worklist(...)` 恒单元素；协议 `legs maxItems: 2`、`items maxItems: 1` | `REQ-0189`、`REQ-0195`、`REQ-0196`、`REQ-0197`、`REQ-0198` |
| **B5** 车载选择 Demand | I5：`NEVER_DISCOVER_SELECT_OR_BIND_DEMAND`、`READ_ONLY_COMMITTED_PROJECTION` | `REQ-0212`、`REQ-0214` |

本票 16 条中 **9 条重构、7 条增量**。增量的 7 条是 `REQ-0185`、`REQ-0202`（两条无不变量
依赖，单车下即可实现并验收）、`REQ-0203`（依赖 B2，标定须报告采样期车辆数）、以及
`REQ-0215`／`REQ-0217`／`REQ-0219`／`REQ-0220`（依赖 B5）。

三条约束由票 02 传下来：

1. **本票内的实施顺序是 `B2 → B3 → B5`**，且票 12 的 `B1 + B4` 插在 B2 与 B3 之间
   （全局顺序 `B2 → (B1+B4) → B3 → B5`）。worklist 只有一项时「选任务」无意义，
   所以 B5 必须在 B3 之后。
2. **B2 在 348 条里没有需求条目载体。**348 条中没有任何一条要求「系统支持多辆车」；
   多车是现场 3 车的事实加上 `REQ-0259`／`REQ-0190`／`REQ-0194`（批次 0 已实施）的结果。
   B2 在 348 行剖面里不产生新行，但它是真实工程任务，票 09 须单列。**本票须说明 B2 的
   工程内容**：`JourneyRuntimeOptions` 标量车辆字段改 N 车、拆掉 `active.Length > 1`
   断言、给排序键加车辆维度。持久化层不必动——`VehicleDispatchLeaseRow` 本来就按
   `VehicleKey` 分行并有过滤唯一索引。
3. **B2 不进协议 v2 冻结；B3 与 B5 必须进。**协议 54 个消息每一个的信封都必填 `agvId`
   且无 `const`／`enum`／`pattern`，从未限制车辆总数为 1，三车三会话即可。而 B3 要动
   `legs maxItems`／`sequence maximum`／`legType` enum／`items maxItems`／`stopRole` enum
   五处硬约束加一条 G1 断言，B5 要新增消息并改 `W2G-IS-01` 的 `definition` 与 forbidden
   side effects。清单见票 02 决议问 4。

须回答：

1. 一辆车同时承载多个 Sublot／多个 Demand 的并发边界：完整产品接受到哪一档——同车多 Demand、途中受控追加、后续停靠换序、顺路取货，是一次全开还是分档，每一档的准入不变量是什么。
2. 多车竞争同一 Demand 时的分配规则：`VehicleMarginalRouteCost`、`RouteCostEquivalenceBand`、车辆公平性、`DispatchZoneVehiclePreference` 这些 MVP 明确排除的评分层，哪些进入完整产品、哪些仍排除，以及排除者是延后还是永久不做。
3. 原子承诺与占用语义怎么从「单车排他」推广到多车：MVP 的最终目录重读 + `HistoryEpoch` 约束 + `DemandId` 唯一执行实例身份在多车并发下是否仍然成立，需要新增哪些唯一性约束才能挡住两台车同时承诺同一 Demand、以及同一台车被两个 Demand 同时承诺。
4. 车载 Worklist 入口模式：`WORKLIST_SELECTION` 同 MVP 的服务端指派模式并存还是替换，入口模式按装货开始边界冻结的含义在多车下如何落地，责任按可证明的控制链划分（`REQ-0219`）对服务端与车载端各要求什么证据。
5. 防饥饿阈值（`REQ-0203`）在完整产品里启用还是继续延后。MVP 因阈值未现场标定而只累计等待年龄不做时间型升级；若完整产品启用，标定与批准由谁在哪个批次完成。
6. 跨地图（单 Map→多 Map）**不在本票，也不在本图**。票 11 已判定为 Out of scope，去处表述已定稿，本票原样引用下面这段，不再自行措辞：

   > 跨 Map 运输不在本规格范围。v1.0.0 的 348 条无一条要求它，`REQ-0191`／`REQ-0192`／`REQ-0193` 明文将运输两端限定在同一 Map，三条均已在批次 0 实施。现场当前为单图作业（`mapId` 25 `老厂前线new`，3 台 AGV 与全部机台、关卡、独占充电桩、等待点均在该图）。若将来现场扩为多图作业，放开跨 Map 运输须先经需求变更流程处置 `REQ-0193`，属独立的后续工作，不在本规格的批次序列内。

   不得把 `REQ-0195`（**同图**跨区）当成跨图能力——它在单 Map 语义内。

7. **本票的多车规模是 3 台，不是 2 台**（票 11，用户 2026-09-03 确认），三台车全部在 `mapId` 25 上，且**车辆数量必须可配置**。配置能力本身不需要新需求——`REQ-0259`（新 AGV 先登记后投运）、`REQ-0190`（`VehicleTaskTypeAdmission` 按 `agvId + taskType`，未配置即不进候选）、`REQ-0194`（`DispatchZoneVehicleAdmission` 硬准入 + `DispatchZoneVehiclePreference` 软偏好）已经覆盖。要做的是实现：当前 `8005-agv-control-server/src/ControlServer.Host/appsettings.json` 的 `JourneyRuntime` 段是单车形态，只有一个 `agvId`、一个 `vehicleKey`、一个 `dispatchZone`，把它改成 N 车配置属本票范围。本票须说明这个配置形态怎么变，以及它同 `REQ-0190`／`REQ-0194` 的关系。

### 已知边界

- 本票不改协议消息面。多车带来的消息面变化由票 06 一次冻结，本票只输出「哪些业务能力必须由协议承载」的清单。
- 本票不决定批次归属与顺序，那是票 09。
- 本票不决定车载端实现方式。车载端归 Kun Wang，其仓库对本工作区只读；本票只能决定服务端要求与跨端契约意图，不得规定车载端的内部实现。
- 自动充电桩相关的多车语义（待充电排队集合、充电桩预占）属票 04，本票只在与分配核心冲突处点名，不越界决定。
