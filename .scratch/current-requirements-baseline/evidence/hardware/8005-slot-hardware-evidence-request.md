# 8005 仓位硬件身份与现场信号证据请求

## 目的与边界

本清单用于补齐“补齐 8005 仓位硬件身份与现场信号证据”所需的项目证据，使仓位硬件候选可以进入当前需求基线判断。它不预先确认任何硬件型号、接线、信号语义或现场行为，也不把需求草稿、代码、模拟器设计或未绑定 8005 实车的通用产品资料当成项目事实。

用户已明确供应商手册可忽略。因此，现存 `slots-simulator/docs/reference/` 下的厂商 PDF 及派生寄存器表只保留原有清单、哈希和来源审计记录，不作为本证据包的必交材料或项目适用性证据。

## 证据包准入规则

每份提交材料必须同时登记：

1. `evidence_id`：本表中的稳定编号；一份材料可支持多个编号，但须逐项写明。
2. 原始文件路径和 SHA-256；照片、视频和导出文件保留原始字节，不用聊天截图或转述替代。
3. 证据形成时间、采集时间（若不同）、版本/修订号及来源系统或设备。
4. 适用范围：项目 `8005`，以及适用的 AGV 资产编号/车号；若只抽测部分车辆，写明总体车辆数、抽测车辆和可代表其余车辆的依据。
5. 形成者和证据保管者的姓名、组织/岗位与联系方式；“项目方”“供应商”不是具名责任人。
6. 确认者姓名、确认日期、授权范围，以及其确认所绑定的文件哈希或受控版本号。
7. 与其它材料的交叉引用；若材料冲突，全部保留并登记冲突，不以较新、较详细或更像正式文件为由自动裁决。

## IO 点表最小字段

以下是一旦未来需要受控配置交付时的建议结构，不再是关闭本票的门槛。当前基线使用用户直接确认的 DO1～DO8、DI1～DI16 映射：

| 字段 | 含义 |
| --- | --- |
| `agv_asset_id` | 车辆稳定资产编号/车号 |
| `slot_physical_no` | 物理仓位号；不得用配置数组索引替代 |
| `signal_role` | `UNLOCK_DO`、`LOCKED_DI`、`OCCUPANCY_DI`、`DOOR_STATE_DI` 或 `MOVE_INTERLOCK` |
| `module_asset_id` | 对应 HW-01/HW-02 的模块身份 |
| `channel_or_address` | 端子、通道及协议地址；若三者不同则分别列出 |
| `active_level` | 高/低有效或等价受控描述 |
| `contact_type` | 常开/常闭/不适用 |
| `normal_state` | 上电、门锁闭、仓位空闲时的预期状态 |
| `invalid_or_fault_state` | 断线、模块离线或数据无效时如何识别，不得把未知值自动解释成安全值 |
| `wire_no` | 与 HW-05 图纸一致的线号/端子引用 |
| `config_version` | 当前生效配置的版本或哈希 |
| `verified_by` / `verified_at` | 现场核验人和时间 |

## 现场验证的最低判定要求

用户已明确本次没有现场文件且不把现场文件作为基线门槛。以下要求只约束未来若执行现场验证时如何保存结果，不阻塞本票：

- 以重新读取的真实输入/输出为证据，不以最后一次软件写入值或界面期望值替代。
- 对 `LOCKED_DI`、`DOOR_STATE_DI`、`OCCUPANCY_DI` 和 `UNLOCK_DO` 分别施加可区分的物理场景，验证它们没有被错误互相镜像或推断。
- 记录明确的三态结论：符合、明确相反、不可判定/信号无效；不得把无效数据归为“未触发”。
- 对多模块车辆记录每个模块的发送顺序/并发方式和每个仓位的独立反馈；不得从单模块成功外推跨模块行为。
- 对移动联锁同时记录仓门/锁/开锁输出状态与车辆移动命令的接受或拒绝结果，并说明阻断发生在硬件、车辆控制器还是应用层。
- 每项失败、冲突或无法执行的步骤都进入缺口登记，不从报告中删除。

## 缺口登记与关闭规则

缺口统一使用以下字段：

| 字段 | 规则 |
| --- | --- |
| `gap_id` | `HW-GAP-NNN`，稳定且不复用 |
| `evidence_id` | 对应 HW-01～HW-10，可多值 |
| `affected_scope` | 受影响的车辆、仓位、模块、信号或候选需求 |
| `status` | `missing`、`received-unverified`、`verified`、`conflict`、`not-applicable`、`not-required-for-this-baseline`、`user-confirmed`、`partial-user-confirmed`、`pending-confirmation`；范围排除必须有具名确认和理由 |
| `description` | 缺什么、为什么现有材料不足；只陈述证据状态，不猜测硬件事实 |
| `owner_name` / `owner_role` | 必须具名；仅写部门或“供应商”不算已分派 |
| `due_date` | ISO 日期；未知时保留 `TBD`，不得写成已完成 |
| `expected_artifact` | 需要提交的文件、导出、照片或验证记录及其范围 |
| `resolution_evidence` | 关闭缺口所绑定的路径、SHA-256、版本、确认者和日期 |
| `closed_by` / `closed_at` | 关闭人和时间；材料到达不等于验证通过 |

文件型缺口只有在材料已验证、范围明确、冲突已裁决并绑定不可变版本后才能变为 `verified`。用户直接确认项以本次对话日期、具体陈述和适用范围作为绑定；被用户排除的文件不要求补交。任一状态都只允许相关硬件候选进入原子分类和最终批准流程，不自动批准其成为当前需求基线。
