# R12 历史本地 spec 与实施票据调查

## 边界与结论

本报告只覆盖[material-inventory.tsv](../material-inventory/material-inventory.tsv) 的 `batch_id=R12` 50 行。逐路径使用 `Get-FileHash -Algorithm SHA256 -LiteralPath` 重算，**50/50 与固定清单一致，0 漂移**；完整哈希、字节数、时间与快照 Git 状态以清单为准。每路径以 `git log --follow` 核对形成/修复提交。

依[01 权威规则](../../issues/01-authority-and-classification-evidence-rules.md)、[04 原子粒度](../../issues/04-atomic-requirement-approval-granularity.md)和[06 历史边界](../../issues/06-current-baseline-history-boundary.md)：**`Status: ready-for-agent`、`Status: done`、勾选验收项、测试全绿、修复提交或 spec 标题都只证明内部实施/关闭状态，不是“具名授权人+日期+范围+版本”需求批准。** 50/50 均未附该四要素，不得直接进入当前需求基线。

## 当前适用性与后续原子指针

1. 两份 spec 是 R12 中最可能保存“需求决定摘要”的记录，但均混合原始业务要求、内部派生设计、技术栈和实施验收。后续以每个 user story / Confirmed Domain Semantic / Functional Requirement / 默认值为指针，追回 `mes/docs`、查询目录、ADR 或具名客户/IT 记录，不整份批准。
2. 31 张 Phase 1/Watch 票是实施计划或后续修复；17 张 remediation 是审查发现/回归修复。它们对“当时代码如何实现/修复”有用，但当前适用性须再与现 HEAD 源码/API/schema 核对，不得由 `done`或测试绿推导仍是当前产品需求。
3. 需补齐每个业务语义的具名授权人、日期、适用 MesIngest Phase 1/Watch/调度的范围与绑定版本；将客户 SQL/MES 语义、运维/UI 偏好、API 契约、数据库设计和修复现状分类。合格来源冲突时另建 HITL 票，本调查不提前批准。
