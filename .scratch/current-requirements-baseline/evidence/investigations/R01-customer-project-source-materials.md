# R01 客户、项目协议与原始需求输入调查

## 调查目的与边界

本资产只调查固定材料清单 R01 的 19 个文件，并给出文档级证据分类与后续原子条目定位指针；不批准任何文档或需求进入当前基线，不修改原始材料，也不以文件名、格式、路径、时间、作者元数据、Git 提交者或代码现状代替批准证据。

适用规则来自已解决票据：[确定权威等级与分类证据规则](../../issues/01-authority-and-classification-evidence-rules.md)、[确定需求证据盘点边界](../../issues/02-requirement-evidence-universe.md)、[确定当前基线的最终批准人](../../issues/03-final-baseline-approver.md)、[确定需求确认的条目粒度](../../issues/04-atomic-requirement-approval-granularity.md)、[确定冲突判定与升级规则](../../issues/05-conflict-classification-and-hitl-escalation.md)、[确定当前基线的历史回溯边界](../../issues/06-current-baseline-history-boundary.md)、[确定当前文档集合的快照方式](../../issues/07-current-document-snapshot-method.md)、[固定初始需求证据快照](../../issues/10-capture-initial-evidence-snapshot.md)及[建立当前需求性材料的无损清单](../../issues/11-inventory-current-requirement-materials.md)。尤其：只有具名授权人、日期、范围和具体版本绑定的可核查批准才可赋予权威性；文档是证据载体，不是不可拆分的批准单元。

## 可重复方法

1. 以 [固定材料清单](../material-inventory/material-inventory.tsv) 中 `batch_id=R01` 的 19 行为全集，逐行使用清单 `sha256`、字节数、`last_write_utc` 和快照 `git_status` 固定调查对象。
2. 在工作树重新执行 `Get-FileHash -Algorithm SHA256`；19/19 与清单完全一致。清单中若干文件记为 `untracked`，但当前固定 HEAD `1469d6309d00b0abb792f6cd686aed68286e638e` 的 `git ls-tree`/`git log` 可找到这些路径；本报告保留清单字段，同时把这一状态差异作为快照复核问题记录，不用任一状态推断批准。
3. 对 Markdown 逐行阅读标题、来源声明、版本/用途、待确认项、迁移/生成关系和批准词；“已确认”“客户提供”等无具名人、日期、范围、版本绑定的自述只算待核实声明。
4. 对 DOCX 检查 ZIP/OOXML 包、`docProps/core.xml`、`docProps/app.xml`、正文/页眉页脚、关系、批注和修订标记，并提取完整可见文本；另用文档技能的 `render_docx.py` 尝试渲染全部四份 DOCX。环境缺少 LibreOffice `soffice`，四次均在转换前以 `FileNotFoundError: [WinError 2]` 失败，故没有声称通过页面级视觉 QA；改以 OOXML 结构、嵌入图片和文本检查补充，但版式、页码与手写签章视觉仍保留为缺口。
5. 对两份 PNG 读取像素尺寸和元数据并逐图视觉检查；图内文字只证明图像表达，不证明授权或当前适用。
6. 对每个路径运行 `git log --follow --format='%H|%aI|%cI|%an|%s' --name-status`，只把提交历史用于形成/派生/复制关系；提交作者不是需求批准人。

## 总体结论（文档级，不是基线批准）

- 19/19 文件均能与固定清单内容哈希一一对应；没有发现哈希漂移。
- 主代理验收以 `git -c core.quotepath=false ls-tree -r --name-only 1469d6309d00b0abb792f6cd686aed68286e638e` 对 1,809 条材料清单做全量比对，发现 58 条被清单记为 `untracked` 的路径实际存在于同一固定 HEAD；其中 R01 占 12 条。该差异不改变路径、字节哈希或本批批准证据结论，但会影响历史追溯，已建立[修正初始快照的 Git 状态分类](../../issues/26-correct-initial-snapshot-git-status-classification.md)进行非破坏性勘误。
- 本批没有找到符合治理规则的“具名最终批准 + 日期 + 范围 + 具体版本/哈希”证据，因此不得在文档级判为权威来源，也不得把其中“已确认”标签直接转成基线批准。
- 两个 MES 根部文件是明确的迁移指针；四个 `mes/sources/customer/.../README.md` 是内部来源快照说明；客户交付目录 README 明确 Markdown→DOCX 的 Pandoc 生成关系。这些关系可帮助追溯，但未连接到合格的权威源。
- 项目技术协议、生产指令书和项目分工图可提供项目范围/职责线索；是否有签章、审批页或具名授权需以 OOXML/图像检查结果逐份判断，且即使存在也只限其明确范围与版本。
- 讨论稿和内部 Markdown 大量混合“已确认”“建议实现”“待确认”或推导性内容；后续必须按原子需求拆分，不能整份批准。
