# 决定 QUEUEING 滞留与下单前清积压策略

Type: grilling
Status: resolved
Blocked by: 55

## Question

面对跨批次冲突 `CF-R09-001`：8005 应如何处理本项目 RIoT 订单长期停留在 QUEUEING，以及下发下一单前发现同车仍有 QUEUEING、HELD 或结果未知订单的情况；系统是否、在什么已批准业务原因和证据条件下可以自动 Hold、Cancel 或清理积压，何时只能告警转人工，UC-008 的“RIoT 队列始终 0/1”应作为硬前置还是目标不变量，并如何与单车订单名额、受控业务终止、状态回查和结果未知阻断规则保持一致？

## Comments

- 2026-08-04：用户批准把 UC-008 的 0/1 作为硬下单门禁；长期 QUEUEING、结果未知和 FAILED 均禁止下新单，超时本身不授权自动 Hold、Cancel 或清理。FAILED 通常表示 RIoT 内部故障，须提示管理员解决，不能因已成终态直接再派。
- 2026-08-04：用户补充长期 QUEUEING 常见于车辆距可执行路线过远、车辆状态不可执行、车辆未启用或其它原因；可执行订单通常很快进入 EXECUTING，长轮询周期可能观察不到短暂 QUEUEING。
- 2026-08-04：用户批准自动恢复自身造成且可证明安全的临时 DispatchDisable 与 CAN_RECOVER 软件急停；人工、外部或未知来源以及 CAN_NOT_RECOVER、物理不可移动或安全不可证明时保持阻断。用户指出无人处置可能导致车辆耗尽电量，因此后续仍须决定低电量升级与救援边界。
- 2026-08-04：用户表示存在专门查询长期 QUEUEING 原因的 API，并愿意提供；已新建后续测试票据验证其契约与行为。
- 2026-08-04：用户确认该接口是 RIoT 原生诊断，并批准其只作为诊断依据而非动作授权；只有经目标 build 实测、纳入批准映射并独立核验状态与安全条件的已知原因才可触发自动恢复，未知或变化的自由文本只告警转人工。

## Answer

用户于 2026-08-04 逐项批准以下结论：

1. **UC-008 的“0/1”是8005的硬下单门禁，不是自动清理目标。** 8005 按下单时的 `appointVehicleKey` 保证同车至多一个未明确终结的本项目 RIoT 订单；下新单前必须确认没有占用名额的 QUEUEING、EXECUTING、PAUSED、HELD、HANG、SUSPENDED、优先队列或未知状态订单，也没有未结写调用或结果未知。发现非8005、来源不明或归属不可证明的相关订单时同样阻断并告警，8005不得擅自处理。
2. **正常 QUEUEING 是短暂过渡，QueueingStall 才是异常滞留。** 可执行订单通常很快进入 EXECUTING，轮询周期较长时可能完全观察不到 QUEUEING；长期可见通常表示车辆距可执行路线过远、车辆状态不允许执行、车辆未启用或其它执行前置不成立。长期 QUEUEING 不会自行变成 FAILED，也不能仅凭停留时间推定订单已经失效。
3. **下单前“清积压”改为检查并阻断积压。** 既有 ADR 所说的自动清除 QUEUEING/HELD 不进入当前批准基线。Hold 是保护性暂停，不是队列整理工具；Cancel 是受控业务终止，不是腾出订单名额的通用手段。本票不新增任何自动取消原因，超时、长期 QUEUEING 和低电量均不授权自动 Hold、Cancel、删除、重建或 PriorityExec。
4. **各终态不等同于可再派。** SUCCESS 后仍须确认车辆 IDLE 并重新通过完整派车检查；CANCELLED 或 DELETED 只表示旧订单已终结，后续仍须按其受控终止流程重新判断。FAILED 通常指向 RIoT 内部故障，虽然订单已成终态，但形成车辆级失败订单派车阻断，必须提示管理员诊断并解决，不能直接下下一单。
5. **结果未知始终先对账。** 创建、Hold、Continue、Cancel、DispatchEnable 或急停解除等状态变更的响应不代表后置状态已实现；结果未知时必须使用原业务标识回查，阻断所有依赖该结果的下游动作，不得通过换号重建或盲目重试绕过。
6. **可证明的暂时阻断应自动恢复。** 8005应自动恢复由自身造成、原因已经消除且安全事实可独立证明的临时 DispatchDisable，并逐次回查 ON_LINE；8005自己触发的软件急停在进入 CAN_RECOVER、原原因消除且全部安全条件通过时应自动调用 cancelEmergency 并回查 `emergencyState=OK`。人工、外部系统或来源未知的禁用/急停，以及 CAN_NOT_RECOVER、物理不可移动或安全不可证明的情况保持阻断并转人工。该批准不自动扩展到 OrderContinue、HangContinue 或其它未具名恢复动作，它们继续遵守既有独立规则。
7. **RIoT 原生 QUEUEING 诊断只提供证据，不提供动作授权。** 用户指定 `GET /api/task/vehicles/queryVehicleNotAssignOrder/{deviceKey}/{orderKey}` 作为长期 QUEUEING 原因诊断；本地静态契约显示其返回自由文本 `reason` 和字符串数组 `suggestList`。8005须保留原始返回，只有经目标 build 实测、纳入项目批准映射并通过独立状态与安全核验的已知原因才可触发相应自动恢复；未知、变化或无法独立验证的文本只告警转人工，绝不直接执行 `suggestList`。
8. **低电量只触发防御性升级，不产生越权恢复。** 既有充电触发阈值和最低接单电量阈值继续承担正常能源调度与候选过滤职责；订单阻断期间电量下降只提高告警等级和响应紧迫度，不授权取消 QUEUEING 订单、改派充电、重建订单或绕过安全门槛。若诊断指向8005缺陷或原因未知，必须保留订单、诊断和上下文作为故障现场，不能用自动防御掩盖 bug；确实无法安全移动时车辆就不应移动。
9. **后续证据单独验证。** 已创建[补齐并验证 QUEUEING 长期滞留原因诊断 API](60-supply-and-validate-queueing-stall-reason-api.md)，绑定 riot-behavior-lab 的 RIoT build `2.2.0.30`，验证 `orderKey` 口径、原因文本稳定性、建议含义、错误/超时、结果新鲜度及 GET 是否确实无副作用。该测试只补充证据，不自动扩大白名单或降低本票门槛。

以上结论解决 `CF-R09-001`：8005以硬门禁、诊断、具名安全恢复和人工升级维持单车订单边界，不以自动清积压维持表面上的队列 0/1。
