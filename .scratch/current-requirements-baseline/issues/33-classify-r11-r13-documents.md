# 建立 R11–R13 文档级证据分类账

Type: task
Status: resolved
Blocked by: 23, 24, 25

## Question

依据已完成的 R11–R13 调查报告、无损清单和既定权威证据规则，为这些批次中的每份材料建立统一的文档级分类记录：固定路径与哈希、材料角色、来源类型、当前适用范围、历史/派生关系、批准四要素状态、可否进入原子需求提取，以及必须保留的证据或冲突指针；如何严格区分外部数据/接口契约、项目需求、SDK 或本地设计、历史实施票据和仅证明观察现状的快照？

## Answer

已把 R11–R13 的逐件调查结论归一到统一的[文档级证据分类账说明](../evidence/document-classification/README.md)，规范化主数据为 [R11–R13 TSV 分类账](../evidence/document-classification/R11-R13-document-evidence-ledger.tsv)，并提供公式驱动的 [XLSX 审阅副本](../../../outputs/019fc6b2-9251-7a80-a62b-af9901373337/R11-R13-document-evidence-ledger.xlsx)及[重建/核验脚本](../evidence/document-classification/build-and-verify-r11-r13-ledger.ps1)。

分类账以无损清单中 R11–R13 的 87 个固定路径为全集，逐条固定完整 SHA-256、字节数、清单原始 Git 状态、勘误覆盖后的有效 Git 状态和材料角色，再记录文档分类、来源类型、当前适用性、历史/派生关系、批准四要素、原子提取路由以及证据/冲突指针。覆盖为 R11 11、R12 50、R13 26；重建和独立 `-VerifyOnly` 均验证 87/87、零漏项、零重复、零当前哈希漂移，并正确应用 R11 一条、R13 三条 Git 状态勘误。

批准边界保持失败式隔离：87 份材料均未同时建立具名批准人、日期、范围与版本绑定，四要素字段全部为 `not-found`，`document_approval_state` 全部为 `not-approved-by-this-classification`；脚本会在分类过程擅自升级批准时失败。24 份材料仅被路由到后续原子拆分、补证、冲突裁决和显式批准：R11 6、R12 2、R13 16，这不代表它们已经是当前需求。

R11 已把客户/外部数据候选、派生查询或应用设计、验收条件、索引/生成视图和限定环境现状分别路由；工厂清单的运行授权与需求批准不再混用。R12 只有两份混合 spec 可按 story/语义继续追源拆分，其余 48 张实施、评审或修复票只保留为实施史、偏差或回归证据，不能独立生成需求。R13 的 14 份静态 schema 必须先绑定受控环境和 RIoT 版本，再按 operation 进入 API 白名单与安全批准；4 份 SDK schema 字节副本去重，normalized 输入和 SDK 设计不反推项目需求；两份供应商 PDF 继续只保留身份、哈希和来源史，不提取内容。

XLSX 的 `Summary` 公式读回为总记录 87、未由分类批准 87、候选路由 24、历史实施/修复隔离 48、待绑定 schema 14、供应商排除 2、Git 状态勘误 4；`Ledger` 提供冻结表头、筛选和按语义着色。两张表均完成视觉检查，成品重新导入后摘要、首尾记录和公式错误扫描全部通过。此票不改变业务领域词汇或决定，因此未修改根 `CONTEXT.md`；下一张 frontier 票为“合并并核验文档级证据分类账”。
