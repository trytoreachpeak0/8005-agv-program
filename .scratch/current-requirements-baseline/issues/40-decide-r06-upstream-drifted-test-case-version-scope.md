## Answer

用户于 2026-08-03 确认采用“旧稿保留为历史证据、另建当前候选”的双轨处理，且这一处置决定不等于批准当前 `FR-016` 或新验收语义。

- `TC-044`～`TC-047` 原始文件不修改，继续以总账已固定的路径、SHA-256 和 Git 身份保留；它们只是未批准的历史验收草案，不得进入当前基线候选。
- 四份 TC 与它们当时名义验证的旧 `FR-016` 共同绑定到 Git 提交 `ecd0fd89c51c6602eda13f37b7c2e9fe181e5aad`；其对应 blob 分别为 `2ceef789d1341c3e6b21d98ae7da68e2eaacefc4`、`4beb9c1dc14c2ac6b12ca3491481b3d323b875c7`、`85f49edd3a7652b7fc8f039df5c0e757c8d63392`、`05e3f0e21c415cee601479dbe7b8b1c585b032a1`，旧 `FR-016` blob 为 `c0cbfa4bfa3a61a9ace63315dbb4d757e0a8438f`。
- 后续“拆分并分类仓位、硬件与车队验收的原子候选”须依固定当前证据另建新身份的验收候选，覆盖“立即禁用”、“待禁用”、“启用不覆盖车载硬件不可操作”和“批量独立结果”四类语义；不复用 `TC-044`～`TC-047` 的身份，不从较新时间或文档外观推定正确性。
- 新候选只进入原子拆分、去重、范围核对、冲突路由和后续显式批准；未经用户的条目级批准不得进入首个当前需求基线。

本决定只固定证据与候选的版本范围，没有形成新的业务领域词汇，因此不修改根 `CONTEXT.md`。
