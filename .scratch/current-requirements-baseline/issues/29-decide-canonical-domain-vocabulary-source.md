# 确定领域词汇唯一入口与旧术语表关系

Type: grilling
Status: resolved
Blocked by: 20

## Question

根 `CONTEXT.md` 与 `glossary/terminology-glossary.md` 应采用怎样的唯一入口、替代或分工关系；当两者对同一术语、范围或规则不一致时，哪一具体版本由谁批准为当前领域语言，旧内容如何保留历史追溯？

## Answer

根 `CONTEXT.md` 是本仓库唯一的现行领域语言入口，也是 Matt Skills 保持不变的运行时词汇入口；`glossary/terminology-glossary.md` 不再作为平行规范，只作为历史证据保留。成为唯一入口只确定读取位置和工作语言，不会把文件中的领域定义、业务规则或设计决定自动批准为当前需求。

当前 `CONTEXT.md` 快照（SHA-256 `221B4E6942BA0FB0C12277A2E7C3311414B979B2AC90280D6400A805A0F937DE`，Git 提交 `493ac5a89cb89daf1f8c090ef6091b8d006180be`）仅是过渡期工作词汇与迁移来源，不整份批准。首个正式“当前领域语言”须清除实现细节、拆开需要独立判断的领域定义与规则，并由本次基线最终批准人——用户本人——批准绑定具体完整 SHA-256 的新版本。

`CONTEXT.md` 采用双层身份：Matt Skills 立即把它作为当前工作词汇源；需求基线仍逐条判断其中内容的来源、范围、冲突和批准状态。Skills 使用某个词不构成对同文件中规范性语句的需求批准。

术语维护必须形成以下闭环：发现新词、旧词或错误词后，先通过 `grilling` 与 `domain-modeling` 澄清概念；待确认提案只留在票据中；用户批准具体名称与一至两句定义后，立即按 Matt Skills 的 `CONTEXT.md` 格式更新原路径文件。旧称或禁用同义词在仍有识别价值时记入 `_Avoid_`，不保留两套同时有效的定义。每次生效修改都以 Git、治理票据、批准记录和完整 SHA-256 留痕，下游 `to-spec`、`to-tickets`、`tdd` 等 Skills 继续读取同一路径；后续发现冲突时重新回到上述澄清与批准环节。

`CONTEXT.md` 只保存项目特有的领域词汇及紧凑定义。业务流程、权限、安全约束、协议或实现方案不因当前混在文件中就成为词汇；后续清理时必须无损路由到需求条目或 ADR，并保留来源指针，不能静默删除。只有满足难以逆转、缺少背景会令人意外且存在真实取舍的决定才另建 ADR。

当 `CONTEXT.md` 与旧术语表不一致时，Skills 的日常命名以 `CONTEXT.md` 为准；但领域定义、业务规则或设计决定不采用“较新文件自动覆盖旧文件”，而由用户按原子条目批准、否决或改写。旧术语表当前快照（SHA-256 `5C7DCA1FE4E0C96EB00936185660725C64BB055C003E1BC3841B15B40D39E4E6`）保持原路径和原内容不变，结合 Git 历史作为历史证据；其被替代关系只写入治理记录。

保持整套 Matt Skills 正常工作并形成“澄清—批准—更新词汇—下游消费—冲突反馈”的闭环，是本地图的硬约束。任何后续决定若会改变根入口、使待确认词汇直接生效、绕过 `domain-modeling` 的即时更新，或让下游 Skills 无法取得一致语言，都必须停止并升级给用户确认。
