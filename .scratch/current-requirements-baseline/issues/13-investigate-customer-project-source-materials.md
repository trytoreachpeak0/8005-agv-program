# 调查客户、项目协议与原始需求输入

Type: research
Status: resolved
Blocked by: 11

## Question

对无损清单 R01 批次中的客户材料、项目协议、需求讨论稿、MES 需求确认和来源附件，逐份核实来源身份、形成/捕获时间、版本与重复关系、具名批准证据、批准适用范围及当前项目版本适用性，并记录缺失证据；如何形成文档级证据分类，而不把文件名、格式、时间或存放位置当成权威性？

## Answer

已完成 R01 的 19/19 份材料调查，并形成逐文件证据记录：

- 19 份当前文件均与固定清单路径及 SHA-256 一致，无哈希漂移。
- 没有任何一份材料包含符合既定规则的“具名最终批准人、日期、批准范围和具体版本/哈希”完整证据，因此本批不能在文档级批准任何当前需求；“已确认”“客户提供”“正式”等无绑定证据的自述仍须追溯。
- 已核实迁移指针、客户 SQL 快照说明、Markdown→DOCX 生成关系、DOCX 内嵌图片、讨论稿版本差异及疑似截图派生关系；它们提供追踪链，但不会自动赋予上游或下游权威性。
- 技术协议缺签字盖章/生效记录，生产指令书缺签发审批，讨论稿明确为非合同草稿，其余内部汇总和方法笔记均缺合格来源与批准链；报告已逐份给出文档级分类、当前适用性、缺失证据和后续原子条目指针。
- 两份 PNG 已视觉检查；四份 DOCX 因环境缺少 LibreOffice `soffice` 无法完成页面渲染，已改做 OOXML、完整可见文本、属性、修订/批注及嵌入媒体检查，并明确保留版式、页码与手写签章视觉缺口。
- 主代理全量验收另发现材料清单有 58 条 Git 状态分类与固定 HEAD 不一致，其中 R01 占 12 条；这不影响本票哈希与批准结论，但已建立独立勘误任务，避免后续遗漏 Git 历史。
