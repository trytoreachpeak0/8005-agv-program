# 决定基线版本的存储与变更治理形式

Type: grilling
Status: resolved
Blocked by: 08

## Question

首个当前需求基线及后续版本应采用什么文件布局、版本编号、不可变发布标识、当前版本指针和变更提交流程，才能同时满足“单独需求文档可直接使用”和“所有历史批准版本可恢复”？

## Answer

这是 2026-08-03 由用户在本次 Codex 对话中重新作出的基线治理决定，不是恢复出的历史事实。用户逐项答复“可以”，并最终确认已经达到共享理解。

### 存储模型

- 使用独立、不可修改的版本快照与唯一当前版本指针。
- 当前指针文件为 `requirements/current-baseline.md`。
- 已批准版本保存在 `requirements/baselines/`，首个文件为 `current-requirements-v1.0.0.md`。
- 已批准版本发布后不再修改；后续需求变化生成新的候选版本，批准后发布为新文件。
- 当前指针只指向最新批准版本；候选版本获批前，当前指针继续指向原批准版本。

### 版本编号

- `v1.0.0`：首个批准基线。
- 次版本：只增加新需求，且不修改、废弃或否定既有需求，例如 `v1.1.0`。
- 主版本：修改既有需求含义、废弃需求、改变适用范围，或使旧基线合规结果失效，例如 `v2.0.0`。
- 补丁版本：只修正错字、链接、证据定位或元数据，不改变需求含义，例如 `v1.0.1`。
- 未批准版本使用 `-draft.N` 后缀，且不能成为当前基线。
- 任何可能改变需求含义的修改都不能按补丁版本处理。

### 正式发布条件

一个版本只有同时具备以下内容才是正式发布：

1. 完整的版本化需求文件。
2. 该文件的 SHA-256 和对应 Git commit。
3. 带说明的 Git tag，格式为 `requirements-baseline-v<version>`。
4. 批准记录，包括批准人、批准时间、适用范围，以及批准所依据的票据、会议记录或等价证据。

缺少任一项的内容只能是候选稿，`requirements/current-baseline.md` 不得指向它。

### 变更门禁

以后每项需求变更都按以下顺序推进：

`变更提案 → 来源与适用范围验证 → 影响和冲突分析 → 必要的 HITL 决策 → 最终批准人批准精确差异 → 生成新版本 → 更新当前版本指针`

每个变更提案至少记录操作类型（新增、修改或废弃）、相关需求 ID、原内容与拟变更内容、理由、来源、适用范围、证据、跨车载端/服务端/共同协议及其他需求的影响，以及目标基线版本。未批准提案与当前批准基线严格分开。

### 需求身份

- 每条批准需求取得永久、无业务分类含义的编号：`REQ-0001`、`REQ-0002`，依此递增。
- 车载端、服务端、共同协议或跨域等信息记录在独立 `Scope` 字段，不编码进需求 ID。
- 文件移动、标题调整和证据链接修正不改变需求 ID。
- 普通语义修改保留原 ID，并记录发生变化的基线版本。
- 本质替代旧要求的新要求取得新 ID，并以 `Supersedes` 指向旧 ID；旧 ID 标记为已废弃但不删除。
- 已分配 ID 永不回收或复用。

### 基线条目内容

每条需求同时保存：

- `Current Requirement`：后续开发与 spec 必须遵守的唯一规范文本。
- `Evidence`：原始文档摘录、路径、精确位置、版本、哈希、批准和必要历史证据。

原始表述明确且无冲突时，规范文本可以直接采用原文。需要合并、消歧或重新措辞时，AI 只能提出候选文本；该文本必须标为“本次重新作出的决定”，并经最终批准人逐条批准后才能成为规范文本。原始材料始终保持不变。

Evidence: 本次 Codex 对话记录，2026-08-03；用户对存储模型、版本编号、正式发布条件、变更门禁、永久需求 ID、双层条目结构分别答复“可以”，并对汇总答案答复“可以”。
