# 决定空闲返回、停靠点资格与调度竞争边界

Type: grilling
Status: open
Blocked by: 63, 82

## Question

普通空闲返回使用的停靠点是否必须具备专用类型、能否复用业务站点；搬运、充电和返回停靠点同时竞争一辆车时如何原子取得处理权；启用后是否立即补触发、导航/监听失败如何恢复，以及它与票据 62 已批准的地图等待点集合和预占规则是同一资源模型还是不同用途的受控集合？

## Evidence rows

`R03-A2993`、`R03-A3049`、`R03-A3072` 及复核账中由 `R03-A3030` 重构出的业务问题。

## Comments

- 2026-08-06：用户确认普通空闲返回复用 `MapWaitingPointPool`，不建立平行的“停车点”资源模型；同时澄清等待点只供已结束当前用途、没有下一业务目标且需要进入待命的车辆使用。正常任务并非每完成一步就返回，正常充电也并非达到完成阈值就返回；充电失败清桩时，等待点只是自动腾空原桩的优先去向之一，授权人员确认车辆已移至其它安全位置也可完成清桩。该术语定义已即时同步到根 `CONTEXT.md`。
- 2026-08-06：用户确认充电失败清桩的领域含义是把车辆与原充电桩安全物理分离，而不是清桩后立即恢复桩位资格或自动派另一辆生产车试桩。原车与原桩在根因未知时分别保持暂停并独立核验、独立恢复；若项目需要用其它车辆验证桩，应作为受维护人员授权和现场安全门禁约束的独立诊断能力另行决定，不能冒充普通调度。`ChargeFailureStationClearance` 已据此同步收紧到根 `CONTEXT.md`。
- 2026-08-06：用户先确认等待点采用“地图级候选 + 最终逐车绑定”，随后在具体场景中修正该结论：每个等待点默认允许同一 RIoT 地图内的全部车辆；只有配置了指定车辆名单时才收窄为白名单，名单外车辆不得选择或排队等待该点。地图一致、路线可达、占用、预占和数据新鲜度门禁始终保留。根 `CONTEXT.md` 已同步用 `WaitingPointVehicleScope` 替换先前短暂写入的强制逐车绑定定义，后者不再是当前结论。
- 2026-08-06：用户纠正站点角色来源：RIoT 地图只提供普通站点，等待、业务和充电用途由 8005 定义；RIoT 支持多个站点坐标重合，因此 8005 可能用不同站点身份分别承载不同角色，而无需让一个站点承担多个角色。但受控 `GET /api/task/vehicles` 只返回单值 `currentMap + currentPosition`，现有证据没有验证车辆处于重叠坐标时返回哪个站点 ID。该事实直接影响到站、占用与角色识别，已毕业为“验证 RIoT 重叠站点的车辆当前位置身份语义”，本票释放认领并等待其实测结论。
