# 决定空闲返回、停靠点资格与调度竞争边界

Type: grilling
Status: resolved
Blocked by: 63

## Question

普通空闲返回使用的停靠点是否必须具备专用类型、能否复用业务站点；搬运、充电和返回停靠点同时竞争一辆车时如何原子取得处理权；启用后是否立即补触发、导航/监听失败如何恢复，以及它与票据 62 已批准的地图等待点集合和预占规则是同一资源模型还是不同用途的受控集合？

## Evidence rows

`R03-A2993`、`R03-A3049`、`R03-A3072` 及复核账中由 `R03-A3030` 重构出的业务问题。

## Answer

用户于 2026-08-24 明确批准第一轮全部推荐值，并指示本票后续分支继续采用推荐值。结合既有 `MapWaitingPointPool`、充电与派车决定以及被取消实测留下的证据边界，本票按以下规则封闭：

1. **首版只允许专用等待点。** 等待点必须以明确的 `RIoT 地图 + 站点`登记，不得同时承担业务或充电角色，也不得与业务站或充电站共享物理坐标。不同站点身份即使坐标相同也不获准使用，因为已取消的实测没有证明单值 `currentPosition` 能稳定区分其角色。等待点继续使用既有 `WaitingPointVehicleScope`：默认对同图全部车辆开放，配置白名单时仅白名单车辆合格。
2. **所有用途通过唯一 VehiclePurposeClaim 原子争用车辆。** 已开始或结果未知的搬运、充电、清桩/维护和空闲返回保持现有占有，不允许新用途抢占。没有现有用途时，达到 `MandatoryChargeEntryThreshold` 的车辆先进入强制充电且不得接普通搬运或空闲返回；电量允许时先执行 `TaskFirstDispatchSelection`，只有没有合法搬运用途时才评估空闲返回。空闲返回不预留未来车辆，也不压过尚未形成承诺的搬运或强制充电。
3. **IdleReturnEligibility 是严格兜底资格。** 车辆须已结束当前用途、没有下一业务目标、活动或结果未知的 RIoT 订单、充电/清桩/维护门禁，电量高于强制充电入口阈值，并且本轮任务优先派车没有选中该车。启用空闲返回或激活新版等待点配置时，立即重评所有当前满足这些条件的车辆；忙碌或受阻车辆不改变当前状态，只在以后首次满足资格时评估。停用功能只阻止新承诺，不取消或改写既有返回订单。
4. **车辆与等待点必须原子取得后才形成 IdleReturnCommit。** 服务端基于同一份新鲜快照同时取得该车的 IDLE_RETURN VehiclePurposeClaim 和具体等待点的 WaitingPointExclusiveClaim；任一取得失败都不形成承诺。形成承诺后，返回成为车辆当前已承诺下一站，沿用 `PlannedStopMutationBoundary`，不得因后来出现搬运任务或其它车辆优先级变化而取消、换点或抢占；新任务等待本次返回到点收敛后重新派车。
5. **等待点实行从在途预占到在点占用的连续单车独占。** 选择候选前必须重新核验当前地图、专用角色、车辆适用范围、身份有效、RouteCost 可达、未被其它车辆占用或预占以及数据新鲜度；候选计算不等于取得资源。到点后 WaitingPointExclusiveClaim 从预占转为占用，车辆在完整收敛后释放 IDLE_RETURN VehiclePurposeClaim 并可再次参加搬运或强制充电选择，但等待点独占只有在确认车辆实际离点后才释放，不能在下达离点订单时提前释放。
6. **空闲返回只使用已批准的通用单段移动能力。** 生成的 RIoT“一键停靠”和 `parkConfig` 客户端不构成授权，现有白名单也明确禁止这些调用。空闲返回必须通过 `RoutineOrderCreationCall`，使用稳定 upperId、已核验车辆/地图/目标站点和 RIoT 单车订单名额创建 `byDefaultMissions` 单段 move，并完整继承 `RIoTRetryReconciliation`；结果未知时保持车辆、目标点、用途占有和等待点独占，不换号、不换点、不重复建单、不表示已经出发或到达。
7. **到点必须由一致证据组合确认。** 单值 `currentPosition` 不得独自证明角色到达；至少要求本次稳定 upperId/订单的目标与预占等待点一致、车辆 `currentMap + currentPosition` 精确匹配该专用站点、车辆已停止、订单达到相容的已确认终态，且全部证据新鲜无冲突。任一字段缺失、过期或冲突都保持在途承诺并对账，不按超时释放车辆或等待点。
8. **失败按“是否可能已有订单或仍在运动”分流。** 首次外部建单前重新核验失败，或明确拒绝且已证明没有活动订单、车辆未开始移动时，可以释放本次 VehiclePurposeClaim 与 WaitingPointExclusiveClaim，车辆回到重新评估；只有在取得新鲜资格/路径变化后才能开始新尝试。建单结果未知、订单存在、车辆可能移动、导航进入未知/HANG 或监听丢失时，必须保持原承诺和独占，按通用订单规则对账、告警并在必要时转人工，不盲选其它等待点。已确认失败只可在排除原失败点并重新通过全部门禁后建立新的独立承诺。
9. **没有合格等待点时进入 IdleReturnPending。** 车辆原地等待并形成去重告警，不猜测业务站、充电站、同坐标站或临时最近点，也不取得车辆用途或等待点独占，因此后续合法搬运或强制充电仍可先取得车辆；只在等待点释放、配置/适用范围、车辆状态、地图或路径等有效事实变化后重评。充电失败清桩继续保留既有人工安全位置闭环，不因本票被强制要求必须到等待点。
10. **配置和拓扑变化不破坏既有引用。** 被删除、停用或改角色的等待点立即停止接受新承诺，但已经预占、在途或在点占用的记录保留到车辆安全离点并完成对账；不得通过配置变更取消订单、释放未知资源或让第二辆车进入。所有承诺、预占、建单、对账、到点、离点、失败与人工处置均保留车辆、地图、站点、配置版本、订单、时间和结果证据。

代码核对只发现生成的 RIoT 停靠相关客户端，没有现成的 8005 空闲返回产品行为；它们既不是当前需求证据，也不得绕过既有 API 白名单。本票只固定需求和领域边界，不选择并发锁、存储、重试次数、界面或其它实现机制。已批准术语同步到根 [`CONTEXT.md`](../../../CONTEXT.md)。

## Comments

- 2026-08-06：用户确认普通空闲返回复用 `MapWaitingPointPool`，不建立平行的“停车点”资源模型；同时澄清等待点只供已结束当前用途、没有下一业务目标且需要进入待命的车辆使用。正常任务并非每完成一步就返回，正常充电也并非达到完成阈值就返回；充电失败清桩时，等待点只是自动腾空原桩的优先去向之一，授权人员确认车辆已移至其它安全位置也可完成清桩。该术语定义已即时同步到根 `CONTEXT.md`。
- 2026-08-06：用户确认充电失败清桩的领域含义是把车辆与原充电桩安全物理分离，而不是清桩后立即恢复桩位资格或自动派另一辆生产车试桩。原车与原桩在根因未知时分别保持暂停并独立核验、独立恢复；若项目需要用其它车辆验证桩，应作为受维护人员授权和现场安全门禁约束的独立诊断能力另行决定，不能冒充普通调度。`ChargeFailureStationClearance` 已据此同步收紧到根 `CONTEXT.md`。
- 2026-08-06：用户先确认等待点采用“地图级候选 + 最终逐车绑定”，随后在具体场景中修正该结论：每个等待点默认允许同一 RIoT 地图内的全部车辆；只有配置了指定车辆名单时才收窄为白名单，名单外车辆不得选择或排队等待该点。地图一致、路线可达、占用、预占和数据新鲜度门禁始终保留。根 `CONTEXT.md` 已同步用 `WaitingPointVehicleScope` 替换先前短暂写入的强制逐车绑定定义，后者不再是当前结论。
- 2026-08-06：用户纠正站点角色来源：RIoT 地图只提供普通站点，等待、业务和充电用途由 8005 定义；RIoT 支持多个站点坐标重合，因此 8005 可能用不同站点身份分别承载不同角色，而无需让一个站点承担多个角色。但受控 `GET /api/task/vehicles` 只返回单值 `currentMap + currentPosition`，现有证据没有验证车辆处于重叠坐标时返回哪个站点 ID。该事实直接影响到站、占用与角色识别，已毕业为“验证 RIoT 重叠站点的车辆当前位置身份语义”，本票释放认领并等待其实测结论。
- 2026-08-24：用户取消“验证 RIoT 重叠站点的车辆当前位置身份语义”，该实测不再作为本路线的前置条件。现有证据缺口继续有效：本票不得依赖单值 `currentPosition` 区分同坐标的等待、业务或充电站点身份，必须在不假设该字段具备角色判别能力的前提下决定站点角色、到达/占用证明和 fail-closed 边界。
