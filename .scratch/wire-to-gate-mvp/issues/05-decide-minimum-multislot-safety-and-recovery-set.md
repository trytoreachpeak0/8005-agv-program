# 决定 MVP 多仓容量、安全联锁与异常恢复最小集

Type: grilling
Status: resolved
Blocked by: 01, 04

## Question

哪些多仓容量、一篮一仓、批量开锁、占用与锁闭检测、StationOperationGuard、PreDepartureSafetyCheck、断联收尾、指令幂等、OnboardExecutionJournal、重启对账和硬件状态未知处理，是即使单 Demand MVP 也不得裁减的安全与可恢复下限？

同时需明确哪些复杂补偿、管理界面、多任务组合和非必要运营能力可以延后，但延后不得把不可解释的物理状态猜测为安全或完成。

## Answer

用户于 2026-08-25 明确回复“全部采用推荐值，然后/handoff”，逐项采用本票 Q1、Q2 的推荐方案，并确认以下单 Demand、多仓 `WIRE_TO_GATE` MVP 安全与恢复下限：

1. **MVP 保留完整八仓模型，不把“单 Demand”错误收窄为“单仓”。** 当前车型继续使用固定的 1～8 号物理仓位以及已批准的版本化硬件事实：DO1～DO8 对应 1～8 号仓位开锁，DI1～DI8 对应锁闭反馈，DI9～DI16 对应仓内光幕，开锁输出采用 500 ms 脉冲及已批准信号极性。全部八仓都必须具有稳定的 `AGV 标识 + 物理仓位号` 身份；未配置、能力缺失、不可操作、版本/指纹不明或安全事实无效的仓位仍保留原身份和业务事实，但不得参加分配。
2. **每个 Demand 的实际占用仓数由冻结的 ExpectedBasketCount 决定。** 沿用票据 04 已批准来源：ControlServer 以 Sublot 执行只读 `SUBLOT_BOX_COUNT`，取得正整数 `MAX_BOX_COUNT`；再用 AcceptedDemandSnapshot 中冻结的 `PACKAGE` 唯一匹配已批准 `mes/reference/package-basket-capacity.csv`，取得正整数 `capacity = max_boxes_per_basket`，并计算 `ExpectedBasketCount = ceil(MAX_BOX_COUNT / capacity)`。本车型必须满足 `1 <= ExpectedBasketCount <= 8`；容量规则未覆盖、计算失败、结果超过当前合格仓位数或任一资格不明时，都在 `OperationCommitPoint` 前整批阻断，不使用默认容量、人工估算、部分装货或后补仓位。
3. **一篮一仓、匿名花篮、完整集合和批量执行不可裁减。** 服务端一次选择、预留并冻结恰好等于 ExpectedBasketCount 的完整目标仓位集合；每个物理仓最多一个花篮，每个花篮占一个仓，不建立单篮身份，不允许替代目标仓位、一仓多篮或把逐仓物理成功解释成部分 LoadBatch 成功。服务端掌握 Demand、Sublot、完整仓位集和业务提交；OnboardHmi 独占 IO、门序列和实时机构安全，按受控 IO 模块集合批量开锁。
4. **StationOperationGuard 覆盖全部站内物理风险窗口。** 服务端在允许 Sublot 提交或下发仓位操作前先证明车辆停稳并持久化 `StationOperationGuard`；它覆盖等待输入、服务端解析、批量装货、批量卸货、纠错、异常暂停、补偿和恢复。只有车载端报告操作已终结，且最新物理事实证明全部相关仓门锁闭、全部开锁输出复位、没有未收敛操作后才可解除；服务端重启、双端断联或保护状态不明时不得推定已解除。Guard 期间所有自动、人工、充电或恢复移动入口都必须被同一门禁阻断。
5. **仓内光幕只形成三态占用事实，锁反馈才证明仓门安全。** `SlotOccupancyState` 只有 `OCCUPIED`、`EMPTY`、`UNKNOWN`；仓内光幕不是人员安全光幕，也不直接触发车辆急停。8005 没有独立门磁，只有有效锁反馈明确证明锁闭才满足仓门安全；未锁闭、反馈无效或未知均按不安全处理。装货必须闭环到 `OCCUPIED + 锁闭 + 开锁输出已复位`，卸货、取消清空和补偿必须闭环到 `EMPTY + 锁闭 + 开锁输出已复位`。关门后读到明确相反占用态时自动再次弹锁并继续原目标态闭环；`UNKNOWN`、锁反馈无效、输出复位不明或 IO 失联时暂停并进入恢复，人员按钮、管理员身份和固定重试次数均不能覆盖事实。
6. **批量部分结果只用于恢复和审计，业务承诺仍保持正确原子边界。** OnboardHmi 可靠报告完整目标集合的逐仓完成、失败或未开始结果，并先写入本地执行日志；装货只有全部目标仓达到装货闭环且安全状态有效后才自动整体提交 LoadBatch。卸货允许已证明为空的仓位独立清除业务绑定，但 `StationOperationGuard` 保持到完整目标集合收敛；整个 Demand 的本地成功仍须遵守票据 04 的原子事务：`UnloadBatch + StopClosureCommit + Demand 成功终态 + TransportDemandCompletion`，不得以部分卸空、PDA/MES 操作或后续移动结果提前或回滚成功。
7. **指令持久接受、幂等和不可撤销承诺点不可裁减。** 服务端首次发送 `SlotOperationCommand` 即到达 `OperationCommitPoint`；在此之前必须最终校验并冻结 Demand、Sublot、ExpectedBasketCount、装卸类型、完整目标仓位集、执行方式和业务预留。OnboardHmi 只有先把完整指令和 `SlotOperationAttemptId` 持久化到 `OnboardExecutionJournal` 后才能回复 accepted ACK 或产生 IO 副作用。ACK 或发送结果未知时只能以原尝试 ID、原 MessageId 和相同内容重发或查询；相同尝试和内容返回既有 ACK、进度或结果，不重复开门，相同尝试携带不同内容必须拒绝。
8. **断联只安全收尾当前开锁集合，不扩大物理副作用。** 双端通信中断时，尚未发送开锁的操作立即暂停；已经发送或发送结果未知的 `ActiveUnlockSet` 只执行 `SafelyFinishActiveUnlockSet`。跨 IO 模块发送途中，尚未发送的模块组不得继续开锁，也不得开始下一仓位集合、自动取消、自动超时清理或盲目重发 DO。装货收尾要求当前集合逐仓达到 `OCCUPIED + 锁闭 + 输出复位`，卸货收尾要求 `EMPTY + 锁闭 + 输出复位`；随后保持 Guard 并等待重连对账和服务端明确授权。
9. **重启与重连只能从唯一可证明恢复点继续。** OnboardHmi 重启后先读取 `OnboardExecutionJournal`，再重新读取实时锁反馈、光幕、输出回读和 IO 在线性；实时 IO 是当前物理权威，关机前观测只作比较。只有日志阶段、实时 IO 和服务端操作事实共同导出唯一安全结论、唯一逐仓结果语义和唯一合法下一步时，才形成 `ProvenRecoveryCheckpoint`。开锁已发但反馈未知时不得重发开锁，只能安全收尾原集合；日志缺失/损坏、状态 UNKNOWN、多种可能解释或任一冲突都进入 `VehicleRecoveryRequired`。重连必须完成连接会话隔离、能力同步、RecoveryStateReport、原尝试结果补报和服务端 `SessionReadiness`；只有明确 `READY` 后才可恢复业务，通信恢复本身不构成授权。
10. **每次移动均须新的发车安全检查，并在安全撤销时自动介入。** OnboardHmi 根据全部仓门锁闭、开锁输出复位、IO 在线有效、仓位操作终结和无致命硬件故障计算 `DepartureSafe`；服务端或调度独占 RIoT 移动决定。每次准备移动前必须取得新的 `PreDepartureSafetyCheck`，检查 ID、观测时间、安全版本和短有效窗口均须有效，不能复用旧 OperationResult。移动请求期间安全从 true 变为 false 时必须可靠上报并自动介入；已知本系统订单先 `OrderHold` 并核验停车，来源未知或非本系统订单按既有分层处置，不能只告警或自动续行。
11. **仓门异常、停车证明和急停采用现有严格边界。** 授权正常装卸开门只维持 Guard；授权外仓门未能证明锁闭而车辆已有停稳证明时，阻断移动并高优先级告警；车辆仍在移动或停稳证明失效时立即自动调用 `triggerEmergency`，不等待固定超时、不得以 Cancel 替代停车。订单 `HELD`、急停状态或单次查询均不能单独证明停稳，必须同时具有新鲜明确的非移动状态、连续稳定位置和期间无新移动迹象。急停未确认前按受控退避重试和回查，远程结果未知且无停稳证明时保持最高优先级现场处置；急停不取消 Demand、订单、货物或仓位绑定，解除后也不自动继续移动。
12. **故障事实采用“疑似阻断—确认隔离”，时间和模糊症状不等于硬故障。** 离线、通信中断、导航失败、单个订单 FAILED 和持续时间只形成 `SuspectedVehicleFaultBlock`，立即阻止新派车、保护当前订单并告警；当前只有新鲜的 `emergencyState=CAN_NOT_RECOVER` 或具备异常恢复权限人员记录的具体现场事实可以确认 `VehicleFaultIsolation`。进入阻断后对本项目当前订单调用并回查 OrderHold；结果未知或无法证明停车时按安全联锁规则升级。任何未知或冲突不能靠身份强解。
13. **部分装货或载货故障必须保留原业务与物理绑定。** 任一目标仓位发生开锁、机构、通信或关键反馈故障时，车载端停止尚未发送的开锁组，不分配替代仓位；服务端保留原 DemandId、SlotOperationAttemptId、完整目标集合、ProvisionalLoadState、全部预留、逐仓事实和 Guard。已有装货事实或货物状态未知时进入 `FaultedVehicleCargoHold`，继续绑定原车辆、Demand、仓位、产品和订单；等待时间只升级告警，不能自动取消、改派或选择恢复路径。
14. **采用 Q1 推荐值：MVP 纳入最小产品化 ExceptionRecoverySession。** 会话由维护管理员或系统管理员以个人账号一次认证建立，只绑定一名处置人员、一个事件、一台车辆及固定任务/仓位范围；断联期间不得扩围，人员交接、换车或扩大范围必须结束原会话。首期仅保留四类必要出口：
    - 设备修复后，以实时 IO、journal、服务端事实和 `HardwareRecoveryConfirmation` 形成唯一闭环，沿用原 Demand、原车辆和原尝试继续；
    - 原 LoadBatch 无法安全继续时，沿用原尝试和完整目标集合全部清空，全部达到 `EMPTY + 锁闭 + 输出复位` 后，原子提交补偿/取消终态与永久 TransportDemandSuppression；
    - 故障车已载货且不能续行时，在车辆停稳或完成合格物理隔离后受控取货，全部目标仓电子闭环且由具名人员接管后，原子形成 FaultCargoRecoveryRecord、`TERMINATED_BY_FAULT_CARGO_HANDOFF` 和永久抑制；
    - 锁、反馈或占用检测失真时允许具备现场资质人员在断电、抱闸或等效隔离后执行 `ForcedMechanicalCargoRecovery`。系统停止重复 DO，建立新的 `ForcedRecoveryGeneration`，使旧命令、快照、检查点和迟到结果只能作为历史证据。具名交接可关闭身份明确货物的业务问题，但不能证明电子空仓、仓门安全或设备恢复；车辆继续隔离，直至修复全部相关 IO/机构并在新代次内通过完整测试与对账。
15. **异常恢复权限采用当前简化角色模型，不恢复旧审批链。** 操作员工号只允许正常本站作业和请求本车急停，不能异常恢复或强制开仓；`MaintenanceAdministrator` 与 `SystemAdministrator` 自动具备 `ExceptionRecoveryPermission`，任一具名管理员可在一次认证后独立完成会话内系统操作，不要求 R-09/R-11/R-13 系统角色、双人批准、逐动作二次认证或共享账号。角色不能覆盖停稳、仓门安全、UNKNOWN、结果未知对账或现场作业资质；断电、抱闸和机械开锁仍须由具备相应资质人员实际执行并记录。
16. **采用 Q2 推荐值：首期使用预置八仓配置和预建具名管理员账户。** 部署前形成并现场验证固定八仓配置包、物理布局、信号语义、版本和指纹；运行时仍必须核对稳定 agvId、连接代次、配置版本/指纹、完整能力快照、逐仓 SlotOperability、锁反馈、光幕、输出复位和业务就绪。任一未配置、未验证、缺失、过期、冲突或未知都阻断整车业务，不提供管理员强制投运。首期至少预建一个不共享的个人 `MaintenanceAdministrator` 或 `SystemAdministrator` 账号用于异常处置，所有敏感操作形成不可改写审计；服务端业务与管理员审计至少在线保留 180 天，车载 IO、安全判断、执行和恢复技术日志至少保留 30 天。该首期剖面只消费已批准配置身份和抽象能力，不在本票裁决现有文档对“原始 IO 映射由车载本地维护”与“服务端配置维护台为唯一入口”的权威冲突。
17. **明确延后不影响上述安全内核的复杂能力。** 首期延后完整 ConfigurationMaintenanceConsole 的配置编辑、复制、激活和文件导入 UI，管理员账号 CRUD、密码找回/增强和完整生命周期 UI，复杂车队故障管理、审批链、跨车取货改派和补运，长期运营报表与短信/邮件/企业微信通知；同时延后多车、多 Demand、多 Sublot、复合任务、其它 WorkType、自动充电/排队/备用桩/空闲返回优化、MES/PDA 写回与结果核对、离站后普通错放的换仓/重绑/重开任务/补运，以及归档/恢复产品面。延后项不得删除稳定车辆/仓位身份、运行时配置和能力核验、当前车与服务端告警、不可改写审计、日志保留、Guard、UNKNOWN 阻断、重启对账或最小 ExceptionRecoverySession；未被首期 UI 支持的异常只能保持明确阻断，不能提供“人工标记安全、清空或完成”的捷径。

关键约束证据包括：票据 04 的 ExpectedBasketCount、完整仓位集、批量装卸闭环、本地成功与 PDA/MES 独立边界；需求基线 `REQ-0232`～`REQ-0249` 的故障、安全联锁与急停事实，`REQ-0250`～`REQ-0253` 的当前身份与异常恢复权限，`REQ-0258`～`REQ-0267` 的仓位配置和八仓硬件事实，`REQ-0269`～`REQ-0272` 的状态、告警与日志，及 `REQ-0312`、`REQ-0315`、`REQ-0319` 的稳定车辆身份、重置后不猜测物理事实和正面业务就绪证据；以及 [`ADR-cross-0003`](../../../docs/adr/cross/0003-onboard-disconnect-safe-finish-and-server-resume.md)、[`ADR-cross-0006`](../../../docs/adr/cross/0006-onboard-minimal-recovery-journal.md)、[`ADR-cross-0008`](../../../docs/adr/cross/0008-onboard-departure-safety-server-movement-control.md)、[`ADR-cross-0009`](../../../docs/adr/cross/0009-fresh-safety-check-before-each-movement.md)、[`ADR-cross-0012`](../../../docs/adr/cross/0012-persisted-movement-guard-during-station-operation.md)、[`ADR-cross-0014`](../../../docs/adr/cross/0014-durable-command-acceptance-and-same-operation-reconciliation.md)、[`ADR-cross-0016`](../../../docs/adr/cross/0016-slot-command-is-irrevocable-commit-point.md)、[`ADR-cross-0017`](../../../docs/adr/cross/0017-restart-resumes-only-from-proven-checkpoint.md)、[`ADR-cross-0028`](../../../docs/adr/cross/0028-connected-session-requires-explicit-business-readiness.md)、[`ADR-cross-0029`](../../../docs/adr/cross/0029-unified-five-step-recovery-handshake.md)、[`ADR-cross-0033`](../../../docs/adr/cross/0033-onboard-publishes-abstract-safety-state-changes.md)、[`ADR-cross-0036`](../../../docs/adr/cross/0036-load-batch-commit-and-hardware-fault-hold.md)、[`ADR-cross-0039`](../../../docs/adr/cross/0039-operator-starts-server-authorized-load-compensation.md)、[`ADR-cross-0040`](../../../docs/adr/cross/0040-internal-light-curtain-is-slot-occupancy-evidence.md)和 [`ADR-cross-0041`](../../../docs/adr/cross/0041-one-basket-per-physical-slot.md) 中已接受的跨端权威、幂等、安全和恢复决定。
