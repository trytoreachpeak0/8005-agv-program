## Question

在 Demand 生命周期、单任务调度、装卸、安全恢复、RIoT、跨端消息、OnboardHmi 原型、共享协议治理、联调切片与工厂验收都已收口后，`REQ-0001`～`REQ-0348` 中哪些精确 ID 最终属于 MVP 直接必须、交互/安全依赖、首期延后或本场景不适用，且每个延后或不适用结论是否与必须链、用户已批准决策和现场验收目标无冲突？

用户必须批准精确清单内容和身份，不以「按前述原则」替代逐条可复核结论。批准只表示 MVP 实施适用性，不修改 v1.0.0 条目的 Lifecycle。

## Answer

本票依据用户对本 Wayfinder 后续各票采用推荐值的明确授权完成裁决；该授权只代表用户本人的 MVP 产品范围选择，不伪造逐项用户发言，不代替车载端开发同事、现场人员、第三方或法定批准。

### 全部候选、推荐值与采用结果

1. **清单身份**：候选 A 为只写四类原则；候选 B 为固定基线 SHA-256、348 行逐条 TSV、四类精确 ID 清单和生成脚本；候选 C 为修改已发布 v1.0.0。**推荐并采用 B**，因为只有 B 可机读、可复核且不改写已批准基线；A 无法证明零遗漏，C 越过本地图权限。
2. **对 01 票候选的处理**：候选 A 为原样批准 83/90/46/129；候选 B 为逐条结合 02～11 最终决议复核，并对冲突或收窄项显式覆盖；候选 C 为脱离 01 票重新分类。**推荐并采用 B**，因为 01 票明确只是候选证据路由，后续决议已经改变 HistoryEpoch、白名单、管理员和恢复等适用边界，而 C 会丢失原始证据链。
3. **部分适用条目的归类**：候选 A 为只要有一句适用就列“直接必须”；候选 B 为整条精确适用才列“直接必须”，只保留其中事实/门禁/安全/恢复语义的列“交互／安全依赖”；候选 C 为拆造新的 REQ。**推荐并采用 B**，既能表达 `REQ-0194`、`REQ-0205`、`REQ-0258` 等局部保留，又不伪造基线 ID。
4. **旧角色和充电专门权限**：候选 A 为继续使用 `REQ-0236` 的 R-09/R-11/R-13 系统授权；候选 B 为按 `REQ-0253` 和票据 05 使用 MaintenanceAdministrator/SystemAdministrator，并把 `REQ-0236`、仅服务自动充电的 `REQ-0254` 列为本场景不适用；候选 C 为修改基线。**推荐并采用 B**；现场断电、抱闸、机械开锁资质仍独立强制，管理员身份不能覆盖安全事实。
5. **批准效力**：候选 A 为等同发布批准；候选 B 为仅批准精确 MVP 实施适用性身份，延后和不适用均不改变 Lifecycle，后续协议、G0～G3、生产 UI、工厂试运行和交接仍按各自门禁取得真实批准；候选 C 为永久废弃未纳入首期需求。**推荐并采用 B**，防止扩张原型票豁免或把首期延后冒充永久删除。
