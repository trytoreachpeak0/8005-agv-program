# SUBLOT 花篮估算端到端实验

## 目的

验证运输任务的 SUBLOT 和冻结 PACKAGE，经 `SUBLOT_BOX_COUNT` 查询与容量对照后，能够得到可解释的预计花篮数，并在失败时安全回退到人工确认流程。

## 关联问题

- `max_box_count` 的查询值能否正确关联到任务 SUBLOT。
- PACKAGE 精确/批准前缀规则能否得到唯一容量。
- 向上取整、零值、空值、超时和对照缺失如何处理。
- 预计数量与现场实际花篮不一致时是否保持可操作和可审计。

## 明确不回答

- 不追踪实体花篮条码。
- 不保证历史料盒计数等于当前物理在场数量。
- 不因估算失败取消运输任务。
- 不修改 MES 或自动修正容量参考。

## 输入

- 已验证的运输任务样本：SUBLOT、PACKAGE、TASK_TYPE。
- `QUERY_ID: SUBLOT_BOX_COUNT` 的批准版本与绑定参数。
- 当前容量对照和已批准的匹配规则。
- Mock 仓位、扫码、仓门和人工确认事件。

## 前置条件与客户批准

- 客户 IT 批准在测试 SUBLOT 集合上执行只读查询、执行窗口和最大请求次数。
- 测试 SUBLOT 由客户提供或从已批准 evidence 选择，不在文档中散布生产明细。
- 现场负责人确认花篮容量和异常兜底交互。
- runner 能记录每次查询和计算的关联 ID。

## 安全边界

- SUBLOT 只通过绑定变量传入，不拼接查询。
- 请求串行或按客户批准并发上限执行，超时默认 30 秒。
- 不查询无关字段，不写 MES。
- 料盒查询失败、无结果、零/负异常值、PACKAGE 未匹配或规则冲突时，均不得取消任务或静默给默认花篮数。
- Mock 仓门流程不得驱动真实设备。

## 步骤

1. 创建 run，记录任务样本、查询哈希、容量表版本和批准信息。
2. 对每个测试 SUBLOT 执行绑定查询，记录 `max_box_count`、耗时、状态和错误类型。
3. 使用任务创建时冻结的 PACKAGE 匹配唯一容量；记录规则 ID。
4. 仅在料盒数为正整数且容量为正整数时计算 `ceil(max_box_count / capacity)`。
5. 覆盖整除、非整除、单篮、多篮、空结果、超时、PACKAGE 空值、未匹配、规则冲突和异常数值。
6. 对成功估算用 Mock 验证达到预计篮数后可结束装载。
7. 对失败场景验证进入“重复扫描同一 SUBLOT、二次确认新增一篮”，包含防抖、仓门与仓内物体传感器校验；并以「开始运送」进入运送（占用为 0 时不可点）。
8. 验证实际篮数与预计不一致时记录差异并允许受控人工完成，不修改冻结 PACKAGE。
9. 输出逐案例证据和汇总结论。

## 通过标准

- 所有成功案例计算可复算，使用正确 SUBLOT、冻结 PACKAGE、容量规则和向上取整。
- 所有失败/未知案例均 fail-closed 到人工兜底，不取消任务、不伪造默认数量。
- 重复扫码不会因扫码枪抖动直接增加花篮；必须二次确认并通过仓门与仓内物体传感器校验。
- 每个花篮序号和仓位占用可追溯到任务与操作员会话。
- 无 MES 写操作或真实设备副作用。

## 输出

- 逐 SUBLOT 查询与计算记录
- 成功/异常案例矩阵
- Mock 扫码与仓门事件日志
- 预计/实际差异报告
- manifest、原始输出和 SHA-256
