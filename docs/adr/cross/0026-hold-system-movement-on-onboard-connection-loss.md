# 行驶中车载连接失联时暂停本系统移动任务

同事初稿 §22 只覆盖仓位操作期间的服务端通信中断，§17.4 与 §27 又明确车载端提供机构安全事实、服务端负责车辆移动。为覆盖行驶期间无法继续取得车载安全状态的空白：车辆正在执行由本系统发起的 RIoT 移动任务时，一旦服务端正式判定 VehicleConnectionSession 失效，必须自动执行 MovementConnectionLossHold，通过 OrderHold 请求并核验车辆停止，不允许车辆在失去车载安全状态通道后继续到站。

通信恢复本身不触发续行。服务端必须先完成车辆连接会话、车载能力、未结仓位操作与物理/业务状态对账，再取得新的 PreDepartureSafetyCheck，并明确决定后才可执行 OrderContinue。若任务来源不是本系统或无法确认，或者暂停后无法在规定时间内核验停车，则沿用 ADR-cross-0011 的取消或 EmergencyStop 升级规则。

**Status**: accepted

**Considered Options**:
- 允许当前移动继续到站（拒绝：失联后服务端无法接收 DepartureSafetyRevoked，也无法证明持续安全）
- 失联即直接 EmergencyStop（拒绝：对可控的本系统任务过于激进，OrderHold 是首选保护动作）
- 本系统任务先暂停并核验，重连对账和新鲜安全核验后明确续行（采纳）

**Consequences**:
- “正式判定失联”的心跳周期和超时阈值必须明确，不能因单个心跳丢失立即暂停。
- 服务端必须跟踪当前 RIoT 任务来源，不能仅凭 AGV 正在移动就决定后续恢复。
- OrderHold 接口成功不等于车辆已经停止，必须观测实际订单或车辆状态。
- 本决定扩展同事初稿 §22；后续接口确认稿应补充“行驶中断链”场景。
