# 车载上位机断线时只收尾当前开锁集合，重连后由服务端授权续行

> *2026-09-18：本文讲批量开锁（BatchUnlock）的部分由 [ADR-cross-0061](0061-one-slot-door-unlocked-at-a-time.md) 取代——业务仓位操作一次只开一扇仓门，按分组再按仓位号依次打开；已随 `CP-0004` 批准生效（2026-09-18，需求基线 `v1.4.0`），具体取代哪几句见该文 Consequences。其余正文不变。*

车载上位机与服务端通信中断后，仓位操作进入断联仓位操作收敛（ConnectionLossSlotContainment）：HMI 明确提示“服务器连接已断开，正在等待恢复”；不得扩大当前开锁集合（ActiveUnlockSet）。尚未发出开锁动作时立即暂停；开锁动作已经开始（含命令已发但反馈尚不明确）时，只执行当前开锁集合安全收尾（SafelyFinishActiveUnlockSet）。装货与卸货都可能批量打开多个仓位，当前开锁集合包含已经发出批量开锁命令或发送结果不确定的仓位。跨 IO 模块发送途中失联时，尚未发送的模块分组不得继续开锁。

安全收尾必须完成本次已经开始的物理意图，而不只是关门：装货仓位达到 `OCCUPIED + 锁闭 + 开锁输出已复位`，卸货仓位达到 `EMPTY + 锁闭 + 开锁输出已复位`，并形成可供恢复对账的明确逐仓结果。开锁输出采用 IO 模块脉冲模式并由模块自动复位；车载端不持续或重复写复位，只在脉宽加通信余量后核验输出回读已无效。锁反馈未按期变为未锁表示开锁或弹门失败，输出未复位表示 IO 故障，均不得自动重复开锁。

暂停不设置自动取消超时，也不得在车载端强制清除当前 Sublot、执行进度或积压结果。重连后车载上位机先按原仓位操作尝试编号同步已完成、当前开锁集合、剩余仓位和抽象实时 IO 状态；只有收到服务端在完成对账后的明确授权才可继续。若只是通信断联且物理状态始终有效，授权到达后无需操作员在 HMI 重复确认；若同时存在锁 DI 等硬件故障，则必须先按 ADR-cross-0036 取得 HardwareRecoveryConfirmation。连接恢复本身不构成授权。未获确认应答（ACK）的结果保留原标识重发，重发不得再次开门。

**状态（Status）**: 已接受（accepted）

**考虑过的方案（Considered Options）**:
- 断线后完成尚未开始的整个指令（拒绝：服务端失去监督后仍会产生新的开门动作）
- 断线后立即中止一切，包括已经打开的仓位（拒绝：可能留下有货/空仓意图未完成的打开仓门）
- 只收尾已经开始的当前开锁集合、其余暂停且不超时，重连对账后由服务端授权续行（采纳）

**影响（Consequences）**:
- “开锁命令已发或发送结果不确定”而不是“已收到开门反馈”作为安全收尾边界，覆盖命令已产生物理副作用但反馈尚未到达时发生断线的竞态。
- 当前开锁集合是安全边界，不是固定单仓：装货与卸货的批量开锁都可以形成多仓集合。
- 当前硬件没有独立的门关闭传感器，仓门是否锁闭只以锁传感器的有效反馈判断；不得另造“门已关闭”状态，也不得根据开锁输出反推仓门锁闭。
- 开锁脉冲结束不表示仓门锁闭；弹簧会在锁舌释放后弹开仓门，锁 DI 只有在仓门实际关闭并重新闩合后才恢复锁闭。锁传感器与开锁输出回读是两个独立事实。
- 逐仓结果是用于恢复和对账的操作记录，不得与上述机构事实混为同一状态。
- 车载上位机必须保留足以按原仓位操作尝试编号对账的执行进度；暂停无论多久都不自动清理，维护人员也不能本地删除。
