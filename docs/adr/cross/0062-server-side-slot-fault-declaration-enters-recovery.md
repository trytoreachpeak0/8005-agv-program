# 仓位卡住但读数有效时，车载端上报超时，由管理员在服务端判为 UNKNOWN 进入恢复

ADR-cross-0058 决策 2 规定「只有 `UNKNOWN` 进人工恢复」，`UNKNOWN` 只来自传感器读不出来：锁闭反馈无效、开锁输出无法确认复位、
光幕状态未知。它没有覆盖传感器**读得出来、但读错了**的情形：锁舌断了一直读「未锁」、门机械卡住关不上、光幕卡在「有货」。
这时车载端的目标态闭环（ADR-cross-0040）一直提示、一直重开，永远不判 `UNKNOWN`；服务端旅程停在等待结果，不进 `Blocked`，
异常处置会话开不了。装货还能由操作员按取消收口，卸货没有取消出口（ADR-cross-0015），就是真正的卡死。

2026-09-18 的只读调研（[program#113](https://github.com/trytoreachpeak0/8005-agv-program/issues/113) 第一条评论）确认这是
硬件卡死的主要来源（报告里的「缺口一」），并排除了用维护开门模式解决的可能（`CP-0004` 修订项三）。本 ADR 给决策 2 补上
`UNKNOWN` 的一种新来源：**有权限的人依据现场事实判定**。条文由 `CP-0005` 新增的 `REQ-0358`、`REQ-0359` 承载。

## 决策

1. **车载端只上报，不判断。**当前仓位自第一次开锁起累计等待操作员达到门槛（默认 3 个 `OperationTimeout`，6 分钟；自动重开不
   清零；车载端配置，投运实测标定），车载端经 `OnboardAlarmSnapshot` 上报告警 `SLOT_EXPECTED_ACTION_OVERDUE`，HMI 提示「期待的
   操作很久没有完成，已上报，班组长或管理员会到现场查看」，会话断开时改为「与服务端断开，请联系管理员」。执行器行为不变：照旧
   提示、照旧重开，不判失败、不进恢复。车载端分不清「硬件坏了」与「人走开了」，所以不替人判断。

2. **判定只在服务端，由持 `ExceptionRecoveryPermission` 的管理员做。**服务端看板新增「期待动作超时」卡片，列车辆、站点、仓位、
   期待的动作、已等时长和锁／光幕／开锁输出读数；卡片每行挂一个判定表单（凭据、工号、角色、故障类别、必填现场说明），提交到
   Host 的新接口，写法照 `REQ-0356` 急停解除接口。**车载 HMI 上没有判定入口，管理员也不在 HMI 上判。**只有已上报超时的仓位
   才有判定表单，这就是触发门槛。

3. **判定生效的方式：服务端可靠下发，车载端核对后中止并如实上报。**车载端收到判定时，同一次尝试、同一个仓仍在等待操作员的，
   把判定写进执行日志，中止执行器（`AbortOperationAsync`），不再发任何开锁输出，上报 `OperationResult`：该仓 `UNKNOWN`、后面的仓
   `NOT_STARTED`、已完成的仓按实时读数报告；服务端照已有路径转 `RecoveryRequired` 与 `Blocked`，之后走现有的异常处置会话。
   仓位已闭环或已换代的，车载端拒绝，服务端撤销判定，不改任何业务状态。判定不开门、不结算、不取消需求、不改 MES、不标记
   仓位不可操作。

4. **决策 3 需要协议新增两条消息，排在 `protocol-v3.0.0`。**`protocol-v2.0.0` 里没有一条服务端→车载端的消息表达「中止这次仓位
   操作、把当前仓结算为 `UNKNOWN`」，挪用任何一条都改变其含义，按协议治理规则属于破坏性改动。新增
   `SlotFaultDeclarationCommand`（服务端→车载端）与 `SlotFaultDeclarationResult`（车载端→服务端），字段见 `CP-0005` 第 4.3 节。
   决策 1 与看板卡片的只读部分用现有消息即可，在 `protocol-v2.0.0` 上先做。

5. **`protocol-v3.0.0` 之前的过渡办法：管理员到车上重启车载端程序。**重启后的中断结算（`SettleInterruptedAsync`）不再输出开锁，
   按实时 IO 把开过但不在目标态的仓报 `UNKNOWN`（原因码 `RECOVERY_CHECKPOINT_NOT_UNIQUE`），旅程随即阻断，异常处置会话可开。
   它留下的痕迹与判定不同：服务端看不出这是一次有意的判定；v2 车载端的会话原因是固定文字，判定人、类别与说明只能记在现场交接
   记录里。决策 4 上线后停用。

**Status**: proposed（随 `CP-0005` 批准转为 accepted）

**Considered Options**:

- 开放维护开门模式，让人在业务操作未收敛时进入维护去修、去取（拒绝：`REQ-0227` 禁止维护开启有未收敛操作的仓，`REQ-0229` 规定维护
  不结算业务，卡住的那一仓在维护里也开不了、退出后操作仍挂着；两类开门并存还破坏 `REQ-0357` 的一次一扇。见 `CP-0004` 修订项三）
- 车载端在重开若干次或等待若干时间后自己判 `UNKNOWN`（拒绝：时间与次数都分不清「硬件坏了」与「人走开了」，这正是 ADR-cross-0040
  禁止的把人的不作为当成故障；`REQ-0232` 也规定时间不能单独升级故障事实）
- 管理员在车载 HMI 上判定，先在本地中止、再开恢复会话（拒绝：用户 2026-09-18 否决。HMI 面对操作工，入口放在那里难免被误用；
  判定要看读数与已等时长，这些集中在服务端看板上）
- 服务端只在自己这边把旅程置为阻断，不通知车载端（拒绝：车载端还在提示、还在重开，可能还会闭环并报 `COMPLETED`，两端对同一次
  操作的结论不一致）
- 挪用 `SessionReadiness` 的 `RECOVERY_REQUIRED` 或快照里的 `blockingFacts` 通知车载端（拒绝：前者是作用于整个连接的握手决定，后者
  是不可靠、不去重的快照，都不能驱动一次仓位操作的中止；改它们的含义同样是破坏性改动）
- 放宽 `RECOVERY_DEMAND_NOT_BLOCKED`，允许对未阻断的需求先开会话、再在会话里判定（拒绝：同样改变协议含义，而且让「一车一会话」
  与正常业务操作并存，审计与状态都更难说清）
- 车载端上报超时，服务端看板判定，可靠消息下发，车载端核对后中止并报 `UNKNOWN`；协议改动排进 `v3.0.0`，之前用重启过渡（采纳）

**Consequences**:

- **ADR-cross-0058 决策 2 读作**：只有 `UNKNOWN` 进人工恢复，`UNKNOWN` 来自传感器不可信，**或来自持权管理员依据现场事实在服务端的
  判定**。「人未放料、未取料、未关门都不是 `UNKNOWN`」不变：判定要求现场事实与现场说明，车载端自己永远不因时间判 `UNKNOWN`。
- **ADR-cross-0040「操作员可以在反复无法达到预期时暂停并呼叫设备维护」**有了具体形态：车载端上报超时就是「呼叫」，判定就是设备
  维护人员接手的那一步。暂停不形成成功结果、不解除站点保护，这一点不变。
- **卸货第一次有了进入恢复的正规入口**，但进入之后能怎么收尾，取决于恢复路径本身：卸货上的受控取货与强制机械取出目前还是断头路，
  由 [onboard-hmi#107](https://github.com/trytoreachpeak0/8005-agv-onboard-hmi/issues/107) 与
  [control-server#137](https://github.com/trytoreachpeak0/8005-agv-control-server/issues/137) 修复。
- **看板第一次有写操作。**看板进程不持有判定权，表单提交到 Host，由 Host 认证、核对、审计、下发；看板仍只绑本机，经 SSH 隧道访问；
  每 2 秒整页刷新不能刷掉填到一半的表单。
- **协议 `v3.0.0` 的代价**：ProtocolVersion 3 升 4，两端重新 pin，全部 `FP-IS-*` 切片的 `G1`、`G2`、`G3` 证据作废。与 `CP-0004` 第五节
  留下的两处措辞（`supportsBatchUnlock`、`FP-IS-04` 的 scope 名）同批处理，只付一次。
- **审计分两层**（ADR-cross-0019）：服务端业务审计记判定人、角色、时间、车辆、Demand、尝试、仓位、类别、说明、判定时的读数与车载端
  接受或拒绝的结果；车载端技术日志记收到判定时的实时 IO 与中止过程。
- **身份验证强度**在账号体系 `FP-C6` 落地前是共享 bearer 凭据加个人工号，与急停解除接口、车载恢复会话的现状相当。
- **过渡期间的判定不留系统痕迹**，只能记在系统外的现场交接记录里。这是用重启副作用换出口的代价，决策 4 上线后消失。
- **门槛是现场参数。**6 分钟在装货站上约晚于站点期限 1 分钟，现场升级规程的升级表不改，HMI 文案写「班组长或管理员」，超时上报
  只让人看到，不改变谁先到场。

**为什么新写一篇而不是在 ADR-cross-0058 里加补充。**票面建议写成 0058 决策 2 的补充，二者都可以。选新写一篇有三条理由：
一是这个决策有自己完整的被否选项与后果，涉及看板写操作、协议发布与过渡办法，塞进一条决策下的斜体补充放不下；二是 0058 已有
约 360 行，前半部分是 MVP 线的历史与验收，读者要找 v2 的恢复入口很难找到；三是与 ADR-cross-0061 的做法一致：新规则集中在一处，
0058 决策 2 与 ADR-cross-0040 各加一行指针，读旧 ADR 的人第一行就知道去哪里看。
