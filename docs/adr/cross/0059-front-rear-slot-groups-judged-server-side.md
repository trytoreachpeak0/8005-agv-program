# 前后仓位分侧只在服务端判定，装满按侧计算并原地持货等单

客户 2026-09-14 反映：多仓位 AGV 车身宽、机台间距窄、停靠点离取料位太近，只有一侧仓门够得着机台边的
架子。八个仓位从此分为前侧（1～4 号）与后侧（5～8 号），每个区域号的机台只能用其中一侧。本条决定这条
约束在系统里怎么表达、由谁判断，以及它怎样改写 ADR-cross-0041 与 ADR-cross-0057。条文见需求变更提案
[`CP-0002`](../../../requirements/change-proposals/CP-0002.md)，问答过程见
[program#65](https://github.com/trytoreachpeak0/8005-agv-program/issues/65)、
[program#68](https://github.com/trytoreachpeak0/8005-agv-program/issues/68)、
[program#70](https://github.com/trytoreachpeak0/8005-agv-program/issues/70)、
[program#71](https://github.com/trytoreachpeak0/8005-agv-program/issues/71)。

**分组沿用 SlotPosition，开门侧按 AREA 指派。**不新建「侧」字段：`SlotPosition` 取 `FRONT`／`REAR`，
来自整车仓位模板。开门侧是 `DispatchZoneAreaAssignment` 的必填列——以 AREA 为键，因为站点会被删除重建而
AREA 稳定；放进分区归属，因为另建一张同键的表只会多出「两表对不上」一类错误。需求在分配目标仓位时冻结
所用的指派版本。

**只在服务端判断，不改协议。**服务端在派车时为整条需求一次选定目标仓位，装货与卸货读同一份，于是「在 AREA
机台站点只开指派那一组」与「在公共站点装送往机台的货时装进目的那一组」由同一条选仓规则满足。车载端按下发的
仓位开门，不按站点校验：那需要改 `protocol-v1.0.0` 并作废两端的 `G1`／`G2`／`G3` 证据，而开错门的后果是
取不出产品、人工处理，是效率问题不是安全问题。分侧与开门侧配置错误的拒绝原因只在服务端记录、在看板展示，
不经 `blockingFacts` 下发——`ErrorCode` 是封闭枚举。

**一条需求不跨组。**机台只开一侧门，拆到另一侧的花篮取不出来。花篮数超过单侧物理仓位数（今天是 4）的需求
没有车能装，按结构性派车阻断告警、人工送，不跨组、不拆趟。

**装满按侧计算，没装满就持货等单。**每一侧分别判断：这一侧已无空仓，或有一条其余准入全过、只因车上已装或
已预留的货占了这一侧而装不下的候选，这一侧就装满。两侧都装满，车辆才装满，不再等新单；已承诺的单照常装完，
在离开计划里最后一个装货停靠之前冒出能装入的单仍然接。只要还有一侧没装满——包括这一侧暂时没单、整辆车一条
候选都没有——车辆就停在最后装货的站点持货等单，直到装满、持货超时或让站。车辆能服务的分区都禁止途中追加时
不等单，因为等也接不到。**理由是提高仓位利用率**：后期一辆车要承接多个任务，运力又不足。

**等单的车停在原地，别的车需要这个站时让站。**机台站点没有站点独占机制，不让站，调度就会把别的车派进一个
被占着的站。别的车被承诺以这个站为下一停靠（装或卸都算）的那一刻，等单的车结束等单、不再接单、前往卸货；
但让站不打断任何阻断离站的状态——仓门开着、正在录入或纠错、状态未知、断联、维护开门——要等它们安全收敛、
离站安全核验通过后才动。

**Status**: proposed（随 `CP-0002` 批准改为 accepted；届时 ADR-cross-0041 与 ADR-cross-0057 的 Status
行加「部分由 ADR-cross-0059 修订」）

**Considered Options**:
- 车载端按站点校验开门侧（拒绝：要改协议并作废两端门禁证据，而开错门是效率问题）
- 开门侧按站点号配置（拒绝：站点会删除重建，AREA 稳定）
- 开门侧放进公共站点绑定或仓位配置（拒绝：公共站点绑定不从 AREA 识别；仓位配置是车辆硬件事实，改一次要整车维护）
- 花篮数超过单侧仓位数的需求跨组装，或拆成两趟（拒绝：到机台取不出来；拆趟破坏整批原子性）
- 有一侧装不下、此刻又没有别的单就立刻去卸货（开图时的定案；拒绝：后侧空着跑，仓位利用率低）
- 一条候选都没有就立刻出发（MVP 现状；拒绝：同上，并且会出现装得少的车反而先走）
- 按整车空仓总数判满（拒绝：前侧的空仓装不了后侧的货）
- 被别的门禁挡住的候选、超大需求也计入「装不下」（拒绝：车会为一条轮不到它的需求提前走，积压里挂一条超大需求就让所有车一趟一单）
- 持货的车开去等待点等单（拒绝：多跑路；等待点只给没有业务目标的车；多一层能力依赖）
- 原地等单、不让站（拒绝：机台站点无独占，会堵站）
- 装满、持货超时、让站判定后一律锁定不再接单（部分采纳：持货超时与让站锁定；装满判定后到离开最后一个装货停靠前仍接单，空位要用上）

**Consequences**:
- **ADR-cross-0041 按分组读。**「子批号花篮数大于可用仓位数时，服务端直接拒绝本次装货」中的可用仓位数指所需
  分组的可用仓位数；「一个 LoadBatch 最多容纳的花篮数受车辆固定物理仓位数和当前 SlotOperability 共同限制」
  中的物理仓位数指所需分组的物理仓位数。一仓一篮本身不变。
- **ADR-cross-0057 的「装满」由本条取代。**原定义「车辆可用仓位已不足以承载下一个候选需求的
  `ExpectedBasketCount`」改为按侧定义；零候选时「等到持货超时」由本条明确为原地持货等单。持货超时的 30 分钟、
  起算点、到期不打断正在进行的仓位操作、以及实施中定下的「装满只停止吸收新需求，不丢下已经承诺的需求」都保留。
- **ADR-cross-0055 不改。**站点离站等待期限照旧结束本站；本站结束后车辆可以留在原地持货等单，真正动身仍走
  0055 的离站流程。
- **相对当前 MVP 生产是有意的行为变化。**MVP 装完当前计划即去关卡（`LoadingClosedReason =
  NO_FURTHER_CARGO`），从不等单。切到 v2 的验收不得把持货等单当作倒退。
- **各调度分区的途中追加最大允许值（`REQ-0198`）成为持货等单生效的投运参数**：零或未配置时车辆不等单。
- **5～8 个花篮的需求分侧后转人工送**，比例未知。
- **推翻不变量 I8「仓位可互换，任何仓位服务任何站点」，属重构**（program#70 定案 4）。不推翻 I4
  「站点无独占」：让站不阻止别的车被派往该站。
- 车载界面把前后两排仓位分开显示是纯界面工作，另行安排。
