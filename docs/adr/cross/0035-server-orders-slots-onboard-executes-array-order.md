# 服务端确定目标仓位集合，车载端批量开锁

> *2026-09-18：本文讲批量开锁（BatchUnlock）的部分拟由 [ADR-cross-0061](0061-one-slot-door-unlocked-at-a-time.md)（`proposed`）取代——业务仓位操作一次只开一扇仓门，按分组再按仓位号依次打开；随 `CP-0004` 批准生效，具体取代哪几句见该文 Consequences。其余正文不变。*

服务端负责确定不可增删的完整目标仓位集合。第一版装货在取得不可修改的 ExpectedBasketCount 后，一次分配数量相等的目标仓位并批量开锁；卸货同样按本站完整目标集合批量开锁。SlotOperationCommand.slots 表达集合，不赋予花篮、操作员放取或关门顺序。车载端按仓位 IO 绑定将目标集合按模块分组，同一模块优先用 Modbus `0x0F` 批量开锁，跨模块并行发送。

服务端可以按物理仓位号稳定排序生成数组，便于消息幂等比较，但该顺序不构成物理执行次序或花篮身份。

车载端在返回指令接受 ACK 前校验数组非空、物理仓位号有效、没有重复，并且所有目标仓位在当前能力快照中可操作且未被服务端管理禁用。校验失败时拒绝整条指令，不打开任何仓位。

**Status**: accepted

**Considered Options**:
- 车载端自行增删目标仓位（拒绝：会改变服务端冻结的任务范围和预留）
- 装货逐仓开门，由用户逐次请求下一仓（拒绝：第一版查询花篮数的目的就是一次打开等量仓门）
- 服务端冻结完整目标集合，装货与卸货均按 IO 模块批量开锁（采纳）

**Consequences**:
- 装货与卸货都必须按物理仓位号分别表达成功、失败或未知；某个模块失败不能抹掉其它模块已打开仓位的结果。
- 操作员可以按任意顺序向已打开仓位放入花篮或从中取出花篮，并按任意顺序关门；逐仓结果不依赖数组下标顺序。
- 同一 SlotOperationAttemptId 的任何重发都必须保持完全相同的 slots 集合；规范化后的内容变化属于冲突并拒绝。
- 执行日志必须在批量写前持久化完整目标集合和模块分组；跨模块发送途中失联时，当前开锁集合只包含已发送或发送结果不确定的分组。
