# 光幕证明取空即结清装货侧的货物业务，仓门锁闭证明改为车辆放行条件

program#149（批次8-04）增量复核发现一格只能改库的死路：装货或装货取消途中某个仓位的锁 DI 坏了，永远读不到锁闭，车载端把该仓判为
`UNKNOWN`，车辆进入 `VehicleRecoveryRequired`；仓内光幕照常工作，明确读到 `EMPTY`，也就是货已经取空或从未放入。按原决策，
取消清空与补偿清空都要求 `EMPTY + 锁闭 + 开锁输出已复位` 才能结清（ADR-cross-0039、0046、0052），修复续行要先修好锁，
强制取出要交接记录而仓里没有货。四条路都走不通。

用户 2026-09-29 选定方向（[program#160](https://github.com/trytoreachpeak0/8005-agv-program/issues/160)）：光幕证明空就结清货物业务，
锁闭证明挪到车辆放行条件。条文由 `CP-0009` 修订的 `REQ-0357`、`REQ-0238` 与新增的 `REQ-0364` 承载。

**依据。**`REQ-0242` 已确立「货物业务闭环与设备恢复闭环分离」。仓内光幕按 ADR-cross-0040 本来就是仓位占用的证据，补偿结束的空仓证据
一直由它提供（ADR-cross-0039）。在这一格里，锁闭证明挡住的其实是「这辆车能不能走」，不是「这笔货清没清」。

**结清。**取消清空与补偿清空中，光幕明确 `EMPTY`、而锁传感器不能证明锁闭或开锁输出不能证明复位的仓位，业务结果按 `EMPTY` 结清：

- 终态与抑制同正常的全空取消或全空补偿（`CANCELLED_BY_OPERATOR` 或 `CANCELLED_BY_LOAD_COMPENSATION`，`REQ-0156`），不形成交接记录；
- 光幕 `UNKNOWN` 不适用，仍判 `UNKNOWN`；
- 这扇门不算闭环，一次只开一扇门的约束照旧（ADR-cross-0061）：此后不再打开任何仓位。其余目标仓位都已证明 `EMPTY` 的，清空按全部
  `EMPTY` 结束；还有仓位要开门的，暂停转人工恢复，那些仓里有货，走修复续行或强制取出；
- 权限不变：车辆处于 `VehicleRecoveryRequired` 时，普通取消仍被拒绝，由管理员在异常处置会话里走装货补偿（ADR-cross-0052、0039）。
  界面上仍叫「取消装货」。

**扣车与放行。**结清之后整车不取得业务就绪：不接新的派车与途中追加，不做空闲返回或自动充电移动，保持 `REQ-0245` 的移动阻断与告警。
放行要两样东西：管理员在异常处置会话中形成的 `HardwareRecoveryRecord`，**加上**重新读到的该仓位锁闭、开锁输出复位、占用 `EMPTY`，
并通过 `PreDepartureSafetyCheck`。维修记录不能代替锁闭证明；维修更换或改动了硬件的，按 `REQ-0263` 重新核验整车。车载界面在结清时说明
「仓已确认无货，门锁未锁闭，本车需维修后才能继续」。

**Status**: accepted（2026-09-29 随 `CP-0009` 批准；需求基线 `v1.8.0`）

**Considered Options**:

- 维持原决策，锁坏时只能改库（拒绝：上真车准入线第 3 条）
- 光幕证明空就结清，但只停用这个仓位、车照常跑（拒绝：`REQ-0244`／`0245` 规定仓门未能证明锁闭就阻断移动，一扇证明不了锁闭的门
  车一开就可能甩开；要这么做需要另一种证明门在行驶中不会打开的方式，例如现场机械固定并由维护人员确认，那是另一件事）
- 让 `ALL_EMPTY` 不再隐含锁闭（拒绝：只看 `overallOutcome` 的一端会把门没证明锁闭的结果当完全闭环而放车）
- 光幕证明空就结清，整车扣到维修记录加新鲜锁闭证明，协议加显式取值（采纳）

**Consequences**:

- **取代的部分**，其余正文不变。只对「光幕明确 `EMPTY`、锁闭或输出复位不能证明」这一格生效：
  - ADR-cross-0039：决定第 8 条「在相关仓位均为 EMPTY、由锁传感器确认锁闭且开锁输出回读确认为复位后可靠上报 `LoadCompensationResult`」，
    与其后「任一目标仓位未证明 EMPTY、锁闭反馈无效、开锁输出未复位……均不得提前取消 DemandId」一段中的「锁闭反馈无效、开锁输出未复位」；
  - ADR-cross-0046：`LoadCancelPending` 完成条件中的「由锁传感器确认仓门锁闭、开锁输出回读确认为复位」；
  - ADR-cross-0052：「以 `EMPTY + 锁闭 + 开锁输出已复位` 完成本仓取消清空」与「最终必须确认所有目标仓位 EMPTY、由锁传感器确认仓门锁闭……」
    中的锁闭与复位；
  - ADR-cross-0061：闭环定义中「同时锁传感器确认锁闭、开锁输出回读确认复位」，对取消清空与补偿清空的这一格改为「业务结清、门不算闭环」。
- **不取代、只补充**：ADR-cross-0040「LoadCompensationRecovery 只有在 EMPTY、锁闭、输出复位后才算物理完成」。物理完成的定义照旧；
  改的是业务结清不再以物理完成为前提，物理完成改由车辆放行来要求。
- **协议**（随 `v3.0.0` 候选）：`LoadCancellationResult`、`LoadCompensationResult` 的 `overallOutcome` 加取值 `ALL_EMPTY_DOOR_UNPROVEN`，
  `ALL_EMPTY` 的含义不变、仍隐含逐仓锁闭与复位；新增原因码 `SLOT_DOOR_LOCK_UNPROVEN_AFTER_EMPTY`；新增向量
  `CV-LOAD-COMPENSATION-EMPTY-DOOR-UNPROVEN`。放行沿用 `HardwareRecoveryRecordSubmitted`／`Result`，不新增消息。
- **10-08 上真车的缺口**：上车用的集成分支仍是 `protocol-v2.0.0`，这一格在那一版里仍只能改库。用户 2026-09-29 定接受这个风险、现场有人盯，
  随 v3 在 10-10 前后补上。
- **卸货的同形格**（`REQ-0222`：货已取空而锁坏，卸货完成不了、车不能离站）不在本 ADR，留给 IO 故障组合矩阵调研。
- **不改**：`REQ-0156` 的抑制规则、`REQ-0240` 受控取货、`REQ-0241`／`0242` 强制取出、`REQ-0244`～`0246` 的仓门安全与急停、
  `REQ-0319` 的业务就绪。

**为什么新写一篇而不是逐篇回写。**这条规则横跨四篇 ADR（补偿、取消两篇、一次一扇），每篇讲的是别的决定。照 ADR-cross-0061 的做法，
把规则集中在一处，四篇各加一行指针，ADR-cross-0040 另加一行说明「物理完成的定义不变」。
