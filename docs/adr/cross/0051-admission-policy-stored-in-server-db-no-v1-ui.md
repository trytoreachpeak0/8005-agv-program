# 任务准入关系存服务端数据库，第一版不做配置界面

同事初稿 §2.2 将站点、任务与业务规则归服务端。StationTaskTypeAdmission 是跨车辆共享的业务配置，与初稿 §2.3 归车载端管理的 IO 映射不同，必须保存在服务端 AdmissionPolicyStore，不下发给车载端维护。

第一版在服务端数据库保存：

- 当前 `(stationId, taskType)` 唯一关系。
- 当前单调 `admissionPolicyVersion`。
- 每次变更的旧值、新值、版本、执行人/部署标识和时间。

第一版不开发运行时管理页面。软件人员通过版本化、幂等的部署脚本或受控配置导入更新；一次导入必须在单个数据库事务中完成全部关系变更、版本递增和审计写入。导入数据包含未知 stationId、未知 taskType、重复关系或其它校验错误时，整次导入失败并保留原配置。

车载端不保存、缓存或编辑准入关系，只向服务端提交 SUBLOT 和当前站点上下文。将来若增加管理页面，仍复用同一 AdmissionPolicyStore 和版本机制，不改变运行时准入接口。

**Status**: accepted

**Considered Options**:
- 像 IO 映射一样保存在车载配置文件（拒绝：准入是全局业务规则，多车副本会不一致）
- 第一版同时建设业务配置管理页面（拒绝：当前只有软件人员维护，投入没有必要）
- 服务端数据库保存，软件人员受控导入，后续按需增加页面（采纳）

**Consequences**:
- 不允许直接手工 UPDATE 后跳过 admissionPolicyVersion 和审计。
- 服务端启动时应验证当前关系引用的站点和 taskType 均有效；异常配置不得静默放行。
- 多服务端实例共享同一数据库版本，不能各自读取不同本地文件。
- 配置导入变化只影响 ADR-cross-0050 规定的新操作，不中断已承诺操作。
- 部署脚本和示例配置属于服务端交付物，需纳入版本控制和测试。
