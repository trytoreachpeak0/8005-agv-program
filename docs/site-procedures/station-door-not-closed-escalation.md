# 站点期限到期而仓门未闭：现场升级规程

装货站上，操作员扫了 SUBLOT、核验通过、仓门打开之后走开了，站点期限到期时仍有仓门没关。按
[ADR-cross-0058](../adr/cross/0058-station-converges-without-operator-and-only-unknown-needs-recovery.md)
决策 4，**本站不结束、车不走，一直等到仓门关上**，关上之后按当时的真实 IO 读数结算。等多久没有上限，
所以要有人来处理。本规程规定由谁、在哪里看到、从什么时候起负责。

决议经过见 [program#55](https://github.com/trytoreachpeak0/8005-agv-program/issues/55)。术语见
`CONTEXT.md` 的「站点期限后仓门未闭升级（StationDoorOpenEscalation）」与「告警可见对象策略（AlertAudiencePolicy）」。

## 1. 适用范围

| 情形 | 是否适用 |
| --- | --- |
| 装货站，已扫码开门，期限到期仍有仓门未闭（服务端挂 `STATION_TIMEOUT_DOOR_NOT_CLOSED`，旅程停在 `AwaitingLoadResult`） | **适用** |
| 装货站，还没扫码就发现仓门开着（旅程挂 `ONBOARD_SESSION_NOT_READY`） | 不适用。那扇门不是我方命令打开的，是离站安全问题，直接交维护管理员，原因读 `SessionRecoveries`（[program#25](https://github.com/trytoreachpeak0/8005-agv-program/issues/25)） |
| 卸货站 | 不适用。卸货必须完成，没有取消出口 |

## 2. 三条原则

1. **时间只把责任交给下一个岗位，不替人做决定。**系统不会因为等得久就结算、取消或放车，也不会因此
   判定车辆故障。
2. **关门不会取消任务。**扫码核验通过、开了门之后，关上一扇空仓门会被当成意外关上，门会重新弹开并
   继续提示。所以路过的任何人都可以放心去关门。
3. **唯一不可逆的一步是按「取消」。**取消之后这条需求被永久抑制（`CANCELLED_BY_OPERATOR`），调度不会
   再派它，这一批货只能人工搬运过站。**按取消之前，必须先弄清这一批货在哪里。**

## 3. 在哪里看得到

第一版不发短信、邮件或企业微信（`REQ-0270`），只有两块屏：

| 在哪里 | 谁看 | 显示什么 |
| --- | --- | --- |
| 车上的屏 | 车旁的任何人 | 期限到期后显示「请放入货物并关闭 N 号仓门；不装了请按取消」和已过期多久，提示按节拍重复 |
| ControlServer 看板 | 维护管理员、系统管理员 | 每条被阻断的旅程：车、站、阻断码、从何时起、已挂多久；挂满 10 分钟、30 分钟各变一次色 |

看板只绑服务器本机，维护管理员从控制端开隧道看：

```powershell
ssh -L 58009:127.0.0.1:58009 factory01
```

然后在浏览器打开 `http://127.0.0.1:58009`。

## 4. 升级表

时间从期限到期那一刻（T0）算起。10 分钟与 30 分钟是服务端配置的默认值。

| 时点 | 负责岗位 | 要做的事 |
| --- | --- | --- |
| T0 起 | 当站操作员 | 回到车前，把货放进亮着提示的仓位并关门 |
| T0 + 10 分钟 | 班组长 | 到车前处理，见 5.2 |
| T0 + 30 分钟仍未解决 | 维护管理员 | 介入，见 5.3 |
| **仓门已经关上，告警却还在**（任何时点） | 维护管理员 | **不等时长，立即介入**，见 5.3 |
| 看板显示安全证据不全 | 维护管理员 | 同上，立即介入。**例外**：看板在这一行标「行驶中（由在途运单解释）」时，是车带着服务端自己下发的运单在排队、避让或正常行驶，RIoT 在这期间读不出「已停稳」，不是故障——照上面的时长走（操作员 → 10 分钟班组长 → 30 分钟维护管理员）（[control-server#139](https://github.com/trytoreachpeak0/8005-agv-control-server/issues/139)） |

「门已关、告警还在」和「安全证据不全」不是有人走开了，是锁反馈或 IO 出了问题，班组长处理不了。

## 5. 各岗位怎么做

### 5.1 当站操作员

- 把货放进提示的仓位，关门。门关好、光幕读到有货，这一批自动提交，不用再按任何按钮。
- 发现不该装这一批（货不对、货拿不到），在车上屏按取消，取消前先告知班组长。

### 5.2 班组长

1. 先找这一批货：问当站操作员，或者到附近找。
2. **找到货**：放进提示的仓位并关门。
3. **找不到货，或者确定这一批不装了**：由持有效工号的操作员在车上屏按取消，并记下这一批的 SUBLOT，
   交 MES 侧人工处理。班组长在系统里没有身份，需要找持工号的操作员来按。
4. 门关上后门又弹开，说明仓里读到的是空的，回到第 1 步。
5. 门关上、光幕读到有货，但车上的屏或看板仍然显示在等，转维护管理员。

### 5.3 维护管理员

1. 在看板上找到这条旅程，确认车、站、仓位与挂上的时刻。
2. 看安全原因：锁反馈是否有效、IO 模块是否在线、是否有安全证据不全。
3. 属于硬件或 IO 问题的，按下面的 5.4 用「人工判故障」进入恢复流程。
4. 不是硬件问题、只是没人处理的，联系班组长按 5.2 办。

### 5.4 硬件问题：用「人工判故障」进入恢复流程

**为什么要多这一步。**这个告警挂着的时候，旅程停在「等待装货结果」，而不是「阻断」；只有阻断的旅程才能开恢复会话
（异常处置会话），所以维护管理员直接去开恢复会话会被拒绝。锁反馈、光幕这类传感器彻底读不出来时，车会自己把那个仓判为
「状态未知（`UNKNOWN`）」，旅程随即转阻断，这时直接开恢复会话就行。麻烦的是**传感器读数有效、但读的是错的**：锁舌断了、
传感器一直读「未锁」，门机械卡住关不上，光幕卡在「有货」。车看到的是「门还没关好」「货还没取走」，会一直提示、一直等，
永远不会自己判 `UNKNOWN`。车上的操作员也分辨不出这是硬件坏了还是人没做完，所以这件事交给维护管理员判断。依据是
[`CP-0005`](../../requirements/change-proposals/CP-0005.md) 与
[ADR-cross-0062](../adr/cross/0062-server-side-slot-fault-declaration-enters-recovery.md)（2026-09-18 已批准，需求基线 `v1.4.0`）。

**谁能做。**只有维护管理员或系统管理员（持异常处置权限的人）。班组长和操作员不能判故障，车上屏也没有这个入口。

**先到车前确认是硬件问题。**不管用下面哪种办法，都要先亲眼确认，并且能说出具体是什么：例如「3 号仓锁舌断，门关上后锁传感器仍
读未锁」「3 号仓门框变形，门关不上」「5 号仓已取空，光幕仍读有货」。说不出具体硬件事实的，不是本节的情形，回到 5.3 第 4 步。
判错了不会多开门，但这一批就不能自动提交了，要在恢复会话里收尾。

#### 5.4.1 看板判定（`protocol-v3.0.0` 上线后）

1. 当前仓位等得太久（默认 6 分钟，从这个仓第一次弹开算起，中间重新弹开不清零），车上屏会提示「期待的操作很久没有完成，已上报，
   班组长或管理员会到现场查看」，看板上「期待动作超时」卡片会出现这一行，列出车、站、仓、期待的动作、已等多久，以及锁、光幕、
   开锁输出的读数。
2. 在这一行上打开判定表单，填凭据、自己的工号和角色、故障类别（锁、仓内光幕、门机构、IO 模块）和现场说明，提交。
3. 车收到后停止对这个仓发开锁指令，把这个仓报为 `UNKNOWN`，把后面还没开的仓报为「未开始」，旅程随即转为阻断。看板上这一行会显示
   车载端已接受；如果显示「被拒」，说明提交的那一刻这个仓刚好已经闭环了，不用再做什么。
4. 到车上屏开恢复会话，选一条路收尾：
   - **修好后续作**：修好锁或传感器后，从这个仓接着做；
   - **补偿清空**（仅装货）：不装了，把这一批已放进去的货全部取出；
   - **受控取货**：系统逐个开门，把货取出交给具名的人，任务终止；
   - **强制机械取出**：锁无法用系统打开时，先断电、抱闸，再由有资质的人手工开锁或拆卸。

判故障本身**不开门、不取消任务、不改 MES**。它只是把这条操作从「一直等」转成「等人来处理」，真正的收尾在第 4 步。

看板判定依赖协议 `v3.0.0` 新增的两条消息，以及服务端、车载端的实现，**在它们随 RC 上线之前不可用**，照 5.4.2 办。第 1 步的超时
提示与看板卡片不依赖协议改动，会先上线。

#### 5.4.2 过渡办法：重启车载端程序（`protocol-v3.0.0` 之前）

1. 确认车停在站上、没有人正在往仓里伸手。
2. 在车上关闭车载端程序，再重新打开（或按部署手册重启车载端）。重启期间服务端会看到车断线，车本来就停着，不会动。
3. 程序重启后会先核对上次没做完的仓位操作，**不会再发任何开锁指令**：没开过的仓报「未开始」，已经做完的仓报「完成」，卡住的那一仓
   不在目标状态，报为 `UNKNOWN`。车上屏显示「上次……在执行中中断……未再开锁，需要管理员恢复」，旅程随即转为阻断。
4. 到车上屏开恢复会话，照 5.4.1 第 4 步收尾。
5. **记下判定人、故障类别和现场说明**，例如「张三，锁：3 号仓锁舌断，门已关但锁传感器读未锁」。恢复会话里有「原因」可填的版本上线后，
   开会话时填进去；上线之前，车上屏开恢复会话时没有地方填写，记进现场交接记录，并告知系统管理员。这一条很重要：重启本身不会把
   这些信息记进系统。「原因」只在管理员开的恢复会话里出现，操作员用的界面上没有判故障的入口。

过渡办法的局限：

- 系统里留下的原因码是 `RECOVERY_CHECKPOINT_NOT_UNIQUE`（IO 读不到时是 `SLOT_STATE_UNKNOWN`），与「程序意外退出」看起来一样，
  看不出这是一次有意的判定；所以第 5 步记下的原因是唯一的记录。
- 已经按过「取消」、取消还没有答复的装货，重启后车会重发取消请求，**不会**把卡住的仓报 `UNKNOWN`，按取消流程收尾。
- 读数错成「已经做完」的（例如卸货时光幕卡在「空」），重启后会被报为「完成」。那不是卡住，而是完工后遗留物，不在本节范围。
- 5.4.1 看板判定上线后，已经亮出超时的仓一律用看板判定。本办法只留给一种情况：没到超时门槛、但现场已经明显损坏（例如门框
  一眼可见地变形），又不能等门槛到。看板判定只对已亮出超时的仓开放，这是有意的限制，防止随手判故障。

**注意：**

- 车上的恢复开关（`recoveryResumeEnabled`）出厂是关的。它关着的时候车上屏开不了恢复会话，两种办法都走不到最后一步，要先由维护
  管理员按部署手册打开。
- 卸货站在装卸这一步同样可能卡住，也用本节的办法进入恢复（卸货不适用本规程的其余部分，见第 1 节）。在 v2 当前实现下，
  卸货进入恢复后能用的只有「修好后续作」：车载端的受控取货与强制机械取出只对装货开放，强制机械取出在服务端也收不了尾。
  修复分别在 [onboard-hmi#107](https://github.com/trytoreachpeak0/8005-agv-onboard-hmi/issues/107) 与
  [control-server#137](https://github.com/trytoreachpeak0/8005-agv-control-server/issues/137)。

## 6. 已知局限

- **站上没人、也没人路过时，没有人会发现。**第一版不推送，也不承诺有人值守看板。看板只是在有人被
  叫来之后，帮他定位车、站、仓位和已经等了多久。如果这一点不能接受，需要改的是 `REQ-0270` 里
  「第一版不推送」那一句，那是另一次决定。
- 车上没有声光硬件，提醒只有文字。

## 7. 生效条件，以及生效之前

本规程第 2 节第 2、3 条、第 3 节和 5.1、5.2 里的取消步骤，依赖两件尚未合入的改动，要随包含它们的
RC 上线后才成立：

- [control-server#42](https://github.com/trytoreachpeak0/8005-agv-control-server/issues/42)：看板显示被阻断的旅程、开始时间与分色，看板进 RC 包；
- [onboard-hmi#48](https://github.com/trytoreachpeak0/8005-agv-onboard-hmi/issues/48)：期限到期后空关仍弹开，在途装货可以取消，到期文案改为让人关门。

**在那之前**，现行行为不一样，照下面办：

| 事项 | 在那之前的行为 | 对规程的影响 |
| --- | --- | --- |
| 车上的屏 | 期限到期后只显示「已到期，等待本站结束」，另外按节拍重复「请向N号仓放入货物并关门」 | 看到这句也按本规程处理 |
| 看板 | 看不到这个告警 | 维护管理员只能在服务器上查 `JourneyRuntimes.BlockReasonCode` |
| 期限到期后空关 | 第一次空关仍弹开，**第二次空关就判取消并永久抑制**（`CANCELLED_BY_STATION_TIMEOUT`） | **没找到货之前，不要关空门** |
| 取消按钮 | 出厂配置下，已开门装货时车上没有取消按钮 | 放弃这一批只能靠第二次空关，那等于取消，同样要先弄清货在哪 |

**5.4 另有自己的生效条件**：`CP-0005` 批准之后，5.4.1 第 1 步的超时提示与看板卡片随 RC 上线；5.4.1 的看板判定要等
`protocol-v3.0.0` 与两端实现随 RC 上线。在那之前，硬件问题照 5.4.2 用重启车载端程序的办法进入恢复。
