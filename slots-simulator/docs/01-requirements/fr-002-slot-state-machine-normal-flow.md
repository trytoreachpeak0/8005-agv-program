# FR-002 仓位状态机与正常流程

## Description 需求描述

每个仓位维护锁状态（锁定/解锁）、门状态（开/关）和光幕检测（有遮挡/无遮挡），并支持"开锁→开门→放料→关门"以及"开锁→开门→取出→关门"的状态迁移。统一术语为"开门、关门、放料、取出"。

其中"锁状态"是"开锁指令"DO 当前电平值的实时镜像（电磁锁通电开锁、断电闩锁），不是独立于 DO 维持的一次性触发动作状态：DO=1（True）时锁状态=解锁，DO=0（False）时锁状态=锁定。该 DO 点位的电平/脉冲控制模式详见 [[fr-012-do-pulse-level-control-mode|FR-012]]——脉冲模式下 DO 会在脉冲时长后被模拟器自动复位为 0，锁状态随之自动变回锁定，不需要主系统显式操作。

"门状态"不对应任何独立的 Modbus 寄存器点位——现场仓门没有独立的门磁/门位传感器，门是否打开由锁的 DO/DI 推算，这一推算属于主系统软件层的判断逻辑（详见 [[dr-013-door-state-not-independent-io-point|DR-013]]）。本 FR 中维护的"门状态"只是模拟器内部用于约束"开锁→开门→放料→关门"操作顺序合法性检查的业务字段，不需要、也不会暴露为独立的 DI 寄存器。

"占用状态"不作为独立字段存储，也不对应独立寄存器，始终由光幕 DI 推导：有遮挡即"已占用"，无遮挡即"空闲"。控制 API 的"放料"使实际遮挡成立并更新光幕 DI，"取出"清除实际遮挡并更新光幕 DI；占用变化在动作生效时发生，不要求先关门。故障注入导致光幕 DI 延迟或不跟随时，占用状态同样只按当时可读的光幕 DI 推导，不以模拟器内部的实际遮挡纠正。

开锁不属于控制 API 动作，只能由主系统写 Modbus DO 发起；控制 API 只模拟人工动作"开门、关门、放料、取出"。开门前必须由锁状态 DI 确认已解锁，放料或取出前必须已开门。任何非法状态迁移均须拒绝、返回明确原因，且锁、门、实际遮挡、DI 与派生占用状态均保持请求前状态。

同一仓位的 Modbus 写入、控制 API 动作、自动脉冲复位和故障注入事件按到达顺序串行处理；不同仓位的事件可并行处理，且不得因共享全局状态相互阻塞或串扰。

**边界说明**：主系统的业务态（如异常锁定、已禁用等，参见根目录 [UC-014 启用/禁用仓位](../../../requirement-documents/03-use-cases/uc-014-enable-disable-slot.md)）完全由主系统根据锁状态 DI、光幕 DI 等硬件状态自行判定和维护；模拟器不感知这些业务态，也不提供"禁用仓位"等业务能力。

## Acceptance Criteria 验收标准

- 主系统通过 Modbus 将开锁 DO 写为 1，锁状态 DI 正常跟随为"解锁"后，控制 API 可依次执行开门、放料、关门；放料生效时光幕 DI 立即变为"有遮挡"，派生占用状态立即为"已占用"，无需等待关门。
- 对已占用仓位完成开锁、开门后，控制 API 执行取出时光幕 DI 立即变为"无遮挡"，派生占用状态立即为"空闲"，无需等待关门。
- 控制 API 不提供开锁动作；所有开锁均由主系统写 Modbus DO 发起。
- 未解锁时开门、门关闭时放料或取出等非法迁移被拒绝并给出明确原因，请求前后的全部状态一致。
- 同一仓位事件严格串行，不同仓位事件可并行且互不串扰。

## Verification 验证方式

- **TC-FR-002-001（预留）**：Given 仓位锁定、门关闭且光幕无遮挡；When 主系统写开锁 DO=1，随后 API 依次执行开门、放料、关门；Then 锁状态 DI 为解锁，放料后光幕 DI 立即为有遮挡且派生占用为已占用，关门不改变占用。
- **TC-FR-002-002（预留）**：Given 已占用仓位已通过 Modbus 解锁并由 API 开门；When API 执行取出；Then 光幕 DI 立即变为无遮挡，派生占用立即为空闲，之后可正常关门。
- **TC-FR-002-003（预留）**：Given 仓位仍锁定且门关闭；When API 请求开门；Then 请求被拒绝并返回原因，锁、门、光幕 DI 与派生占用均不变。
- **TC-FR-002-004（预留）**：Given 两个仓位同时接收动作且其中一个仓位连续接收多个事件；When 并发执行；Then 单仓位事件按到达顺序完成，不同仓位可并行且状态互不串扰。
