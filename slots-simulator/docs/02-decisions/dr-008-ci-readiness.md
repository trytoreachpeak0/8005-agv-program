# DR-008 CI 接入能力——架构上保留，当前不搭建流水线本身

## Decision 决策

当前不要求真正把模拟器接入某个 CI 系统，但要求核心逻辑现在就按"能被 CI 使用"的方式设计（对应 [[fr-009-headless-host|FR-009]]、[[fr-010-automation-test-infrastructure|FR-010]]），不能等以后要接 CI 时再返工架构。

## Rationale 理由

用户明确"还是保留这个接入 CI 的能力吧"。具体需要保留的能力点（讨论产出）：

1. **核心逻辑必须能脱离 WPF 独立无界面运行**——这是能否接 CI 的前提条件，因为 CI Runner 通常没有桌面会话，WPF 窗口起不来。因此项目结构上要把"状态机 + Modbus Slave + 控制 API"（Core）与"WPF 界面"（Wpf）分离，WPF 只是 Core 的一种可选客户端，不是必须的启动入口；额外提供一个不带界面的启动方式（Host，如控制台程序）。
2. **状态重置接口**：CI 场景下测试用例之间需要快速恢复干净状态，不能靠重启整个进程；完整 reset 的范围按 [[dr-015-do-power-on-state-vs-reset|DR-015]] 清理运行态、故障和计时器并恢复配置默认值。
3. **健康检查/就绪探针**：CI 脚本拉起模拟器后需要明确信号判断服务是否就绪，避免偶发的连接失败（flaky test）。
4. **确定性时序与职责边界**：模拟器只提供可控的硬件状态、故障和时间刺激，不负责判定"长时间不关门""开锁超时"等业务超时，也不生成业务告警；超时阈值、计时和处置由被测主系统负责。测试可通过保持门/DI 状态、让指定模块不响应，以及缩短主系统测试配置等方式触发超时。模拟器自身只为 DO 脉冲等硬件行为维护必要计时器，不提供会绕过主系统计时逻辑的"直接置业务超时"状态。
5. **结构化日志**：CI 环境没人盯屏幕，失败后要能从保存的日志里复盘状态变化序列。
6. **干净的进程生命周期**：能响应终止信号，保证端口释放、日志落盘完整，不影响下一次实例启动。

## Alternatives Considered 备选方案

曾考虑维持"当前不接 CI"的原判（[[dr-006-users-and-automation-style|DR-006]]）不做任何架构预留，等真要接 CI 时再改；用户认为应该现在就保留这个能力，避免以后返工，因此本决策不推翻 DR-006"当前不搭建 CI 流水线"这一点，只是要求架构设计时不要把这条路堵死。
