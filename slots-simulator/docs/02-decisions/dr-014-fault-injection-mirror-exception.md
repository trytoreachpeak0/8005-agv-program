# DR-014 故障注入允许临时打破 DO/DI 镜像与光幕反馈关系——新增三类脱钩故障场景

## Decision 决策

1. 正常操作路径下（非故障注入触发），锁状态 DI 必须严格镜像开锁指令 DO 的当前电平（[[dr-010-do-control-mode|DR-010]] 已定义），光幕 DI 必须严格反映仓位内实际遮挡情况，模拟器不允许打破这两个关系。
2. 唯一允许打破以上关系的场景是 [[fr-003-exception-scenario-simulation|FR-003]] 的故障注入。新增三类可注入的"脱钩"故障，分别对应锁开合的两个方向以及光幕反馈：
   - **开锁失败（DO→DI 脱钩，开方向）**：主系统下发开锁指令（DO 由 0 变为 1）后，锁状态 DI 保持"锁定"不跟随变化，模拟电子锁本身机械/电气故障导致的开锁失败。
   - **闩锁/复位失败（DO→DI 脱钩，闩方向）**：DO 变回 0（无论是主系统显式写 0，还是脉冲模式超时后模拟器自动复位）后，锁状态 DI 保持"解锁"不跟随变回锁定，模拟锁虽已断电但未能真正闩上的故障。
   - **光幕反馈脱钩**：光幕 DI 卡死在故障注入发生时的值，此后不再随仓位内实际遮挡情况的变化而更新，模拟光幕传感器/反馈线路本身失灵。这与 FR-003 中已有的"开门后有异物""关门后有残留"等业务语义场景不同——那些场景下光幕本身工作正常，只是仓位内实际状态不符合预期；这里是传感器/反馈本身失效，与仓位内实际状态无关。
3. 触发某个点位的脱钩故障后，该点位应保持脱钩状态直至通过 HTTP/JSON 控制 API 显式清除，或执行完整 reset。清除故障后恢复正常镜像/反馈关系，并立即按当前 DO、实际遮挡重新计算对应 DI，不保留故障期间的陈旧反馈值。
4. IO 通信故障按指定模块实例注入，至少支持两种模式：
   - **断连**：主动关闭该模块现有 Modbus TCP 连接，并在故障清除前拒绝/立即关闭新连接；
   - **不响应**：保持连接但不返回 Modbus 响应，用于测试主系统请求超时。
   其他模块实例继续正常服务。两种模块故障均可显式清除；清除后模块恢复接受请求，不要求重启整个模拟器。

## Rationale 理由

用户确认 [[fr-003-exception-scenario-simulation|FR-003]] 原有"开锁失败/超时（触发开锁指令后不返回锁状态变化）"措辞描述的正是"给了 DO 信号但锁没弹开"的故障，这与 DR-010"锁状态是 DO 电平的实时镜像"在字面上存在冲突。用户选择保留该异常场景的可测试性，做法是明确"故障注入是模拟器唯一被允许打破镜像关系的场景"，并进一步补充闩锁方向和光幕反馈两类同类故障，使故障注入能力更完整地覆盖三类点位关系（DO↔锁状态DI 的两个方向、光幕DI↔实际遮挡）可能出现的脱钩情形，也顺带覆盖了原报告中"门状态信号异常"的诉求——因门状态本身由锁状态推算（见 [[dr-013-door-state-not-independent-io-point|DR-013]]），其信号异常本质上就是锁状态 DI 反馈脱钩。

多模块部署下，断连和无响应会触发主系统不同的网络处理路径，且局部模块故障不应拖垮其他模块；因此必须可按模块、按模式注入并可恢复。

## Alternatives Considered 备选方案

- 曾考虑只支持电平/脉冲两种正常控制模式，不提供任何打破镜像关系的手段，把"开锁失败"这类场景改写为纯业务语义（如仅在门状态层面模拟）——因无法真实还原"DO 已下发但锁状态没有正确反馈"这类底层硬件故障对主系统 IO 对接代码的影响，未采纳。
- 曾考虑只新增一条"锁状态与 DO 脱钩"的笼统场景，不区分开/闩两个方向——因两个方向对应的故障原因和主系统应有的处理逻辑不同（开方向对应"仓位不可用"，闩方向对应"锁没有真正闩上、可能被误认为已完成关闭"），拆分为两条更利于自动化测试脚本精确断言。
