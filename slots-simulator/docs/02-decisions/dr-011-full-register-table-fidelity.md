# DR-011 寄存器表完整还原为可配置模板

## Decision 决策

1. **寄存器表做成可配置的"模块类型模板"，不写死在代码里**：以真实 IO 模块（康耐德 C2000-A2-KDDA0A0-AD6）说明书的寄存器表为依据建立首个模板，以后如果换了另一型号的 IO 模块，只需要换一份模板配置，不用改代码。
2. **模板要完整还原说明书里的整份寄存器表**：不只是 DO/DI 状态等"业务相关"寄存器，也包括模块自身的 MAC 地址、IP/端口/子网掩码/网关、工作模式、DI 滤波参数、脉冲计数器等所有寄存器。
3. **模板中声明的 DO/DI 数量是该型号模块的硬性上限**，仓位的 DO/DI 点位映射不能指向超出模板范围的通道。
4. **配置格式统一为 JSON，并提供 JSON Schema**：模块模板、模块实例、仓位映射、布局及运行默认值均应能由 Schema 做结构、类型、枚举、必填项和基础范围校验；跨对象引用、地址重叠、端口冲突、通道容量等语义约束再由应用层严格校验。无效配置不得部分加载。
5. **区分动态核心与静态保真**：DO、DI、DO 工作模式、DO 脉冲宽度是首批核心动态寄存器，读写会驱动或反映运行时行为；其余寄存器按模板提供协议级读写与合理初值，但只有在设备资料明确规定且项目确认后才增加副作用，不因"完整还原"而虚构行为。

## Rationale 理由

背景：[[dr-005-modbus-protocol-fidelity|DR-005]] 最初以"点位表尚未最终确认"说明可配置性的必要性；用户现已提供真实设备 [reference/C2000-A2-KDDA0A0-AD6_寄存器表.md](../reference/C2000-A2-KDDA0A0-AD6_寄存器表.md)，确认寄存器位置固定、DO/DI 数量有限。这里更新为：设备寄存器表已知并作为首个模板依据，仍待具体项目配置的是各仓位到模块实例/通道的分配。

1. 做成可配置模板而不是写死代码，是延续项目一贯的"不写死"风格（参考 [[dr-004-configurable-slot-count|DR-004]]、[[dr-005-modbus-protocol-fidelity|DR-005]]）：寄存器表虽然现在已知，但仍然可能因为换型号 IO 模块而变化，不应该和某一具体型号强绑定在代码里。
2. 完整还原整份寄存器表（而不是只挑 DO/DI 状态等业务相关的一部分），是因为模拟器的目标是让被测系统"感觉不到在连接的是模拟器还是真实硬件"（见 `../00-vision/vision-and-scope.md` 第 2 节），如果只模拟业务相关寄存器，被测系统一旦读取/校验模块信息类或网络配置类寄存器（如设备型号、MAC 地址），就会立刻暴露出连接的是模拟器；完整还原可以避免后续因为发现遗漏而返工。
3. 模板声明的 DO/DI 数量作为硬性上限，是因为这是真实硬件的物理限制（一个模块确实只有 16 个 DO、16 个 DI），仿真如果不遵守这个限制，会让测试结果失去参考意义。
4. JSON + Schema 便于 WPF 编辑器、Headless Host 和脚本共享同一份机器可校验契约；应用层语义校验补足 JSON Schema 无法完整表达的跨引用和资源边界。

## Alternatives Considered 备选方案

- 曾考虑只模拟与仓位控制直接相关的寄存器（DO 状态、DO 工作模式、DO 脉冲宽度、DI 状态），网络配置类寄存器（MAC/IP/子网掩码等）先不管——因为担心以后被测系统的点位表核对测试（参考根目录 [UC-018 IO 点位映射表核对测试](../../../requirement-documents/03-use-cases/uc-018-io-point-mapping-verification-test.md)）或联调过程中读取到这些寄存器，未采纳，选择完整还原。
