# 最小状态闭环实验

## 1. 目标

用一台测试车和一个安全短距站点，回答 Q-001～Q-005：

- 哪个 API 面适合创建本项目移动任务。
- 如何关联本地标识、订单标识、车辆和站点。
- 哪个信号能可靠表示接单、移动、到站、完成和重新空闲。
- 相同 `upperId` 重复提交的行为。
- 车辆任务队列“0 或 1”的可观测判定。

本实验不是性能测试，也不覆盖充电、停靠和多仓位动作。

## 2. 前置条件

- A1、B1、B2、C1、C2 已通过。
- 已确认唯一测试车在线、自动模式、定位正常且没有未识别订单。
- 已由用户确认同图、短距、不影响产线的目的站。
- 本轮明确批准创建、取消测试车订单；未批准的写接口不得调用。
- 已准备统一状态采样器，能够在同一时间轴记录所有候选状态面。

## 4. 执行步骤

### MC-01 建立空闲基线

连续采样至少 3 次，确认车辆状态稳定，并保存订单查询、车辆任务信息和设备运行时状态。无法证明车辆空闲时停止实验。

### MC-02 比较建单 API 面

先根据 Swagger 分别整理 Task API 与 Order API 的最小合法请求，但不要在同一时刻创建两笔真实订单。

推荐顺序：

1. 在安全环境只执行一个候选 API。
2. 保存完整请求、响应和返回标识。
3. 用 Task 与 Order 两个查询面交叉查询同一订单。
4. 完成或取消并确认车辆回到基线。
5. 用户确认可以继续后，再用另一个候选 API 创建独立 `upperId` 的订单。

比较维度：

- 是否允许显式指定唯一测试车。
- 是否只需目的站，还是依赖模板。
- 返回哪些订单标识。
- 能否通过 `upperId` 反查。
- 是否进入同一调度队列。
- 后续查询、取消和状态字段是否一致。

在完成比较前，不把任一候选接口写成项目正式建单契约。

### MC-03 完整成功轨迹

选择已确认的建单 API 创建一笔短距订单。自提交前开始，每 2～3 秒采样：

- 订单详情和 mission。
- 测试车调度信息。
- 车辆聚合状态和当前站点。
- 设备 `sysState`、`movementState` 等相关物模型属性。

人工观察到“车辆开始移动”和“物理进入目标站”时，向日志写入带时间戳事件。持续采样到订单终态并确认车辆恢复可接单状态。

### MC-04 幂等与响应丢失模拟

不直接假设重复提交安全。先用 `upperId` 查询已完成订单，再在批准范围内提交相同 `upperId`：

- 若返回原订单，记录其识别方式。
- 若拒绝，记录业务码和消息。
- 若创建新订单，立即按安全边界收尾，并把“`upperId` 不幂等”记录为重大契约发现。

### MC-05 取消轨迹

使用新的 `upperId` 创建第二笔短距订单，在明确进入执行态后调用候选取消接口。持续采样到订单和车辆都进入稳定状态，并验证队列重新为空。

`interrupt` 不与本步骤混测；它属于单独的暂停/恢复实验。

## 5. 通过条件

本实验通过不等于所有假设都成立，而是必须产出足够证据回答：

1. 项目应该采用哪个建单 API，或者明确说明当前仍不能选型。
2. `upperId`、RIoT 订单标识、测试车和站点如何关联。
3. “到站”“订单完成”“车辆重新空闲”分别由哪些观测判定。
4. 队列 0/1 使用哪个查询和字段判断。
5. 相同 `upperId` 重复提交的真实结果。
6. 成功与取消两条完整时间轨迹。

任何无法回答的项都回到 [`../hypotheses/open-questions.md`](../hypotheses/open-questions.md)，不得用常见 RCS 经验补齐。
