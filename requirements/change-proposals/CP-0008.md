## 为什么要改

### 一、交接终止写不写抑制，基线前后说法相反

- `REQ-0240`：故障货物交接完成后，系统形成 `FaultCargoRecoveryRecord`，「与原任务 `TERMINATED_BY_FAULT_CARGO_HANDOFF` 终态及对应 `TransportDemandKey` 的永久抑制原子提交」。
- `REQ-0242`：强制取出、身份明确并完成交接时，「允许终止对应任务并写入抑制」。
- `REQ-0156`：「抑制只由本地取消产生」，只列了四个 `CANCELLED_BY_*` 码。

按 `REQ-0156` 的字面，交接不写抑制，`REQ-0240` 就永远满足不了；按 `REQ-0240`，又违反 `REQ-0156` 的「只由」。

**本意应当是交接也写抑制**（起草时的判断，用户同意按此出提案）：
- `REQ-0240`、`REQ-0242` 出自专门讲故障车货物处置的决定（`.scratch/current-requirements-baseline/issues/69-…`），写明了「原子提交」。
- `REQ-0156` 出自讲需求身份与取消抑制边界的决定（`issues/56-…`），它要划的线是「本地取消」与「MES 那边消失（`MES_DISAPPEARED`、`GONE`）」，不是要把交接排除在外。
- `CONTEXT.md` 的「故障载货补救记录」词条写的也是「身份明确的完整交接与原任务 `TERMINATED_BY_FAULT_CARGO_HANDOFF` 终态及 TransportDemandSuppression 原子提交」。
- MVP 线（生产在跑）当年就给交接写了抑制（control-server 提交 `557644a6`）。v2 线按 `REQ-0156` 的字面只写四个码（control-server#210，批次7-05，`PickupStopTermination.cs` 的 `KeySuppressingReasonCodes`），是只核了 `REQ-0156`、漏看了 `REQ-0240`。

**不改的后果**：交接之后 MES 那边任务仍在（`REQ-0240`：「不表示 8005 或 MES 已完成运输」）。MesIngest 以新 `DemandId` 再出这个键时，v2 会再派一次车。货已被取走，到站录入对不上，操作员只能取消；货若被放回原处，就会被搬第二次。

### 二、强制取出的货现场都能识别

`REQ-0242` 末句为「产品身份不明时只记录实物，相关任务保持待盘点，不猜测绑定」。用户 2026-09-29 给出现场事实：强制取出的货现场一定能识别。所以这一支没有发生的场景，也不应让实现去维护一条走不到的路。协议 v3 的强制取出交接记录已按此去掉身份不明的取值（program#149）。

## 一、修订既有条目

### 修订项一：`REQ-0156` 故障货物交接终止也写抑制

#### 基线原文

> 抑制只由本地取消产生。 CANCELLED_BY_OPERATOR、CANCELLED_BY_LOAD_COMPENSATION、CANCELLED_BY_STOP_COMPLETE 与 CANCELLED_BY_STATION_TIMEOUT 均原子写入 TransportDemandSuppression；单纯 MES_DISAPPEARED 或 GONE 不写抑制，同键以后再现时可作为新实例重新进入调度判断。

#### 建议修订文

> 抑制由本地取消与故障货物交接终止产生。 CANCELLED_BY_OPERATOR、CANCELLED_BY_LOAD_COMPENSATION、CANCELLED_BY_STOP_COMPLETE 与 CANCELLED_BY_STATION_TIMEOUT 均原子写入 TransportDemandSuppression；按 REQ-0240 与 REQ-0242 以 TERMINATED_BY_FAULT_CARGO_HANDOFF 终止的任务同样与终态原子写入抑制。人员放弃已停止的自动重建、在车上没有该任务货物时终止任务的，不写抑制，因为货物从未离开原取货位置，同键以后再现时可重新派车；单纯 MES_DISAPPEARED 或 GONE 不写抑制，同键以后再现时可作为新实例重新进入调度判断。

#### 修订说明

1. **改了什么**：
   - 首句「只由本地取消」改成「由本地取消与故障货物交接终止」；
   - 加一句：以 `TERMINATED_BY_FAULT_CARGO_HANDOFF` 终止的任务同样原子写入抑制。故障货物交接（`REQ-0240`）与强制取出后交接（`REQ-0242`）两条路都落在这个终态上（control-server `OnboardRecoveryCoordinator.cs` 实读）；
   - 加一句：人员放弃已停止的自动重建时不写抑制，并写明理由；
   - 原有四个码与「`MES_DISAPPEARED`／`GONE` 不写」一字未动。
2. **「人员放弃已停止的自动重建」不写抑制（用户定写明，理由起草时定）**：
   - 这是 `REQ-0361` 护栏停住之后由人员处理的出口之一，实现上以 `TERMINATED_BY_OPERATOR_AFTER_REBUILD_STOP` 终止（control-server#345）。实现只在车上没有该任务货物时允许这样终止。
   - 那时货物还在原取货位置，MES 那边的任务也还在。以后同键再现，重新派车去取正是该做的；写了抑制，这批货就再也不会被搬。
   - 条文写行为不写码：码是实现名。
3. **标题行会变**：首句改了，前 54 个字符随之变化。
   - 原：`抑制只由本地取消产生。 CANCELLED_BY_OPERATOR、CANCELLED_BY_LOAD_CO…`
   - 新：`抑制由本地取消与故障货物交接终止产生。 CANCELLED_BY_OPERATOR、CANCELLED_BY…`
   - 这是本提案与 `CP-0006`、`CP-0007` 的一处不同，请用户批准时留意。
4. **与 `REQ-0155` 的关系**：`REQ-0155` 的标题是「本地取消终态挂 DemandId，禁止再次执行业务挂 TransportDemandKey」，正文讲的是抑制命中后的效果，不限定抑制从哪来。本提案不改它；命中效果对交接写下的抑制同样适用。

### 修订项二：`REQ-0242` 去掉「身份不明、待盘点」分支

#### 基线原文

> 货物业务闭环与设备恢复闭环分离。 强制取出后，产品身份明确且完成具名交接时，ForcedCargoHandoffRecord 可以证明货物已经救出和责任交接，允许终止对应任务并写入抑制，但不能证明电子空仓、仓门安全或车辆恢复。产品身份不明时只记录实物，相关任务保持待盘点，不猜测绑定。

#### 建议修订文

> 货物业务闭环与设备恢复闭环分离。 强制取出后，产品身份明确且完成具名交接时，ForcedCargoHandoffRecord 可以证明货物已经救出和责任交接，终止对应任务并写入抑制，但不能证明电子空仓、仓门安全或车辆恢复。强制取出的产品在现场都能识别身份，不设身份不明时只记录实物、任务待盘点的分支。

#### 修订说明

1. **改了什么**：
   - 「允许终止对应任务并写入抑制」改为「终止对应任务并写入抑制」，与修订项一和 `REQ-0240` 一致：交接完成就终止并抑制，不是可选；
   - 末句「产品身份不明时只记录实物，相关任务保持待盘点，不猜测绑定」换成「强制取出的产品在现场都能识别身份，不设……待盘点的分支」。
2. **依据**：用户 2026-09-29 给出的现场事实「强制取出的货现场一定能识别」（经调度会话 Coordinator 9 转达）。
3. **协议已按此处理**：协议 v3 的强制取出交接记录去掉了身份不明的取值（program#149，批次8-04）。本条让需求与协议一致。
4. **修订在前 54 个字符之后，标题行不变**（已核对：前 54 个字符止于「ForcedCargoHando」）。

## 二、提案边界：核查后不需要修订的条目

在 `v1.6.0` 全部条文里检索「抑制、Suppression、待盘点、身份不明、`TERMINATED_BY_FAULT_CARGO_HANDOFF`」，命中的条目逐条核查：

| 条目 | 为什么不动 |
| --- | --- |
| `REQ-0155` | 讲抑制命中后的效果，不限定来源（修订项一说明 4） |
| `REQ-0240` | 本来就要求交接与抑制原子提交；本提案让 `REQ-0156` 与它一致 |
| `REQ-0211` | 同站取消以 `CANCELLED_BY_OPERATOR` 终结并永久抑制，在原四个码之内 |
| `REQ-0150`、`REQ-0153`、`REQ-0154` | 对账键与实例身份，不涉及抑制从哪来 |
| `REQ-0001` | MesIngest 不拥有取消抑制，与本提案无关 |
| `REQ-0096` | MesIngest 自身写入抑制，是另一件事（文件事件），关键词误命中 |

## 三、ADR、`CONTEXT.md` 与协议

1. **ADR：不需要改。**在 `docs/adr/` 下检索「抑制、Suppression、待盘点、身份不明」：
   - ADR-cross-0047 讲取消后按 `TransportDemandKey` 永久抑制，举的是 `CANCELLED_BY_OPERATOR` 与 `CANCELLED_BY_LOAD_COMPENSATION` 两例，没有写「只有取消才抑制」，与本提案相容；
   - ADR-cross-0038、0039 讲装货补救的抑制，在原四个码之内；
   - 没有 ADR 讲待盘点分支。
2. **`CONTEXT.md`：两个词条要改**，与需求条文保持一致，随基线落地一并提交。

   「故障载货补救记录（FaultCargoRecoveryRecord）」词条，现文末句：

   > ……身份明确的完整交接与原任务 `TERMINATED_BY_FAULT_CARGO_HANDOFF` 终态及 TransportDemandSuppression 原子提交，产品身份未知时相关任务保持待盘点。

   改为：

   > ……身份明确的完整交接与原任务 `TERMINATED_BY_FAULT_CARGO_HANDOFF` 终态及 TransportDemandSuppression 原子提交；强制取出的产品在现场都能识别身份，不设身份未知时待盘点的分支。

   「强制取出交接记录（ForcedCargoHandoffRecord）」词条，现文：

   > ……身份明确时它证明货物已经救出并完成责任交接，允许关闭对应货物业务，但不证明电子空仓、仓门安全或设备恢复。产品身份不明时只形成实物记录并保持相关任务待盘点。

   改为：

   > ……身份明确时它证明货物已经救出并完成责任交接，关闭对应货物业务并写入抑制，但不证明电子空仓、仓门安全或设备恢复。强制取出的产品在现场都能识别身份，不设身份不明时只形成实物记录的分支。

   两个词条的 `_Avoid_` 行（含「未知产品猜绑定」）不改。
3. **协议：不需要改。**抑制是服务端内部状态，不经过车载协议。强制取出交接记录去掉身份不明取值，已由协议 v3（program#149）处理。
